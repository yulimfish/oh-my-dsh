# dsh-omo — Oh My DSH-style orchestration

An independent DeepSeek Harness plugin that brings an Oh My OpenCode-inspired specialist workflow to DSH. It is being implemented against the installed DSH `0.2.0-rc.2` APIs; it does **not** install or depend on the incompatible `dsh-autopilot` alpha. No Oh My OpenCode source code is copied. This is an early-stage compatibility layer, not a claim of complete 1:1 feature parity or affiliation with either project.

## First milestone

- Adds `dsh_omo_task`, a bounded one-shot launcher with automatic parent follow-up, and an opt-in `dsh_omo_task_continuable` tool backed by DSH durable child sessions. Specialist roles include `explore`, `librarian`, `architect`, `plan-consultant`, `plan-reviewer`, `ultrabrain`, `quick`, `visual`, `reviewer`, `test`, and `security`.
- Adds role personas, opt-in per-role model routes, reasoning effort and token ceilings, inherited tool-scope allow/deny filters, and bounded literal `promptAppend` guidance in delegated task messages.
- Adds twelve packaged workflow skills: four `/omo-*` skills plus `debugging`, `frontend`, `git-master`, `init-deep`, `remove-ai-slops`, `review-work`, `security-research`, and `visual-qa`; these guides do not reproduce upstream lifecycle integrations.
- Adds a cwd-aware provider for project `.opencode/skills` and `.claude/skills` files through DSH skill/filesystem services.
- Adds default-off, one-shot support for safe current-session-CWD `.claude/agents/*.md` prompt personas; no global discovery or permission parity.
- Adds `/omo-skills-refresh` to invalidate the project-skill catalog after local edits; filesystem watchers normally refresh it automatically.
- Adds persistent system-prompt guidance for task decomposition, parallel delegation, integration, and verification.
- Adds `/ulw`, `/ultrawork`, `/ulw-execute`, `/architect`, `/review`, `/handoff`, `/refactor`, `/remove-ai-slops`, `/omo` (including `/omo status`), `/omo-tasks`, `/omo-interrupt`, and `/omo-skills-refresh`; `/goal` and `/omo-models` are registered when their native DSH services are available, or when the default-off models.dev refresh is enabled with DSH `web.fetch` and its selected provider can return the full catalog untruncated. `/stop-continuation` is registered only when the native DSH Goal service exposes `get` and `clear`. Task commands still report DSH residency/interrupt attempts, not plugin origin or guaranteed completion.
- `/ulw-execute <existing plan name>` asks the current agent to locate and follow an existing approved project plan, asking if missing or ambiguous. It is prompt-only: no OMO hook/session-history resume, Atlas/Sisyphus selection, boulder/notepad state, worktree, PR, shipping, or merge lifecycle; `--worktree`, `--make-pr`, and `--ship` are rejected.
- Adds opt-in native Agent Teams tools (`enableTeamTools: true`) when the DSH `agentTeams` service exists; DSH remains authoritative for Team membership, permissions, persistence, messages, and task revisions.
- Adds default-off model-facing `dsh_omo_goal_get`, `dsh_omo_goal_create`, and `dsh_omo_goal_update` tools via `enableGoalTools`; operations target only the exact calling Agent and use DSH revision-fenced Goal state; create never clears a Goal or replaces a non-complete current Goal.
- Adds user-configured category-to-primary-route delegation via `categoryRoutes` and optional `category` arguments; categories may specify up to three ordered explicit `fallbackModels`, which use a bounded DSH spawn-time capability preflight (not upstream model resolution or runtime fallback); categories also support reasoning, an optional `maxTokens` ceiling, disabled-route filtering, task-tool descriptions, partial inherited-tool allow/deny filters (`tools: true`/`false`, with category allows intersecting role allowlists and denies winning), and bounded task-message `promptAppend` (not a system prompt). Categories are not personas or a built-in upstream registry.
- Adds a default-off, profile-wide `runtimeFallback` controller with up to 32 exact primary provider/model chains, each containing 1–3 explicit fallback routes. It preserves delegated `{kind:'retry'}` actions and consults the supplied `retryPolicy`; it will not cross-route while a normal policy still has retry budget beyond observed delegated same-route retry actions (counted cumulatively across error codes for that route/Agent step), and `always`/unknown/malformed policies fail closed. When no same-route retry remains (or the error is not retryable under that policy), it switches only for selected `failure.status` HTTP values. It does not discover provider/model availability or provide OMO cooldown, timeout, toast, or primary-restoration behavior. A successful provider switch can affect later Agent requests; configure only providers approved for the prompt data.
- Adds on-demand `/omo-models` diagnostics over registered DSH providers and exact model metadata, plus a default-off, explicit-user-invoked models.dev snapshot refresh that stays in memory and advisory; no startup refresh, durable cache, synthetic LLM call, or route gate.
- Adds a default-off, explicit human-only `/omo web-search <query>` subcommand backed by at most one DSH `web.search` call per invocation (maximum five results); it is not an Agent Tool/MCP adapter and never auto-fetches returned URLs.
- `/omo status` reports dsh-omo feature flags and optional-service presence observed during plugin setup only; it does not call business Service methods, query models, read session content, or claim runtime health/readiness. The separate explicit `/omo status capabilities` query reads the configured DSH subagent provider's advertised capability flags and up to 32 IDs from the live LLM provider registry. These are registry declarations, not endpoint health, model availability, route compatibility, or future-call guarantees; this command does not resolve models or preflight routes.
- Adds opt-in, read-only `lsp_goto_definition` and `lsp_find_references` adapters when DSH `lsp.query`, `sessions.get`, and filesystem canonicalization methods are available; input paths are canonicalized and checked against the invoking Agent cwd (not a race-free OS sandbox), while provider-returned URIs are untrusted metadata and may identify files outside that cwd.
- Adds optional `enableRootAgentsContext` to snapshot bounded cwd-level `AGENTS.md` into each new Agent's DSH `systemPrompt.context()` scope at awaited `agent/created`, before its first step; it is root-only, untrusted repository text, and has no file watcher.
- Adds independent opt-in `enableAgentsOnRead` to append bounded root-to-nested `AGENTS.md` context after successful DSH `read` calls through `tools/post-execute` `additionalContexts`; it preserves the native read result, stays inside the Agent cwd, and treats repository text as untrusted.
- Adds separate opt-in `enableRootReadmeContext` to snapshot only the cwd-root `README.md` into the Agent prompt before its first step; unlike upstream OMO's post-`read` output mutation and root-to-nested README walk, this is a bounded DSH creation-time snapshot with no backfill or watcher.
- Adds independent opt-in `enableReadmeOnRead` to enrich successful DSH `read` calls with bounded root-to-nested README contexts. It uses DSH `tools/post-execute` `additionalContexts` so the native read value/content stays intact; this is a separate user message, and only safe relative or in-cwd POSIX absolute `file_path` values are supported.
- Adds default-off `enableClaudeRulesOnRead` to scan only cwd-root `.claude/rules` Markdown (`.md`/`.mdc`) files after successful `read`, `write`, and `edit` calls and append matching rule contexts through `additionalContexts`; the legacy flag name is retained, no verified `multiedit` schema is available to this adapter, and this remains a root-only partial adapter with no ancestor/project-root or home/global rule discovery or native Tool-result mutation.
- Adds default-off `enableWriteExistingFileGuard` for a one-use permission after a successful same-live-Agent Tool call named `read`, before an existing in-cwd target is written through a Tool named `write` (case-insensitive name matching includes same-named custom Tools). It honors upstream `.omo`/`overwrite` bypasses while a bounded decision slot is available; verified missing/out-of-cwd targets normally pass below the caps, though saturation may busy-deny writes. It does not guard `edit` or shell; DSH's preflight→read/write gaps mean it is not a security boundary.
- Adds default-off `enableEditErrorRecovery` to append a fixed read-before-retry guidance message after a schema-verified DSH `edit` failure matching a pinned OMO error pattern; it preserves the native outcome and never retries or rewrites the call.
- Adds default-off `enableJsonErrorRecovery` to append fixed JSON-parse guidance after bounded matching DSH Tool failures, excluding upstream and DSH content-heavy tools; it does not rewrite arguments or auto-retry.
- Adds default-off `enableBashFileReadGuidance` to append fixed post-execution advice after a successful, simple Bash `cat`, `head`, or `tail` file read; it leaves the command and native Tool result unchanged and is not a guard.
- Adds opt-in read-only `session_search` (`enableSessionSearch: true`) when DSH `sessionQuery` is available. Search defaults to the current Agent session cwd; cross-project search requires `includeOtherProjects: true`. Results are bounded snippets, not log bodies; a cold workspace observation or search indexing may still do full-session work internally, and index completeness is backend-dependent.
- Adds separately opt-in `session_read` (`enableSessionRead: true`) for one DSH `readEvent` window. It defaults to the current workspace and target-only reads, caps explicitly requested context to four events on either side (subject to any stricter Host limit), and returns only bounded direct-user/model-assistant text, omitting synthetic user-role context, system/developer content, reasoning, tool calls/results, and attachments; it does not expose a full session or resume it, though RC2 `readEvent` loads/snapshots the complete target log before slicing the bounded response window (live sources snapshot all events; persisted sources read/reconstruct the full log); a cold current-Agent workspace observation may also prepare that Agent's full log.
- Adds separately opt-in `session_list` (`enableSessionList: true`) for bounded listing, metadata-only by default. It defaults to the current workspace, supports inclusive date bounds, caps output at 25 records, and has no stable page cursor; the Host materializes the complete logical corpus before filtering. When DSH exposes title-snapshot support, explicit `includeTitles: true` adds sanitized untrusted titles for at most the first three displayed rows; each title-snapshot lookup may scan or reconstruct a complete target log, so this deliberately bounded opt-in can still be expensive. It returns no event text, and a cold current-Agent workspace observation may also prepare that Agent's full event log. This title option is a DSH-specific convenience, not upstream OMO behavior (which lists IDs, message counts, date ranges, and agents; see [upstream tool](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/tools/session-manager/tools.ts) and [formatter](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/tools/session-manager/session-formatter.ts)).
- Adds separately opt-in `session_info` (`enableSessionInfo: true`) for one session's allowlisted header and optional bounded title. Title lookup snapshots/scans the entire live target log or reads/reconstructs the complete persisted target log on every call; it returns no event text or message statistics. Default scope is the current workspace; global scope is only a model-supplied selector, not authorization.
- Adds optional DSH Host job monitoring (`enableJobTools: true`) through `dsh_omo_job_list` and `dsh_omo_job_follow`. It defaults off, derives the service owner from the current Agent, caps streams/output, drops `JobView.detail` and `output.spillPaths`, and exposes no model-facing kill Tool. With the same opt-in and a Host `jobController.kill` method, the separate human-only `/omo-job-kill` command can request cancellation. This does not implement OMO `background_output`, `background_cancel`, or subagent-result retrieval.
- Adds `/remove-ai-slops` steering that reuses the bundled workflow skill; it is not an automatic diff hook or enforcement boundary.
- Adds project skills as a source in the DSH skill registry. Provider reads use `ctx.fs`, cwd containment, file-version checks, and a post-read path revalidation—not model-facing filesystem tools or their approval prompts; DSH remains authoritative for normal tool mutations, shell/network access, and approvals.

A role prompt and `allowTools`/`denyTools` filters are not a hard security boundary. In DSH RC2, the subagent tool filter affects inherited global and ancestor-scope tools; the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport may still be visible. For must-be-read-only work, verify that DSH-native permissions, sandbox policy, or tool guards cover every visible tool, including scoped registrations and the reserved transport; dsh-omo does not install a per-worker hard guard; its optional write-existing-file guard covers only Tool calls named `write` case-insensitively (including same-named custom Tools; other names bypass) and does not remove the stat→write TOCTOU. Project-skill provider reads do not pass through model-facing tool approval or mutation-sandbox checks; they use the mounted DSH filesystem backend, cwd containment, version checks, and post-read path revalidation. The RC2 filesystem contract has no atomic no-follow open, so an adversarial concurrent swap-and-restore could still evade path checks; this is not a race-free OS read sandbox. Treat repository skill content as untrusted and do not use it to expose secrets.

## Install in an isolated profile

Build a local package tarball, then add it to a dedicated profile:

```sh
cd oh-my-dsh
pnpm install
pnpm run check
pnpm pack --pack-destination .artifacts

# Create/seed the isolated audit profile from the shipped web template, then add the tarball.
dsh --profile ohmy-test --from-default-profile web --dump-config
dsh plugin --profile ohmy-test add "$(pwd)/.artifacts/dsh-omo-0.1.9.tgz"
dsh --profile ohmy-test --dump-config
```

The user-facing app should be restarted after adding the package. Test the isolated profile first; only add it to `desktop` after reviewing the effective configuration.

## Configure roles

The package installs a bundle row in `cordis.patch.yml`. Add entries to `roleRoutes` for provider/model, reasoning, token ceilings, inherited tool-scope filters (`allowTools`/`denyTools`, at most 64 names of up to 128 UTF-8 bytes each), and bounded literal `promptAppend` guidance. For one-shot launches that emit a filter, the DSH subagent provider must advertise `toolFilter`; DSH rejects unsupported filters before publishing a child. Continuable tasks apply the filter through DSH's scoped `tools.restrict` path and do not require that provider capability flag. `enableContinuableTasks` defaults to `false`; turn it on only after verifying the selected DSH subagent provider implements the optional `prepareContinuable` method and the DSH persistence path is available. Optional DSH-native `userAgents` definitions require `name` and `prompt`, accept optional `description` and `mode` (omitted `mode` defaults to `subagent`), and add up to 32 config-only named subagents. Names are ASCII slugs of at most 64 characters, descriptions are limited to 512 UTF-8 bytes, and raw persona prompts are limited to 16 KiB each (64 KiB total). Only `mode: subagent` is supported. The prompt is passed as DSH `SubagentStartRequest.persona`, so a custom role fails closed unless the selected DSH subagent provider advertises `persona`; use `roleRoutes`/`categoryRoutes` for model and inherited-tool routing, and `disabledOmoRoles` may disable built-in or custom names.

### Project agent files

With `enableProjectAgentFiles: true`, an extra dsh-omo roster tool scans only the active session cwd's direct `.claude/agents/*.md` files; select one in the one-shot task tool with `role: __project_agent_file__` and `agentFile: <lowercase ASCII slug filename stem>`. This adapter accepts stems matching `[a-z][a-z0-9-]{0,63}` only. The loader rereads the selected file, requires a matching `name`, optional single-line `description`, and a non-empty file body (it does not parse Markdown syntax), and accepts optional bounded `tools` metadata as a comma-separated scalar or YAML string array. It rejects unsupported metadata (including model/permission fields), YAML tags/aliases/nesting/multiline values, invalid UTF-8, symlinks, and paths outside cwd. Listing and launch fail closed unless the configured DSH subagent provider advertises `persona`.

This feature is default-off and bounded at the adapter level (it copies/processes at most the first 256 direct entries, returns at most 32 roster entries, reads at most 16 KiB/file and 128 KiB per roster, and applies a five-second deadline per list/load operation; a backend that ignores `AbortSignal` may continue I/O after return). DSH `fs.listDir` has no paging/limit contract and returns the full direct-child array, so an unusually large directory can still cause Host-side allocation before the adapter cap.

The roster returns only filename/name/description, while only the sanitized body becomes provider `persona`; `tools` metadata is not exposed in the roster.

A non-empty `tools` list is lowercased/deduplicated and capped at 64 names of at most 128 UTF-8 bytes each. At launch, every name must resolve to a DSH global Tool visible in the parent scope, and the selected provider must advertise `toolFilter`. The list becomes a one-shot allowlist for inherited global/ancestor DSH tools and intersects the selected category filter (denies win); unknown/unavailable names or an empty intersection fail closed. Missing or empty `tools` leaves existing inherited-tool behavior unchanged. The reserved DSH name `run_code` is rejected in configured filters. This maps only to DSH `SubagentStartRequest.toolFilter`, not full Claude permission semantics: child-scope registrations and the reserved PTC transport may remain visible, so it is not a hard permission boundary.

Project instructions are untrusted prompt text and cannot directly grant tools, but may influence a child that already inherits tools; the warning is advisory rather than an enforcement boundary. Treat this mode as trusted-repository-only, select a category with restrictive inherited-tool filters, and retain DSH approvals/policy. Project-file agents have no role-specific route.

Files cannot define model routes or full permission semantics beyond the narrow inherited-tool allowlist, and the selected file is reread at launch. There is no home/global/ancestor scan or merge, primary-agent switching, Host-native picker, or per-agent skills/display metadata.

DSH filesystem reads are plugin-level, not an approval-gated model Tool, and identity/version rechecks cannot remove TOCTOU risk. The existing role/filter warning above applies to these definitions as well.

    maxConcurrent: 4
    # Optional LLM-route subcaps; model keys are exact provider/model pairs.

    providerConcurrency: { deepseek-official: 2 }
    modelConcurrency: { 'deepseek-official/deepseek-flash': 1 }

    maxTaskChars: 12000
    maxResultChars: 8000

    enableGoalTools: false
    enableTeamTools: false
    enableSessionSearch: false
    enableSessionRead: false
    enableSessionList: false
    enableSessionInfo: false
    enableJobTools: false
    enableToolResultPruning: false
    enableAgentTerminalTools: false
    enableLspTools: false
    enableRootAgentsContext: false
    enableAgentsOnRead: false

        category: research

`providerConcurrency` accepts at most 64 exact provider IDs and `modelConcurrency` at most 128 exact `provider/model` keys; values are non-negative safe integers. A model entry overrides its provider entry; therefore model `0` bypasses the provider cap for that exact model only, while the global ceiling still applies. The selected route cap cannot raise the `maxConcurrent` plugin-instance global ceiling (default 4; upstream `defaultConcurrency` defaults to 5). Route admission uses the effective explicit category/role/fallback route and never guesses the parent’s inherited model; saturated one-shot launches fail immediately rather than queue. These caps are local to one plugin instance and do not cover continuable children or provide OMO TTL/activity behavior.

Category and role route `fallbackModels` accept at most three explicit `{provider, model, reasoningEffort?, maxTokens?}` candidates; a role route may set them only with an explicit paired `provider`/`model` pin. That role chain supersedes a selected category fallback chain; a role pin without its own chain continues to bypass the category chain. One-shot and continuable launches probe the selected primary route and its candidates serially with `llm.resolveCallConfig`; DSH applies role reasoning before candidate reasoning before selected-category reasoning. Role `maxTokens` overrides category `maxTokens` for the primary and fallback defaults; a selected fallback's own `maxTokens` overrides that shared value for that candidate only, while candidates that omit it inherit the route value. Continuable launches with role/category/parent `maxTokens`, or any effective fallback candidate `maxTokens`, reject before probing because RC2 does not preserve these ceilings across cold resume. This is a narrow spawn-time config/capability preflight: it does not query upstream `availableModels`, bind or reserve a later dispatch, or provide runtime retries. DSH `resolveCallConfig` validates exact settings but does not downgrade reasoning or cap `maxTokens` to a reported output limit; resolver-rejected configs fail closed, while some provider-specific limits may fail only at dispatch. Only reasoning and fallback-specific `maxTokens` are adapted; upstream sampling/provider-specific tuning is not included here ([model-resolution priority](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#L388-L403), [fallback settings](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#L1057-L1128)).

`enableGoalTools` defaults to `false` and requires DSH `goals.get/create/edit/pause/resume/complete`. It registers model-facing `dsh_omo_goal_get`, `dsh_omo_goal_create`, and `dsh_omo_goal_update` for the exact calling Agent only—there is no session-id override. Create accepts a non-empty objective up to 2,000 characters and an optional 1–1,000 round cap; it never clears an active, paused, or blocked Goal (the DSH service may replace a completed Goal). Update uses the current Goal revision and performs either a phase change (`active`, `paused`, or `complete`) or an objective/round-cap edit per call, because DSH exposes no transaction spanning both. The Goal summary exposes DSH activation and an optional bounded blocked reason; objective/reason text is sanitized and labeled as data, not higher-priority instructions. DSH owns persistence and continuation; these tools do not expose OMO token/time accounting or its project-file/TUI mirror. A cancellation before a mutation dispatch prevents it, but DSH Goal methods do not accept an AbortSignal, so cancellation after dispatch may not undo the write; the Tool then advises rereading the Goal before retrying. The Tools' explicit-intent wording is advisory, not a permission boundary; configure DSH Tool availability separately. Registration and `/omo status` do not call Goal business methods.

`enableTeamTools` defaults to `false`; opt in only when the optional DSH `agentTeams` service is present. It exposes eleven Host-backed `team_*` tools, including read-only `team_status` for the caller’s current Team only; that snapshot combines membership, up to 100 visible members, and up to 100 tasks, with explicit truncation flags and a 48,000-character aggregate cap. This is not exact upstream 12-tool parity: global Team listing, whole-Team create/delete/shutdown operations, including shutdown approval flows, worktrees, and tmux lifecycle remain unavailable. An `inactive` member is not reported as completed; task `writeScopes` remain advisory and DSH owns authorization and shared state. `enableSessionSearch` also defaults to `false` and requires DSH `sessionQuery.searchSessions` plus `observeSession`; the read-only tool derives the current Agent cwd from a projection-free observation and uses the DSH `sessionFilters: [{ kind: 'cwd', values: [...] }]` contract by default. `includeOtherProjects: true` deliberately removes that filter; the flag is model-supplied, not proof of user consent/authorization or an enforcement boundary; configure DSH tool permissions separately. It bounds results to 20 hits with 600-character snippets, forwards cancellation, returns a cursor for pagination, and does not request full log output or mutate sessions; a cold workspace observation or search indexing may still do full-session work internally. DSH owns search indexing/reconciliation, so completeness and backend availability are not guaranteed. `enableSessionRead` separately defaults to `false` and requires `sessionQuery.readEvent`, `observeSession`, and `filterSessions`. It validates the selected session against the current cwd before reading, defaults to zero neighboring events and allows at most four on either side (the Host may be stricter), and projects only bounded `text` blocks from direct user (`source.kind: 'user'`) and model assistant messages; synthetic user-role context, system/developer messages, reasoning, tool calls/results, and non-text blocks are omitted. It never calls `readSession` or resumes a session; output is bounded, but RC2 `readEvent` loads/snapshots the complete target log before slicing the requested window; a cold current-Agent workspace observation may also prepare that Agent's full log. Historical text is marked untrusted. `includeOtherProjects: true` is model-supplied, not proof of user consent or authorization; use it only after an explicit user request; it does not enforce consent, so configure DSH tool permissions separately. `enableSessionList` separately defaults to `false` and requires `sessionQuery.listSessions`, `filterSessions`, and `observeSession`. It uses the current Agent cwd by default, fails closed if cwd is unavailable, and accepts optional inclusive `fromDate`/`toDate` bounds; output is metadata-only by default and capped at 25 records. When `sessionQuery` exposes title-snapshot support, `includeTitles: true` adds sanitized untrusted titles for at most the first three displayed rows; each lookup may scan/reconstruct a complete target log and returns no event text. The Host materializes the complete logical corpus before filtering and provides no stable cursor, so a truncated result must be narrowed by workspace or date. Global scope uses the same model-supplied `includeOtherProjects: true` selector; set it only after an explicit user request, since the flag does not enforce consent/authorization. `/goal` is registered only when the native DSH Goals service is available; Goal persistence and continuation remain Host-owned. `/omo-models` is registered only when DSH LLM metadata is available; it lists up to 100 provider rows and resolves a named `provider/model` on demand (lookup scans at most 1,024 provider entries, then reports indeterminate). The command returns on caller cancellation or a 15-second timeout and passes that signal to the adapter; an adapter that ignores cancellation may continue its own work. This is diagnostic metadata, not model validation for child launch or a model request.

`enableLspTools` defaults to `false` and requires DSH `lsp.query`, `sessions.get`, and `fs.resolve`/`contains`/`processPath`. It exposes only the read-only definition and references aliases; the input is a relative path resolved against the invoking Agent session cwd and checked with canonical DSH filesystem containment before the query; this is not a race-free OS sandbox. Provider queries may inspect dependencies, and returned file URIs are untrusted metadata that may be outside the cwd; results are never followed or read by this adapter and do not grant access. Only `file:` result URIs are accepted; non-file schemes are rejected. The response caps locations at 50 and serialized data at 24,000 bytes and forwards cancellation. Upstream defaults `includeDeclaration` to true, but DSH exposes no such control: provider behavior is unverified, `false` cannot be honored and is rejected, and `true` is not guaranteed. The adapter uses the session cwd as `workspaceRoot`; whether providers expect that or the project root is unverified. The adapter assumes standard zero-based LSP positions when converting the upstream 1-based line; Inspect does not specify DSH indexing, and this conversion has not been tested with a live provider. Seven other upstream LSP tools remain missing: status, diagnostics, symbols, prepare_rename, rename, format, and install decisions. No live LSP provider was verified in the current target profile; service presence alone is not provider health. Configure DSH permissions separately for any later file access.\n\n`enableRootAgentsContext` defaults to `false`. When enabled, for each awaited DSH `agent/created` event (`startup`, `resume`, `clear`, or `compact`) while the hook is registered, it checks only that Agent session cwd's `AGENTS.md`; an eligible file is registered through that Agent's `systemPrompt.context()` scope before creation resolves and queued input proceeds. Missing, invalid, or otherwise rejected files produce no context. This is a DSH creation-time snapshot, not upstream OMO's post-`read` result injection; no read Tool result is modified. `enableWriteExistingFileGuard` defaults to `false`; enabling it requires DSH `agents.get`, `sessions.get`, `fs.resolve/contains/lstat/stat`, `tools.guard`, and Cordis lifecycle events. For case-insensitive Tool names `read`/`write` with a scalar `file_path` argument (a supplied schema must declare that property as a string), async `tools/pre-execute` preflight resolves canonical targets within the live Agent cwd and checks `lstat`/`stat` type plus matching nonempty version metadata (and size when available); a grant is recorded only when `tools/result` reports final `isError: false`. A final successful Tool result (`isError: false`) for a call named `read`, whose preflight identified an in-cwd regular file, grants exactly one same-live-Agent call named `write` to that opaque `targetKey`; concurrent writes reserve the grant once. This is name-based, so a custom Tool named `read` can mint a grant without proving it returned file contents. The grant pins the `targetKey` seen during preflight, not returned bytes/version; neither preflight+read nor preflight+write is atomic, so TOCTOU remains and this is not a permission boundary. Below the caps, a verified missing target or canonical outside-cwd target normally passes (including a symlink resolving outside); at preflight/record saturation it may be busy-denied before or after target classification. In-cwd final symlink/non-file targets and writes the adapter cannot classify fail closed. Every write pass-through/bypass is token-bound; the guard rechecks the exact path, schema compatibility, live Agent identity, and effective bypass status (not unrelated schema metadata or equivalent overwrite representations). Compatibility bypasses include a raw, case-sensitive slash-delimited `.omo` segment checked before normalization (so `src/.omo/../target` also bypasses), or `overwrite` set to boolean `true` or an exact case-insensitive string `"true"` (not trimmed); DSH Tool arguments are not stripped.

State is process-local: Agent grants/pending records reset on Agent creation/disposal, while shared token history, collision tombstones/overflow flags, and filesystem leases persist per FS provider across listener re-registration. Bounds are 256 Agent states, 256 grants per Agent, 64 primary pending records, a 64-token overflow ledger, 64 token-collision tombstones, 16,384 token-use history entries per FS provider, 64 simultaneous filesystem preflight leases, and a five-second waiter deadline. A backend that ignores `AbortSignal` may continue after its waiter returns, but its lease remains held until the underlying operation settles, bounding outstanding work to 64 per loaded module/FS provider. At lease saturation, reads skip filesystem preflight/pending grants only after attempting to claim a shared token-history entry; non-bypass writes that reach preflight fail busy, while explicit bypasses avoid FS leases but still need a token record. Full per-listener ledgers busy-deny unrecordable writes, with an extra unrecordable call latching unknown writes closed for that listener’s lifetime; this latch resets on disposal/replacement. A reused token is ambiguous: reads skip filesystem preflight/pending grants but still consume collision-history state and may be guard-denied if the token maps to a pending write; writes using a reused token are busy-denied. Collision-tombstone overflow denies all writes for that FS-provider/module state; token-history saturation skips read grants and denies writes until that FS provider's shared state is recreated (Agent create/dispose and listener re-registration do not clear it). DSH cannot make preflight+read or preflight+write atomic; the `targetKey` captures preflight identity, not returned bytes/version, so TOCTOU remains. This is a UX guard, not a permission boundary. This covers only calls named `write` (including custom Tools whose names match `write` case-insensitively); `edit`/`multiedit`, shell, and differently named custom/native writers are not covered.

`categoryRoutes` is an explicit dsh-omo user-configured (custom-only) primary-route table (up to 32 names, each at most 64 characters), not an upstream built-in category registry: a task may choose a configured `category`, or `roleRoutes.category` may set that role's default. Optional `description` is a single line capped at 512 UTF-8 bytes before trimming and appears as `name: description` entries in the one-shot/continuable task-tool description for enabled categories only; it is chooser metadata, not a child prompt or policy. Optional `disable` defaults to `false`; `disable: true` hides a configured route from tool choices and rejects explicit selection; role defaults to disabled routes fail configuration because they implicitly select that category; disabled entries still require provider/model. A category specifies a primary provider/model plus optional ordered `fallbackModels` (at most 3 explicit provider/model candidates, each optionally with `reasoningEffort`), category `reasoningEffort`, and dsh-omo's camelCase `maxTokens` field (not upstream's canonical `max_tokens`); dsh-omo validates it as a positive safe integer. Explicit role provider/model/reasoning/token settings take precedence, while the specialist role controls the prompt. Category `tools` accepts at most 64 boolean tool-name rules (each name at most 128 UTF-8 bytes) and rejects DSH's reserved `run_code` name; `true` entries map to DSH inherited-tool allow filters and `false` entries map to denies; category allowlists intersect role allowlists (an empty intersection filters all inherited tools), while category and role denies are unioned and removed from allowlists so denies win. Unlike upstream tool-set overrides, these monotonic DSH filters cannot grant tools that were not already inherited. As with role filters, DSH restricts inherited global/ancestor-scope tools only; child-scoped registrations and reserved PTC `run_code` may remain. One-shot filters require the selected DSH subagent provider's `toolFilter` capability; continuable tasks use DSH's scoped `tools.restrict`; this is not full upstream permission-policy parity. Category `promptAppend` remains task-message guidance, not a child system-prompt append. Category `maxTokens` maps to DSH `agentOptions.maxTokens`; the selected DSH subagent provider must advertise `SubagentCapabilities.agentOptions`. This is an output-token ceiling, not upstream `max_prompt_tokens` prompt-budget control, which is not implemented. No category/model fallback chain is implemented, and missing routes still inherit the parent/session model. Shared slash-task steering commands reject raw input longer than `maxTaskChars` before queueing it to the current agent.

`roleRoutes.promptAppend` and `categoryRoutes.promptAppend` are literal UTF-8 strings capped at 4,096 bytes each before trimming; whitespace-only values within the cap are ignored. dsh-omo rejects disallowed C0/C1 controls (tab and line breaks are allowed); `file://`, relative-path, home-path, and network references remain literal text; the adapter never resolves or reads them. For a selected category (explicit category before role default), its text appears in an “Additional category guidance” section, followed by any “Additional role guidance”; the two append payloads together are at most 8,192 bytes. This task-message composition is dsh-omo’s partial adapter for upstream category `prompt_append`, which appends to the system prompt; DSH exposes no per-child system-prompt append field here, so this does not change/replace the provider’s system prompt or grant an enforcement boundary. The chosen category-before-role section order is an adapter rule, not an upstream category-vs-agent system-prompt ordering guarantee.

`provider` and `model` must be set together when overriding the route; role `reasoningEffort` and positive-safe-integer `maxTokens` may be configured alone and ordinarily merge over the parent route. Category and role `maxTokens` pass through DSH `agentOptions`; `subagents.start` rejects options unsupported by the selected DSH subagent provider before delegation. If provider/model changes without an explicit `reasoningEffort`, inherited effort is cleared so the new model can use its default; do not generalize this to other omitted options. dsh-omo does not preflight ordinary category/role routes; when a selected category has non-empty `fallbackModels` and no explicit paired role provider/model pin applies, or when an explicit paired role route defines its own non-empty chain, it probes the primary then up to 3 candidates serially with DSH `llm.resolveCallConfig` before child start (a missing resolver or all rejected candidates fails the launch). A role chain supersedes the selected category chain; a role pin without its own chain still bypasses category fallback preflight. This checks exact call configuration, does not reserve or bind a later dispatch, and cannot guarantee the provider/model will work at request time; routes without configured chains retain no-preflight behavior. `/omo-models` reports advisory metadata and does not reserve or validate a future route. Role-route `allowTools` and `denyTools` reject the reserved DSH name `run_code` and are filters over tools inherited from the global and ancestor scopes; restrictions intersect, the child's own scoped registrations remain visible, and these are not hard permission boundaries. An explicit `allowTools: []` is preserved and hides all tools inherited from the global and ancestor scopes, but the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport may remain; it is not a hard deny-all. Empty `denyTools` is a no-op and is omitted. DSH exposes provider-owned retry policy metadata and an `agent/request-error` retry-action waterfall; the default-off profile-wide `runtimeFallback` table adds a bounded partial cross-model route switch as described below. `maxConcurrent` limits this plugin's active one-shot runs; DSH owns the separate continuable-session capacity. A parent's `maxTokens` can be inherited at child creation, but RC2 continuable descriptors/cold resume do not persist it; dsh-omo rejects continuable launch if a role/category route or parent has `maxTokens`. DSH workers inherit the parent workspace; this plugin does not promise a separate child `cwd`.

`runtimeFallback` is an explicit profile-wide route table, not a dsh-omo-child-only policy. Example:

```yaml
runtimeFallback:
  enabled: true
  retryOnStatuses: [429, 500, 502, 503, 504]
  chains:
    - provider: primary-provider
      model: primary-model
      fallbacks:
        - provider: approved-backup-provider
          model: backup-model
```

The config accepts at most 32 primary chains, each with 1–3 fallback routes. The controller matches the exact `provider`/`model` returned by DSH `agent/request`. In `agent/request-error`, it calls the waterfall's `next()` and preserves any delegated `{kind:'retry'}` action. It also consults the supplied `retryPolicy`: for `mode: 'normal'`, when the current `failure.code` is in `retryableCodes`, a remaining `maxRetries` budget blocks cross-route switching until the route-wide delegated retry count reaches `maxRetries` (counts are cumulative across failure codes for the same Agent/turn/step and reset on route change); `mode: 'always'` and unknown/malformed policies fail closed. If no policy is present, or no same-route retry remains (or the code is not retryable under the policy), it switches only when the numeric `failure.status` field is listed in `retryOnStatuses` (default `[429, 500, 502, 503, 504]`). If a normal policy advertises retries remaining but no delegated handler returns `{kind:'retry'}`, the adapter leaves the failure terminal rather than switching. Host Inspect contracts were checked, but no live AgentLoop/provider integration test was run. Candidate state is bounded and scoped to one Agent/turn/step; after a successful fallback response, DSH's logged provider/model may remain in later requests, and this adapter does not restore the primary. It has no proactive availability lookup, message-text error classifier, cooldown, timeout, or user-facing toast. Missing/unlisted statuses fail closed. A route switch can send the same prompt to another provider; configure only endpoints approved for that data. Route changes are logged without Agent/session ID, prompt, or error contents; DSH retains control of cancellation.

`disabledOmoRoles` defaults to `[]` and accepts exact dsh-omo built-in specialist names or names declared in `userAgents`; for example, `disabledOmoRoles: [architect, reviewer]`. It removes those roles from dsh-omo's one-shot/continuable tool choices and descriptions, orchestration guidance, and `/omo` help. Calls and `roleRoutes` entries targeting a disabled role fail closed, and at least one role must remain enabled. This local selector does not deregister Host/native/third-party agents and does not disable a same-named slash command (for example, `/architect`); it is not upstream per-agent `disable` behavior or OpenCode's global `disabled_agents` setting.

## DSH Host job monitoring

`enableJobTools` defaults to `false`. Set it to `true` only when the optional Host `jobController.list` and `jobController.follow` methods are available:

```yaml
enableJobTools: true
```

`dsh_omo_job_list` reads only the initial rows snapshot from the infinite stream, then closes it; output is capped at 50 jobs (25 by default) and 48,000 bytes after serialization/rendering. `dsh_omo_job_follow` derives its owner session from the current `exec.agent.id` (never a model-supplied `sessionId`), accepts an optional absolute byte offset `from`, and bounds each call to 8 seconds, 32 frames, 16 KiB of UTF-8 output, and 48,000 serialized/rendered bytes. It preserves absolute cursors and `lossy`/`gapBefore` indicators while projecting an explicit allowlist; `JobView.detail` and `output.spillPaths` are omitted. These model-facing tools do not expose or call `jobController.kill`; when `enableJobTools` is on and the Host method exists, only the separate human command `/omo-job-kill` calls it. Native DSH job-control tools are separate and remain governed by Host policy. Job kinds, labels, and log output are untrusted data. The model-facing tools provide DSH job monitoring only; they do not implement OMO `background_output`, `background_cancel`, or background subagent-result retrieval.

`enableToolResultPruning` defaults to `false` and requires at least one high-output adapter: `enableJobTools: true` or `enableAgentTerminalTools: true`. If the optional Host `toolResultPruner.pruneContent` method is present, it attaches DSH's final-content pruner only to successful `dsh_omo_job_follow`, `dsh_omo_terminal_read`, and `dsh_omo_terminal_send` results. Over-budget rendered text may be pruned while each structured `value` remains unchanged; errors and pruner failures keep original content. The Host pruner preserves rich-block order. If the service is absent or incomplete, no finalizer is registered. This is narrow DSH output pruning, not OMO Dynamic Context Pruning (duplicate-call recovery, protected tools, turn protection, and compaction-triggered behavior); it never invokes durable `pruneSession` rewrites. Enable it alongside job tools with:

```yaml
enableJobTools: true
enableToolResultPruning: true
```

## Optional models.dev capability snapshot

`enableModelCapabilitiesRefresh` defaults to `false` and requires DSH `web.fetch` plus a provider configured to return the complete catalog. Plugin setup never fetches: a user must explicitly run `/omo-models refresh`. The adapter requests only `https://models.dev/api.json`, requires a non-truncated 2xx text response with valid JSON, and forwards cancellation with a five-second deadline; a provider that ignores abort may continue I/O, but its late reply is discarded. The exact `WebFetchResult.url` comparison is only a post-fetch consistency check: the DSH contract does not say whether it is the requested or final URL, and the built-in HTTP provider allows up to five redirects by default, so this is not redirect/SSRF protection. Generic `WebFetchRequest` has no per-call size, MIME, or redirect controls. The inspected `include:web-fetch-http` schema defaults to `maxBodyChars: 100000`, `maxResponseBytes: 5000000`, and `maxRedirects: 5`; a current models.dev response exceeded the 100,000-character cap during this audit, so the default HTTP provider may return `truncated: true` and the plugin will reject it. Raise the selected HTTP provider's `maxBodyChars` above the complete catalog (256,000 is an audit-time starting point, not a future guarantee) and keep its pre-read `maxResponseBytes` cap at or below 8 MiB; configure custom providers with comparable pre-fetch bounds. The plugin cannot inspect or change provider config, and its own 8 MiB check happens only after the body is returned, so it does not limit network/memory use from an unbounded provider.

A successful refresh stores only an allowlisted capability projection for up to 512 providers and 100,000 scanned models in memory; it does not write a file or survive plugin restart. Use `/omo-models snapshot` for the count/time summary or `/omo-models snapshot <model-id>` for a single exact model entry. The snapshot is advisory metadata only: it does not establish provider availability, route compatibility, future call success, or a valid launch; it never makes an LLM request or affects routing. This is a bounded manual-refresh slice of OMO's [pinned refresh command](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/cli/refresh-model-capabilities.ts) and [snapshot parser](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/model-core/src/model-capabilities-snapshot.ts), not full cache/startup/compatibility parity.

```yaml
enableModelCapabilitiesRefresh: true
```

## Optional human-invoked DSH web search

`enableWebSearchCommand` defaults to `false`; when enabled it requires the optional DSH `web.search` service and adds `/omo web-search <query>`. Each explicit command invocation issues at most one search with `maxResults: 5` and a 2,000-character single-line query cap. A 20-second handler wait deadline forwards an abort request through a combined Command/lifecycle signal, but the provider may continue work if it ignores cancellation. To prevent repeated calls from accumulating such work, dsh-omo rejects new searches while a prior provider Promise remains unsettled; at most one request can remain in flight per registered command. Plugin setup and `/omo status` never search. The command is human-only: it does not register an Agent Tool or MCP server. Search text and URLs are rendered as bounded inert code spans and labeled untrusted; dsh-omo displays result URLs only and makes no follow-up DSH `web.fetch` call or URL navigation. DSH resolves its selected search provider at call time, so an absent, unavailable, or ambiguous provider returns a clear failure; dsh-omo does not inspect provider health or handle API keys. This subcommand shares the `/omo` registration, so `disabledOmoCommands: [omo]` disables it. It is a narrow DSH Service adapter, **not** OMO's [remote Exa/Tavily `websearch` MCP implementation](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/mcp/websearch.ts), full MCP loading, or an Agent-callable search tool.

```yaml
enableWebSearchCommand: true
```

## Read-only OMO plan checklist

`enablePlanChecklist` defaults to `false`. When enabled, `dsh_omo_plan_checklist` reads one safe basename under the current Agent session's `.omo/plans/` directory; it does not accept arbitrary paths. The adapter observes the current session by exact Agent id with `projectionMode: 'none'`, requires a matching session id and absolute cwd, resolves and contains every path in that workspace, rejects symlinked plan directories/files, caps the UTF-8 file at 128 KiB, and rechecks filesystem identity/version after reading. It returns top-level checkbox counts, at most one sanitized 256-byte next-open-item label, and fixed advisory warnings when structured TODO/Final Verification sections contain malformed rows or no valid tasks; it never returns the plan body. The parser follows the simple and structured TODO/Final Verification rules in the [pinned OMO checklist parser](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/boulder-state/src/plan-checklist.ts), while bounding input to 4,096 lines and 500 checklist entries. Plan text remains untrusted data. Warnings appear only when the Tool is explicitly invoked; it is not an automatic post-write hook and does not normalize duration-based Effort. The pinned OMO [plan-format-validator](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/hooks/plan-format-validator/hook.ts) runs after Write/Edit and may perform a second Effort-normalization write; this DSH adaptation intentionally does not. This read-only checklist view does not edit plans, execute dependencies, launch workpool workers, reconcile stale work, or resume tasks, and it is not full DAG parity.

```yaml
enablePlanChecklist: true
```

## Agent-owned DSH PTY tools

`enableAgentTerminalTools` defaults to `false`. When explicitly enabled, dsh-omo calls the optional Host `terminals.listBackends()` during setup and registers five core tools only if a backend and the required Host methods are available: owner-scoped list, spawn, read, send, and close. If `terminals.signal` is available, it also registers `dsh_omo_terminal_interrupt`, which sends only `SIGINT` through the Host backend to an owned session; the backend chooses its target process group. This is a Ctrl+C-style interrupt, not a guarantee of tmux `send-keys` semantics or session close; no arbitrary signal is model-selectable. Registration is at plugin/profile scope, so every Agent that receives this plugin's tools can see them; each call still passes its exact `exec.agent` object to the Host, which fences access to that caller's sessions. The tool schemas expose no caller-supplied owner id or cwd; session-specific operations accept only a PTY session id and derive ownership from exact `exec.agent`. Spawn forwards only backend type and optional display name; extra input fields are not forwarded. List is never global. Spawn uses the backend's default cwd and accepts only a registered backend type plus optional display name. Reads are capped at 200 lines and 16 KiB of text; sends are capped at 4 KiB and wait at most 12 seconds, with output capped at 16 KiB. Cancellation requests Host operation cancellation and drains for up to one second; if the Host operation still has not settled, the tool reports that the PTY may remain busy. After a cancelled or timed-out interrupt, delivery may already have occurred or may still occur; the Host signal cannot be retracted. Terminal text and backend MOTDs are untrusted.

This grants an enabled Agent the ability to send interactive input that may execute commands. dsh-omo adds no sandbox or approval layer; execution/approval semantics belong to the configured Host backend, which must be trusted and reviewed before opting in. This is an Agent-owned PTY adapter, not tmux panes/layouts, worktree isolation, or a claim of full OMO terminal parity. No live terminal backend was verified in this session.

```yaml
enableAgentTerminalTools: true
```

To opt into the Host output pruner for PTY reads and sends as well, enable both flags (the optional pruner Service must also be present):

```yaml
enableAgentTerminalTools: true
enableToolResultPruning: true
```

## Project skills

The DSH skill registry now discovers project-local skills relative to each skill lookup's `cwd`. Defaults are `.opencode/skills` and `.claude/skills`; each root accepts `<name>/SKILL.md` bundles and top-level `<name>.md` files. Skills need YAML `name` and `description`; optional `whenToUse` becomes top-level routing guidance, while `disable-model-invocation` and `user-invocable` map to DSH invocation flags. Other JSON-compatible frontmatter (including upstream `agent`, `model`, `tools`, or `mcp` fields) is preserved as metadata up to 12 levels deep; YAML aliases are rejected. These fields are not enforced: dsh-omo does not execute embedded MCP or bind the skill to an agent, toolset, or model.

```yaml
- id: dsh-omo
  config:
    projectSkillDirs: [.opencode/skills, .claude/skills]
    enabledProjectSkills: [incident-response]
    disabledProjectSkills: [retired-project-skill]
    disabledOmoBundledSkills: [omo-code-review]
    disabledSkills: [legacy-skill]
```

`enabledProjectSkills` is an optional exact-name allowlist of up to 256 distinct valid names for dsh-omo's project-skill provider: when omitted or set to `null`, all discovered project skills are visible; `[]` exposes none. It is a narrow local adapter for upstream [`skills.enable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills), which filters config-sourced skills; the local field filters only project-provider candidates; bundled, native, and other-provider registrations are not filtered by it, so a same-name entry may remain visible. `disabledProjectSkills` is an optional denylist of up to 256 distinct valid names for that same provider, adapting upstream [`skills.disable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills); if both project lists contain a name, the denylist wins. Excluded project entries can reveal lower-priority same-name skills from another provider. `disabledOmoBundledSkills` hides exact dsh-omo bundled-skill names only, adapting upstream [`disabled_skills`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills) narrowly; names outside this package's bundled set are rejected, and DSH-native/other-provider registrations are not filtered; a same-name entry may remain visible. If a name appears in both this field and `disabledSkills`, hiding wins. Unlike these visibility filters, `disabledSkills` keeps matching bundled/project entries visible while disabling model and user invocation. The provider still scans and parses project skill files to read their frontmatter names, so these filters are not a scan-cost reduction or filesystem security boundary. When a project skill is both enabled and listed in `disabledSkills`, it remains visible but non-invocable.

`disabledSkills` sets model and user invocation to false only on dsh-omo's bundled/project entries; it does not alter another provider's flags. Disabled entries remain registered, so a lower-priority same-name external skill may still be shadowed by the DSH registry's single-winner resolution. `projectSkillDirs` must be relative to the lookup cwd and cannot contain `..`; only canonical targets under that cwd are accepted, and symlinks resolving outside the configured root are skipped. Reads go through DSH `ctx.fs.readBytes` with a 256 KiB per-file cap; each catalog scan also caps processing at 512 directory entries, 256 accepted skills, and 8 MiB of skill text. `ctx.fs.listDir` returns a complete entry array before the plugin applies its scan cap, so extremely large directories may still cost backend enumeration memory. Reads do not pass through tool-level permission/approval prompts or the mutation sandbox. Reads compare DSH file versions and revalidate the final path after reading, but RC2 exposes no atomic no-follow open; a hostile swap-and-restore race is still possible, so this is not an OS read sandbox or race-free directory-handle boundary. Treat repository-provided skill text as untrusted instructions. Within dsh-omo roots, earlier configured paths rank first; all up to 16 configured roots rank ahead of dsh-omo runtime/bundled skills but remain below higher-priority DSH project sources. Filesystem watchers monitor symlink parents and canonical skill paths when available; if watch setup fails the catalog remains uncached, and `/omo-skills-refresh` can request another scan. User-global and remote skill sources, full OMO priority/config rules, intent activation, and skill-embedded MCP lifecycle remain unsupported.

## Try it

In an interactive DSH session:

```text
/omo
/goal status
/goal Keep improving this project
/stop-continuation
/ulw Split the migration into independent discovery and test tasks, integrate the results, and run the checks.
/ulw-execute migration-plan
/architect Should this service be event-driven or request-driven?
/review Inspect the current diff for correctness and security issues.
/handoff
/refactor src/feature.ts --scope=file
/refactor the auth and session modules --scope=module --strategy=safe
/remove-ai-slops src/feature.ts
/omo status
/omo-models
/omo-models <provider>/<model>
/omo-models refresh
/omo-models snapshot
/omo-models snapshot <model-id>
/omo-tasks
/omo-interrupt <child-id>
/omo-job-kill <jobId>
/omo-skills-refresh
```

`/goal` appears only when its native DSH service is mounted. `/omo-models` appears when the native DSH LLM service is mounted or when `enableModelCapabilitiesRefresh: true` is configured with DSH `web.fetch` and a provider that can return the full catalog untruncated; models.dev subcommands are unavailable unless explicitly enabled. `session_search` requires `enableSessionSearch: true` and DSH `sessionQuery.searchSessions` plus `observeSession`; `session_read` separately requires `enableSessionRead: true` and `sessionQuery.readEvent`, `observeSession`, and `filterSessions`. Model-facing `team_*` tools require `enableTeamTools: true` and the optional DSH `agentTeams` service. `/remove-ai-slops` is user-requested steering only, not an automatic diff hook. `/handoff` queues a prompt asking the current agent for a copyable summary in this conversation; completeness is not guaranteed, and the user must copy the reply manually. It cannot create a new session or durable handoff file. When registered, `/stop-continuation` clears only the current native DSH Goal using its current revision (the Host retains a tombstone/history); it does not stop OMO todo continuation, clear OMO boulder state, or interrupt DSH continuable children. If enabled, `/goal pause` preserves a Goal; when enabled, `/omo-interrupt` can request interruption of a supported direct child.

`disabledOmoCommands` defaults to `[]` and accepts these dsh-omo-owned command names (without `/`): `goal`, `stop-continuation`, `omo-models`, `ulw`, `ultrawork`, `ulw-execute`, `architect`, `handoff`, `refactor`, `remove-ai-slops`, `omo-tasks`, `omo-job-kill`, `omo-interrupt`, `omo-skills-refresh`, and `omo`. For example:

```yaml
disabledOmoCommands: [refactor, omo-models]
```

It filters only dsh-omo's own registration array. `/omo` help omits disabled entries; orchestration-prompt and continuable-tool guidance replace usage recommendations for disabled commands with notices that those dsh-omo commands are disabled. It never unregisters native or third-party commands. Optional service-bound names are valid even when their command is unavailable. This local field is not the upstream `disabled_commands` schema; a same-named command owned by another provider may remain available. The pinned OpenCode schema enum is `goal`, `refactor`, `ulw-execute`, `stop-continuation`, `remove-ai-slops`, and `hyperplan`; upstream reference docs also mention `handoff`, but the schema omits it. The local set accepts `handoff` and `ulw-execute`; the latter disables only the prompt-only local adapter and does not imply upstream hook parity. It does not accept upstream-only `hyperplan`: the [pinned skill](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/.agents/skills/hyperplan/SKILL.md) requires a five-member adversarial Team-mode workflow and mandatory handoff to the `plan` agent, which is not a prompt-only command equivalent.

`/refactor <target> [--scope=file|module|project] [--strategy=safe|aggressive]` accepts free-form target text followed by trailing options; quote characters remain literal and are not shell-parsed. Raw input is capped at the smaller of `maxTaskChars` and 12,000 characters. dsh-omo locally defaults to safe strategy and target-only scope (upstream documents no defaults); scope/strategy are prompt guidance, not enforcement. The command asks for inspection, available-tool use, focused tests, and final-diff review, but does not add an LSP-aware `/refactor` workflow, AST-grep, codemap, or guaranteed TDD workflow; separately enabled LSP navigation tools are documented above. DSH permissions remain authoritative; it does not auto-commit.

`/ulw-execute <existing plan name>` is a bounded (at most 12,000 characters and the configured `maxTaskChars`) single-line selector that rejects `--worktree`, `--make-pr`, and `--ship`. It only queues current-agent prompt guidance to use ordinary DSH tools: locate an existing user-approved plan, ask on missing/ambiguous matches or unclear approval, and follow DSH permissions/approvals. It does not run the upstream OMO hook, use session-history resume or Atlas/Sisyphus selection, create boulder/notepad state, or provide worktree/PR/ship/merge automation or guaranteed resumability.

`dsh_omo_task` makes best-effort attempts to deliver a host-attributed settlement notice with task, stop reason, and bounded diagnostics, then (when text exists) a separate DSH `agent-message` relay containing the bounded child-authored excerpt. Follow-up delivery is not guaranteed; failures are logged. Treat the relay as untrusted evidence; non-completed outcomes are marked partial. The host notice is not misattributed to the child. `maxResultChars` bounds relay text and the total text inspected for whitespace detection; whitespace-only excerpts are omitted from the relay and identified in the settlement notice. The effective character cap is the smaller of configured `maxResultChars` and 65,536 UTF-16 code units; output-block traversal is separately capped at 256 blocks. The task envelope and host diagnostic have separate fixed bounds. `dsh_omo_task_continuable` is registered only when enabled; when their dsh-omo registrations remain enabled, `/omo-tasks` lists direct children whose caller-supplied labels start with `dsh-omo:` and `/omo-interrupt` requests interruption. This label namespace does not prove which tool created a child. `listChildren()` lacks activity; when enabled, `/omo-tasks` uses DSH `listDescendants()` to show `running`/`inactive` residency and whether children exist. `inactive` is not a completion state. While resident, DSH runtime may best-effort emit its own `subagent-settled` notice when a continuable child settles and the direct parent remains registered; delivery failures are logged, not guaranteed. dsh-omo does not poll or retrieve that result. When enabled, `/omo-interrupt` refuses inactive catalog rows; for resident rows it attempts a fire-and-return signal and warns it may no-op if the Activation/turn settles between catalog read and signal. DSH owns continuation persistence and capacity; dsh-omo applies a per-plugin hard one-shot `maxConcurrent` ceiling plus optional `providerConcurrency`/`modelConcurrency` subcaps for explicit LLM routes (model overrides provider; `0` removes only that route-specific cap). Saturated calls fail fast rather than queue, inherited parent routes are not guessed, and no host-wide/shared quota is claimed; continuable capacity remains DSH-owned.

When enabled, human-only `/omo-job-kill <jobId>` is registered only if `enableJobTools: true` and Host `jobController.kill` exists. It derives `sessionId` from the exact invoking Agent and never accepts a session ID; DSH's visible job set includes current-session and unowned jobs, so verify the requested ID. The Host outcome `requested` is admission only, not terminal completion. This cancels a visible DSH job only—not OMO `background_cancel`, continuable-child interruption, or result retrieval.

## Parity ledger

This project is staged. The following are working or deferred, not claims that the upstream product has been fully recreated.

| Capability area | Status in this milestone |
| --- | --- |
| One-shot and opt-in continuable specialist tasks | DSH-managed; direct children expose running/inactive residency, but no completion status, plugin-origin proof, result polling, or TTL |
| Ultrawork workflow, packaged skills, and slash commands | Prompt-level task steering, twelve bundled skills, `/remove-ai-slops` steering, optional native `/goal` and `/omo-models`, and partial cwd-relative project skill sources; hooks, plan execution, and recovery remain missing |
| Per-role model selection | Static provider/model/reasoning/token overrides plus user-defined category routes and bounded category/explicit-pair role `fallbackModels` preflight (role chains supersede category chains); DSH clears inherited reasoning on route change unless specified; upstream model profiles, availability-aware resolution, global/provider fallback policy, catalog normalization, and full role-scoped fallback chains/tuning remain missing |
| Model capability diagnostics | Optional `/omo-models` lists DSH provider IDs and inspects exact live DSH metadata; default-off `enableModelCapabilitiesRefresh` adds explicit fixed-source models.dev refresh and an in-memory advisory snapshot (provider limits must allow a complete response), but no startup refresh, durable cache, compatibility heuristics, synthetic LLM calls, or route gate. The opt-in category/role `llm.resolveCallConfig` fallback preflights are not later request guarantees |
| Prompt-cache retention | OMO Native's documented Anthropic retention/idle keep-alive is not adapted by dsh-omo. DSH's optional `llm-pi-ai` Config schema has per-model `cacheRetention`, but no generic LLM `keepAlive` scheduler or safe provider-agnostic warm-up; schema presence does not prove it is active. No synthetic warm-up calls are issued; provider-internal caching may exist |
| Retry/fallback | Default-off profile-wide `runtimeFallback` supports up to 32 exact primary provider/model routes with 1–3 explicit fallbacks each and selected `failure.status` codes only when the delegated waterfall is terminal and either `retryPolicy` is absent or a normal policy's current code is nonretryable / its route-wide delegated retry count has reached `maxRetries`; if a normal budget remains, or policy is `always`/unknown/malformed, it fails closed. | Permissions/tool scoping | DSH remains authoritative; allowTools/denyTools filter tools inherited from global and ancestor scopes; the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport remain, so this is not a hard boundary |
