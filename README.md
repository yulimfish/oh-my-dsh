# dsh-omo — Oh My DSH-style orchestration

An independent DeepSeek Harness plugin that brings an Oh My OpenCode-inspired specialist workflow to DSH. It is being implemented against the installed DSH `0.2.1-rc.3` APIs; it does **not** install or depend on the incompatible `dsh-autopilot` alpha. No Oh My OpenCode source code is copied. This is an early-stage compatibility layer, not a claim of complete 1:1 feature parity or affiliation with either project.

## Ready-to-use candidate

The current candidate is **0.1.14**. See [release readiness and conservative setup](docs/release-readiness.md) before activation. It provides a tested DSH-native workflow, **not complete upstream parity**; the guide separates supported paths, opt-ins, and Host limitations.

## First milestone

- Adds `dsh_omo_task`, a bounded one-shot launcher with automatic parent follow-up and optional per-call `load_skills` (up to four exact model-invocable names from the parent CWD/default catalog; bodies are capped at 8 KiB each and 24 KiB total, then appended as untrusted guidance). This is a DSH-specific adaptation rather than a native DSH task field. Also adds an opt-in `dsh_omo_task_continuable` tool backed by DSH durable child sessions. Specialist roles include `explore`, `librarian`, `architect`, `plan-consultant`, `plan-reviewer`, `ultrabrain`, `quick`, `visual`, `reviewer`, `test`, and `security`. The default-off `enableCallOmoAgentTool` exposes a separate Explore/Librarian-only one-shot delegation Tool without upstream session-continuation or background-mode semantics.
- Default-off `enableCategorySkillReminder` can append one static category-skill hint after three accepted direct `read`/`edit`/`write`/`bash`/`grep`/`glob` calls by an exact live root Agent, only when configured skill defaults and a visible category-aware one-shot Tool are present. Any direct call to `dsh_omo_task`, `dsh_omo_call_agent`, `dsh_omo_task_continuable`, or `dsh_omo_task_followup` suppresses it; nested/child Agents do not receive it. The hint shows at most four categories from the first 32 routes, capped at 2 KiB, and never queries or loads skills; launch-time validation remains authoritative. This is process-local and DSH-specific: it cannot identify OMO's Sisyphus roles, is not replay-stable, and another `tools/post-execute` listener may drop the added context after its state commits.
- Adds separately default-off `enableTaskResultTool` (`dsh_omo_task_list`, `dsh_omo_task_result`) to list up to 32 retained one-shot child IDs/status pairs for the exact Agent (local-only by default) and read bounded output only for a tracked one-shot child and exact Agent/session (in-memory by default; terminal-only persistence is optional). Explicit `includeResidency: true` performs a cancellable, 2-second Host descendant lookup only when local entries are running, projects at most 1,024 returned rows onto tracked direct children (Host traversal may be larger), and adds activity as a residency-only hint; it never changes local terminal status, and absent/incomplete Host visibility is not completion. Running entries remain while active, terminal results expire 30 minutes after settlement, reads do not extend TTL, and records are lost on unload/restart by default. The optional `enableTaskResultPersistence` stores only terminal result snapshots for the same session ID for up to 30 minutes; it never stores or restores running work, does not guarantee backend durability, and may persist sensitive child excerpts. `enableTaskWaitTool` (`dsh_omo_task_wait`) is also default-off, requires result tracking, and waits only on an active one-shot child tracked to the exact Agent (or returns that Agent's already-cached result; 8-second default, 30-second maximum, 32 concurrent waiters total and four per Agent). Timeout or caller cancellation ends only the wait, not the child; the existing result cache may retain a later settlement. `enableTaskCancelTool` exposes `dsh_omo_task_cancel` for exact-Agent tracked active one-shot children; DSH interruption is fire-and-return, so acceptance does not prove the child stopped. These tools do not address arbitrary sessions, continuable children, or generic jobs.
- Adds separately default-off `enablePersistentMemoryTools` (`dsh_omo_persistent_memory`) for explicit search/read/write/delete of small notes in DSH `storageDomain` KV. Records are scoped by SHA-256 of the exact absolute Session cwd (not canonicalized), capped at 64 cwd keys, 32 notes per key, 256-byte titles, and 4-KiB content. Search returns up to five bounded excerpts. A separate 36,736-character serialized-JSON response budget accounts conservatively for escaping; it does not increase note limits. Write responses are checked before storage mutation, preventing valid escaping-heavy notes from committing and then failing the old smaller output guard. At most 64 memory operations may be queued or executing per Tool instance; excess calls fail busy before joining the queue, without silently dropping an accepted write. Action parameters are validated and copied before admission or storage reads, so invalid requests fail fast and queued operations do not reuse mutable caller input. State-dependent checks remain serialized. Slots return only when the serialized operation settles, including errors. Restart persistence depends on the configured Host backend; a Tool call waiting for storage readiness is capped at 15 seconds, queued writes/deletes check cancellation before mutation, and an already-started Host KV operation cannot be canceled; `storageDomain.open` itself has no cancellation signal, so unload does not wait for a pending open and closes any late handle. Host `storageDomain.open` validates/loads existing rows before the adapter enforces its 64-key cap, so that cap does not bound Host-side loading. Notes are untrusted data and are never auto-injected into prompts; this is not OMO Markdown/Git/remote-sync/dream memory.
- Adds built-in specialist prompts, opt-in per-role model routes, reasoning effort and token ceilings, and bounded `promptAppend` guidance in delegated task messages, with a default-off current-session-CWD file-reference subset for selected configured appends (task-message guidance only, not OMO system-prompt parity). The current Host `startActivation` API has no per-request persona or `toolFilter`; prompt-based custom personas fail closed, while custom roles may select an existing `agentPreset` only when the provider advertises that capability. A selected role/category tool filter still rejects the one-shot launch rather than changing child permissions. Legacy `start` providers may support those options.
- Adds thirteen packaged skill names: four `omo-*` skills plus `debugging`, `frontend`, `git-master`, `init-deep`, `remove-ai-slops`, `review-work`, `security-research`, `visual-qa`, and the upstream-named `security-review` alias of `security-research`. The legacy `omo-security-review` remains a separate checklist. These are bounded guides, not upstream lifecycle integrations or automatic scanners. Disabling/hiding is per DSH skill name: configure both `security-review` and `security-research` if neither should be invocable; the pinned upstream runtime selector also checks these two names independently. `disabledSkills` accepts ASCII case variants and normalizes them to lowercase; other skill filters remain exact, and upstream's alternative skill-config syntax is not replicated.
- Adds a cwd-aware provider for project `.opencode/skills`, `.claude/skills`, and `.agents/skills` files through DSH skill/filesystem services.
- Adds a default-off constrained `.claude/agents/*.md` source adapter; enabling it fails closed on the current Host `startActivation` API, which has no per-request persona or `toolFilter`. Legacy `start` providers may launch these untrusted project personas; there is no global discovery or permission parity.

When `enableProjectCommands` is on, `/omo-project-commands-refresh` explicitly rescans project and configured user command files for the current Agent after edits.

Task commands still report DSH residency/interrupt attempts, not plugin origin or guaranteed completion.

It is prompt-only for plan selection/execution: no OMO hook/session-history resume, Atlas/Sisyphus selection, boulder/notepad state, PR, shipping, or merge lifecycle. An explicit trailing `--worktree` requests a fresh DSH-managed local Git worktree before the plan task is queued; the queued prompt receives bounded JSON-quoted path/branch/base-commit metadata (with per-field and serialized-output caps). The Host exposes worktree creation but no removal method, so the command leaves the worktree retained by default and directs the Agent not to attempt cleanup; Host failures may leave partial artifacts. This is not OMO worktree lifecycle parity. `--make-pr` and `--ship` remain rejected.

This is prompt guidance, not a read-only gate: the current Agent and delegated specialists may still use write/execute Tools allowed by their provider/AgentPreset and DSH policies. The command itself only queues a prompt; it does not directly edit or execute the plan, create/join a Team, or reproduce upstream OMO's seven-phase Team workflow or mandatory plan-agent handoff.

- Adds a default-off `enableTeamModeContext` that gives exact live Team Leads and teammates fixed, role-aware startup guidance; it contains no Team IDs, roster, task, or mailbox data and grants no permissions.
- Adds a separate default-off `enableTeamStatusContext` that injects an exact live Team Agent's count-only Team snapshot into scoped prompt context; it is independent of Team Tools, read-only/advisory, bounded to 100 rows per list at the adapter, and grants no permissions.
- Adds a default-off `enableTeamTaskUseReminder` for exact Team Agents whose IDs fit explicit code-unit bounds; every ten accepted non-task Tool results (including errors) appends a fixed advisory context, with bounded per-Agent state and no task creation or mutation.
- Adds default-off model-facing `dsh_omo_goal_get`, `dsh_omo_goal_create`, and `dsh_omo_goal_update` tools via `enableGoalTools`; operations target only the exact calling Agent and use DSH revision-fenced Goal state; create never clears a Goal or replaces a non-complete current Goal.
- Adds default-off `enableRepeatedCallAdvisory` for a Cline/Goose-inspired soft loop warning. It hashes bounded, recursively key-sorted Tool arguments at pre-execution, counts accepted top-level completions (including Tool errors) in completion order, and adds one advisory at the third consecutive identical call for the exact live Agent. Unsupported/cyclic/over-budget input and missing pre/post identity reset the run rather than creating truncation collisions; parallel calls, cancellation, same-ID replacement, and pending/state caps are handled. It never denies a call, echoes arguments, persists signatures, or treats repetition as proof of no progress.
- Adds default-off `enableProgressContext` for Cline/Goose-style progress continuity without a second task store. Each exact live Agent scope incrementally folds its DSH session log and exposes only the latest successful `todo_write` snapshot as bounded prompt context. Pending or failed writes do not replace the current list, an accepted empty list clears it, skipped/malformed event windows emit no stale list, and compacted/replaced Sessions are re-read. Todo content is sanitized and JSON-quoted; the adapter never treats checked items as proof of user-task completion.
- Adds default-off `enableGoalCompletionReview` as a Goose-inspired one-shot end-of-turn check. At the awaited `agent/turn-stopping` boundary it re-reads the exact live Agent's active native Goal and calls `agent.steer()` at most once per Goal ID/revision, asking the model to continue unfinished work, avoid repeated exploration, or finish concisely. State is bounded and isolated across same-ID replacements; steer/Goal-service failures do not force a retry loop, and the review never changes Goal lifecycle state.
- Adds default-off `/omo verify` via `enableVerifyCommand`. It reads the current workspace's bounded `package.json` scripts and the current session's bash call/result evidence, then distinguishes suggested checks, completed-without-Tool-error results, and failures. It never executes scripts, edits files, changes Goal state, or treats a bash completion as proof of passing tests. Missing evidence is explicitly unverified rather than failed, and other sessions/CI are outside its evidence scope.
- Adds a separate default-off `enableGoalUseReminder` DSH-specific advisory when Goal Tools, `agents.get`, and `agentTeams.tryMembership` are available; it skips Team Agents, emits at most three reminders per Agent, and is not generic task CRUD or OMO reminder parity.
- Adds default-off `enableAgentUsageReminder` as a bounded root-Agent partial: exact visible search/fetch Tool calls append up to three fixed reminders only when at least one DSH delegation Tool is visible; any exact DSH task Tool call suppresses later reminders. State is process-local and resets when DSH disposes/recreates the Agent (including compaction when it creates a new Agent scope); the feature cannot identify OMO orchestrator names or persist per-session state.
- Adds default-off `enableSearchToolResultPruning` as a name-routed content-only partial: direct exact `grep`/`glob`/`web_fetch` calls are eligible by default, with up to 32 additional exact Tool names permitted only by explicit configuration; successful downstream content-only accept decisions and caller-visible Tool definitions without content projection/finalizer callbacks are still required. It uses the Host character-budget pruner, preserves downstream decision fields, skips structured-value outcomes, and does not prune `web.fetch` or call `pruneSession`; it cannot prove native Tool provenance or OMO token/context-budget parity.
- Adds default-off `enableGeneralToolResultPruning` as a broad but opt-in content-only partial: it prunes eligible top-level successful Tool decisions for the exact caller-visible definition when no Tool-owned content projection/finalizer applies, while skipping `run_code`, nested, blocked, value-returning, errored, and cancelled outcomes. It uses the Host character budget and may hide useful output; it is not OMO's token-estimated, remaining-context-aware truncation.
- Adds default-off `dsh_omo_image_query` as a DSH-specific direct vision query: it accepts legacy `imageIndex` or up to four unique `imageIndices` from the latest actual user message and can compare those images in one request to the explicitly configured image-capable provider/model. Each selected image is capped at 8 MiB/32 megapixels and the batch at 16 MiB/64 megapixels combined, with bounded goal/output and an empty Tool list; unsupported multi-image routes fail closed without fallback. It accepts no filesystem paths, does no history search, and saves no session image. It is not OMO `look_at`: no Multimodal-Looker child session, and the Host LLM adapter may read/cache a provider-specific image projection when the Tool is invoked.
- Adds user-configured category-to-primary-route delegation via `categoryRoutes` and optional `category` arguments; default-off `enableRoleCategoryRouteAliases` maps up to 32 exact provider/model pairs only in configured role/category primary and fallback routes before selection, preflight, and capacity admission, with optional reasoningEffort defaults that yield to explicit route settings (not global model aliases); categories may specify up to three ordered explicit `fallbackModels`, which use a bounded DSH spawn-time capability preflight (not upstream model resolution or runtime fallback); the default-off `enablePinnedRoutePreflight` optionally validates a selected explicit role/category primary route without an applicable fallback chain; default-off `enableThinkModeReasoning` maps bounded think cues to `reasoningEffort: 'high'` only after same-route resolution accepts it (not a dispatch guarantee); categories also support reasoning, an optional `maxTokens` ceiling, disabled-route filtering, task-tool descriptions, bounded task-message `promptAppend` (not a system prompt), and optional one-shot skill defaults for selected categories (not preset-scoped or continuable). Category `tools` maps are retained for legacy launch providers; on current Host `startActivation`, selecting a filtered route fails closed because the request cannot enforce `toolFilter`. Categories are not personas or a built-in upstream registry.
- Adds default-off `enableAgentPresetPreflight` to resolve only a selected configured `agentPreset` through DSH `agentPresets.resolve` immediately before child activation; missing, mismatched, or activation-failed presets fail before spawn (bounded, caller-cancellable lookup; not a revision pin).
- Adds a default-off, profile-wide `runtimeFallback` controller with up to 32 exact primary provider/model chains, each containing 1–3 explicit fallback routes. It preserves delegated `{kind:'retry'}` actions and consults the supplied `retryPolicy`; it will not cross-route while a normal policy still has retry budget beyond observed delegated same-route retry actions (counted cumulatively across error codes for that route/Agent step), and `always`/unknown/malformed policies fail closed. When no same-route retry remains (or the error is not retryable under that policy), it switches only for selected `failure.status` HTTP values. It does not discover provider/model availability. Its bounded `cooldownSeconds` (default 60, maximum 86,400; zero disables) records a route that failed when a different fallback was selected, per exact Agent; later fallback choices skip that route until its cooldown expires. State is capped at 256 Agents and 128 routes per Agent, expires lazily on the next fallback decision, and clears on Agent disposal/plugin unload. This is a partial cooldown subset, not OMO's timeout, toast, or automatic primary-restoration behavior. A successful provider switch can affect later Agent requests; configure only providers approved for the prompt data.
- Adds on-demand `/omo-models` diagnostics over registered DSH providers and exact model metadata, plus a default-off, explicit-user-invoked models.dev snapshot refresh that stays in memory and advisory; no startup refresh, durable cache, synthetic LLM call, or route gate.
- Adds two separately default-off DSH web-search surfaces: human-only `/omo web-search <query>` and model-callable `dsh_omo_web_search`, each backed by one bounded DSH `web.search` request (maximum five results). The Tool is not OMO's remote MCP adapter, and neither surface auto-fetches returned URLs.

Separately, explicit `/omo status route role:<name>` or `/omo status route category:<name>` preflights exactly one selected pinned primary through `llm.resolveCallConfig` with a five-second caller-cancellable deadline; role pins reuse selected category reasoning/token controls, no fallbacks are scanned, and unknown, disabled, or unpinned routes are not checked. It does not stream a model call, create a child, or prove credentials, endpoint/model health, or a later dispatch; adapter lookup may continue if it ignores cancellation.

This is DSH-native current-session event search, not OMO session/task-manager parity; no complete-log work bound is claimed, and backend-owned search/indexing may still involve full-session work.

- Adds optional DSH Host job monitoring (`enableJobTools: true`) through `dsh_omo_job_list` and `dsh_omo_job_follow`. It defaults off, derives the service owner from the current Agent, caps streams/output, drops `JobView.detail` and `output.spillPaths`, and exposes no model-facing kill Tool. With the same opt-in and a Host `jobController.kill` method, the separate human-only `/omo-job-kill` command can request cancellation. This does not implement OMO `background_output`, `background_cancel`, or subagent-result retrieval.
- Adds `/remove-ai-slops` steering that reuses the bundled workflow skill; it is not an automatic diff hook or enforcement boundary.
- Adds project skills as a source in the DSH skill registry. Provider reads use `ctx.fs`, cwd containment, file-version checks, and a post-read path revalidation—not model-facing filesystem tools or their approval prompts; DSH remains authoritative for normal tool mutations, shell/network access, and approvals.
- Adds opt-in `enableProjectCommands` for bounded `.opencode/commands/*.md`, `.opencode/command/*.md`, and `.claude/commands/*.md` files. Commands are discovered for each Agent CWD, registered only in that Agent's DSH command scope, and run only after explicit human invocation; the limited parser accepts plain Markdown or optional YAML metadata with `description` and bounded display-only `argument-hint` from either source, plus literal `$ARGUMENTS`. Missing descriptions use the safe display fallback `Project command /<name>`. Each rendered prompt wraps the trimmed instruction and always appends raw invocation text in a `<user-request>` section, even when the body has no placeholder; when the body does contain `$ARGUMENTS`, the input appears there too, matching upstream template framing. Plural OpenCode commands take priority over singular OpenCode commands, then Claude commands. Shell substitutions, recursive references, automatic chat rewriting, and source-specific Claude/OpenCode command semantics are not implemented. A separate administrator-only `commandRoutes` mapping can route selected discovered commands to an enabled existing specialist role, using the existing one-shot launcher and settlement relay instead of queuing the original prompt. Mapping a command does not create it; built-in/disabled command conflicts, unknown/disabled roles and duplicate entries reject setup. Attachments and frontmatter-driven model/tool/handoff selection remain unsupported. This is a text-only, asynchronous DSH adaptation, not upstream command-routing parity.

If a one-shot activation arrives after its caller cancelled startup, the source adapter attempts disposal and does not relay its result. An accepted child may already have executed. The plugin instance retains its worker capacity if that disposal fails; reloading the plugin does not prove the child stopped. This is not a guarantee that an already-returned child is cancelled when its caller later stops waiting. The native ToolRuntime may report the cleanup path as a Tool error rather than canonical `ABORTED`. If the current Host returns a malformed activation, or a legacy provider returns a malformed run, the plugin observes any accessible result rejection and retains global/route capacity unless the captured disposer succeeds; this fail-closed state lasts for the plugin instance and does not prove an unknown child has stopped.

A role prompt and `allowTools`/`denyTools` filters are not a hard security boundary. In DSH RC2, the subagent tool filter affects inherited global and ancestor-scope tools; the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport may still be visible. For must-be-read-only work, verify that DSH-native permissions, sandbox policy, or tool guards cover every visible tool, including scoped registrations and the reserved transport; dsh-omo does not install a per-worker hard guard; its optional write-existing-file guard covers only Tool calls named `write` case-insensitively (including same-named custom Tools; other names bypass) and does not remove the stat→write TOCTOU. Project-skill provider reads do not pass through model-facing tool approval or mutation-sandbox checks; they use the mounted DSH filesystem backend, cwd containment, version checks, and post-read path revalidation. The RC2 filesystem contract has no atomic no-follow open, so an adversarial concurrent swap-and-restore could still evade path checks; this is not a race-free OS read sandbox. Treat repository skill content as untrusted and do not use it to expose secrets.

### Project agent files

On compatible legacy `start` providers, with `enableProjectAgentFiles: true`, an extra dsh-omo roster tool scans only the active session cwd's direct `.claude/agents/*.md` files; select one in the one-shot task tool with `role: __project_agent_file__` and `agentFile: <lowercase ASCII slug filename stem>`. This adapter accepts stems matching `[a-z][a-z0-9-]{0,63}` only. The loader rereads the selected file, requires a matching `name`, optional single-line `description`, and a non-empty file body (it does not parse Markdown syntax), and accepts optional bounded `tools` metadata as a comma-separated scalar or YAML string array. It rejects unsupported metadata (including model/permission fields), YAML tags/aliases/nesting/multiline values, invalid UTF-8, symlinks, and paths outside cwd. The current Host `startActivation` contract has no per-request `persona` or `toolFilter`, so setting `enableProjectAgentFiles: true` fails during plugin setup; the detailed listing/launch flow below is available only to compatible legacy `start` providers.

This feature is default-off and bounded at the adapter level (it copies/processes at most the first 256 direct entries, returns at most 32 roster entries, reads at most 16 KiB/file and 128 KiB per roster, and applies a five-second deadline per list/load operation; a backend that ignores `AbortSignal` may continue I/O after return). DSH `fs.listDir` has no paging/limit contract and returns the full direct-child array, so an unusually large directory can still cause Host-side allocation before the adapter cap.

For compatible legacy `start` providers, the roster returns only filename/name/description, while only the sanitized body becomes provider `persona`; `tools` metadata is not exposed in the roster.

A non-empty `tools` list is lowercased/deduplicated and capped at 64 names of at most 128 UTF-8 bytes each. For compatible legacy `start` providers, each name must resolve to a DSH global Tool visible in the parent scope, and the selected provider must advertise `toolFilter`. The list becomes a one-shot allowlist for inherited global/ancestor DSH tools and intersects the selected category filter (denies win); unknown/unavailable names or an empty intersection fail closed. Missing or empty `tools` leaves existing inherited-tool behavior unchanged. The reserved DSH name `run_code` is rejected in configured filters. Current Host `startActivation` has no `toolFilter` field, so `enableProjectAgentFiles` rejects at setup and no allowlist is applied. Even with legacy providers, this maps only to DSH `SubagentStartRequest.toolFilter`, not full Claude permission semantics: child-scope registrations and the reserved PTC transport may remain visible, so it is not a hard permission boundary.

Project instructions are untrusted prompt text and cannot directly grant tools, but may influence a child that already inherits tools; the warning is advisory rather than an enforcement boundary. Treat this mode as trusted-repository-only; on compatible legacy providers, select a category with restrictive inherited-tool filters and retain DSH approvals/policy. Project-file agents have no role-specific route.

Files cannot define model routes or full permission semantics beyond the narrow inherited-tool allowlist, and the selected file is reread at launch. There is no home/global/ancestor scan or merge, primary-agent switching, Host-native picker, or per-agent skills/display metadata.

DSH filesystem reads are plugin-level, not an approval-gated model Tool, and identity/version rechecks cannot remove TOCTOU risk. The existing role/filter warning above applies to these definitions as well.

`enableImageQueryTool` defaults to `false`. When enabled, configure `imageQueryRoute: { provider, model }` for the user's image data, and ensure globally installed `llm/stream` middleware is trusted: it may observe or rewrite the request, including the route. The Tool accepts only image references captured from the last real user message in the current Agent's pre-step (`source.kind: user`), never a model-supplied attachment ID or file path. Use legacy `imageIndex` (default 0) for one image, or `imageIndices` for 1–4 unique zero-based positions from the first 16 image blocks found within 4,096 content blocks; selected images are sent together in that order, then the capture is consumed once. Each image is capped at 8 MiB/32 megapixels and a multi-image batch at 16 MiB/64 megapixels combined. Capture/generation state is bounded at 128 and owner-tagged to exact Agent identity; when Host `agents.get` is available, stale same-ID Tool calls and late completions are ignored and disposal clears only matching owners. Without that lookup, conflicting same-ID captures fail closed until exact disposal. Cross-event Agent reference stability is not live-runtime verified; identity mismatches intentionally fail closed. The selected model must advertise image input, which does not guarantee it accepts multiple images; a rejection fails closed without fallback. Per-image adapter bounds also include 12,000 pixels per dimension, 1,024 output tokens, and 6,000 output characters. dsh-omo submits a non-persisted `RequestUserInput` and does not itself append a session message or save a new image. This is a DSH-specific direct call, not an OMO `look_at` child session. The Host LLM adapter may also read or cache provider-specific image projections.

`enableReadImageResizing` defaults to `false`. When enabled, a successful top-level `read` result with at most 256 content blocks and four valid image references (each at most 8 MiB, 12,000 px per edge, and 32 MP) can be adapted through `tools/post-execute`. Images are considered only above 1,568 pixels on an edge or 5 MiB; DSH `attachments.readImageRequest` is asked for those targets, and a replacement is accepted only when the variant preserves aspect ratio, fits both targets, and is strictly smaller than its source. The source file and original attachment are never modified. This is a DSH-specific approximation, not exact OMO parity: the Host event does not expose the session model provider, so there is no Anthropic-only gate or provider-specific token estimate; instead, the adapter appends one bounded pixel-dimensions-only context for valid references (source → validated result dimensions when resized). `readImageRequest`'s byte target is best-effort, and `saveImages` durably stores derivatives; there is no delete capability: the 8-MiB cap is per read and applies to request-variant bytes handed to `saveImages`, not normalized durable bytes or lifetime storage, so unique images can accumulate indefinitely. Cancellation during a commit or a post-save normalization mismatch can also leave an unreferenced derivative. Enable this only if that storage tradeoff is acceptable.

`enableThinkModeReasoning` defaults to `false` and requires DSH `llm.resolveCallConfig`. It scans the latest real user message, capped at 4,096 content blocks and 65,536 UTF-16 text units, strips fenced/inline code, and detects the pinned multilingual think/ultrathink cues. For a cue, if the selected `agent/request` config omits `reasoningEffort`, it tries the unchanged provider/model with `reasoningEffort: 'high'` under a five-second deadline and returns only that field change when resolution accepts it; explicit effort and route are preserved. Rejection, timeout, or caller cancellation leaves the original config unchanged. The cue is tied to exact Agent object/turn/step identity and mismatches fail closed; without Host `agents.get`, a same-ID conflict stays unavailable until exact disposal. This is a DSH-specific approximation: DSH has no OpenCode `variant` field, and `resolveCallConfig` does not bind the later `prepareCall` dispatch, so the final adapter may still differ. It never guesses a `-high` model ID.

**Shared model catalog (added in 0.1.13):** `models` accepts up to 64 explicitly authored aliases, for example `models: { fast: { model: 'your-provider/your-model', reasoning: 'low' } }` (replace placeholders with exact configured IDs). A role/category may set `model: 'fast'` and omit `provider`; this expands once before existing exact-pair route aliases and fallback duplicate checks. An explicit `provider`/`model` pair remains literal, even if its model happens to match a catalog alias. Catalog `reasoning` fills only omitted same-entry `reasoningEffort`; use-site settings win. Targets must already be fully qualified: no recursive aliases, reasoning suffix parsing, fuzzy IDs, provider discovery, builtin tables, startup requests, or automatic parent routing. Aliases are case-sensitive ASCII letter-led names up to 64 characters (letters/digits/`_`/`.`/`-`; reserved prototype keys reject); provider/model-tail/reasoning caps are 128/256/64 characters with no surrounding whitespace or controls. The model tail retains additional `/` characters. Invalid catalog entries fail setup, even if unselected. `fallbackModels` may likewise use `{ model: 'fast', reasoningEffort?, maxTokens? }` with omitted provider; expansion occurs before exact-pair route aliases and duplicate checks against both primary and other candidates. Explicit fallback pairs remain literal. Catalog reasoning is only a candidate default; explicit role reasoning still overrides candidate reasoning, and candidate token overrides retain existing behavior. Unknown model-only names reject rather than guessing a provider; existing chain sizes and deadlines are unchanged. This is not full upstream catalog/model-entry/config-layer parity.

`providerConcurrency` accepts at most 64 exact provider IDs and `modelConcurrency` at most 128 exact `provider/model` keys; values are non-negative safe integers. A model entry overrides its provider entry; therefore model `0` bypasses the provider cap for that exact model only, while the global ceiling still applies. The selected route cap cannot raise the `maxConcurrent` plugin-instance global ceiling (default 4). At the pinned upstream revision, [`defaultConcurrency` defaults to 5](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/features/background-agent/concurrency.ts), but its fallback counter is keyed by model when no explicit provider/model cap applies; the upstream configuration reference describes this as an all-provider maximum. It is therefore not equivalent to dsh-omo's global hard ceiling. Route admission uses the effective explicit category/role/fallback route and never guesses the parent’s inherited model. Global and selected-route saturation rejects immediately by default. Setting `maxPendingTasks` to an integer from 1 to 16 enables a bounded wait inside the original one-shot Tool call after route resolution, with an eight-second monotonic deadline. The coordinator checks global and route capacity in one synchronous grant; the same route remains FIFO while unrelated routes may bypass a saturated bucket. Excess, cancelled, expired or stale-parent calls reject without a child ID. Separately, `enablePendingBackgroundTasks` defaults to `false` and requires `maxPendingTasks` from 1 to 16; when enabled, only direct `dsh_omo_task` calls switch to no-wait startup and receive a process-local `bg_` pending task ID on global or selected-route saturation. Other shared callers (`dsh_omo_call_agent`, foreground join and `commandRoutes`) keep the existing in-call wait semantics. Pending IDs are not child IDs; `dsh_omo_task_pending_status` reads their lifecycle and `dsh_omo_task_pending_cancel` cancels queued/starting work or requests a fire-and-return interrupt for bound children when DSH supports it; a request does not prove the child stopped. A bound child's result and cancellation aren't available through this pending-ID adapter; child-ID result/wait/cancel Tools are mutually exclusive with this opt-in. Startup failures and expiries are announced to the exact current Agent; successful startup has no separate notice; this opt-in is mutually exclusive with those Tools. Queue state is in-memory only (up to 16 pending per exact Agent, 64 retained total, 30-minute pending TTL), does not survive plugin unload/restart, and has no dedicated pending-status/cancel Tool yet. Actual startup failures and child settlement are reported separately. When a call must wait, the combined role, task, category, agentFile and distinct explicitly requested skill names are limited to 32,768 UTF-16 code units; immediately admitted calls retain the ordinary validation limits. Invalid explicit category and project agent-file selectors reject before queueing. This is a logical input bound, not a hard heap-size guarantee; timers may return late if the event loop is blocked. It requires DSH `agents.get`/`withoutInitiator` and Cordis `ctx.on`/`ctx.effect`. The wait does not guarantee startup, does not survive plugin unload, and is not upstream's immediate pending-ID background queue. When `agents.get` is available, every one-shot launch rechecks the exact parent before startup and before result publication; a late activation for a stale or same-ID-replaced parent is disposed instead of being registered or relayed. Stale result settlement also unbinds that exact Agent's local result record so a replacement can track new work; it does not migrate results to the replacement. Without that Host lookup, an exact `agent/disposed` event also fences late startup/publication and clears the corresponding local result record. A same-ID replacement that is never accompanied by that event cannot be distinguished reliably; stale relay and an ID-bound result record can remain and may prevent the replacement from tracking work. This is a bounded lifecycle guard, not proof of liveness. A caller cancellation or plugin unload ends the local skill-lookup wait even if the Host `skills.get` Promise ignores cancellation, allowing the launch slot to return. At most 64 unsettled `skills.get` Promises are admitted per plugin instance; each retains its separate lookup slot until that Promise settles, and excess skill loads fail busy. The Host receives a signal linked to caller cancellation and plugin unload; unload does not abort the caller's own signal. The current Host contract races cancellation, but a provider may continue behind a settled Host Promise, so this is not a bound on underlying provider work, cross-instance work, or work after reload. Without cancellation, this adapter adds no separate lookup deadline. The one-shot launcher snapshots role, task, category, selected skill names, parent and signal before waiting or preflight; The inspected current Host ToolRuntime already snapshots and freezes JSON arguments, while defensive parent capture also limits damage from contract-violating same-process middleware. It is not a sandbox or permission boundary. If cleanup fails, or a Host returns an ambiguous duplicate child identity, this instance retains worker capacity until unload; it does not retry the failed disposer, and unloading or reloading does not prove a child stopped. Normal result settlement still releases its route reservation before disposal; in opt-in mode, global capacity remains held if disposal fails. These caps are local to one plugin instance and do not cover continuable children or provide OMO TTL/activity behavior.

Category and role route `fallbackModels` accept at most three explicit `{provider, model, reasoningEffort?, maxTokens?}` candidates. **Added in 0.1.12:** a role may also have a nonempty fallback-only chain without a primary pin or default category; an explicit task category then rejects. Its DSH `tools/post-execute` listener calls `next()` exactly once, then appends one fixed `additionalContexts` message only for a successful accepted result, live `exec.signal`, exact `bash` Tool/schema names, a schema with required string `command`, and a command no longer than 1,024 characters matching the pinned simple `cat`/`head`/`tail` file-read patterns ([upstream hook](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/hooks/bash-file-read-guard.ts)). It skips failed calls, compound shell expressions/pipes, option forms outside those patterns, schema mismatches, cancellation, and downstream blocks. Because DSH exposes no equivalent pre-execution warning output, this DSH adaptation advises after the command has run; it never blocks, rewrites, or retries Bash and does not mutate native results. A same-named custom Tool with the matching schema may also match, and later middleware may drop the advisory context. DSH `read` provides line-numbered output; this is not OpenCode hash-anchor parity or a security boundary.

`categoryRoutes` is an explicit dsh-omo user-configured (custom-only) primary-route table (up to 32 names, each at most 64 characters), not an upstream built-in category registry: a task may choose a configured `category`, or `roleRoutes.category` may set that role's default. Optional `description` is a single line capped at 512 UTF-8 bytes before trimming and appears as `name: description` entries in the one-shot/continuable task-tool description for enabled categories only; it is chooser metadata, not a child prompt or policy. Optional `disable` defaults to `false`; `disable: true` hides a configured route from tool choices and rejects explicit selection; role defaults to disabled routes fail configuration because they implicitly select that category; disabled entries still require provider/model. A category specifies a primary provider/model plus optional ordered `fallbackModels` (at most 3 explicit provider/model candidates, each optionally with `reasoningEffort`), category `reasoningEffort`, and dsh-omo's camelCase `maxTokens` field (not upstream's canonical `max_tokens`); dsh-omo validates it as a positive safe integer. Explicit role provider/model/reasoning/token settings take precedence, while the specialist role controls the prompt. Category `tools` accepts at most 64 boolean tool-name rules (each name at most 128 UTF-8 bytes) and rejects DSH's reserved `run_code` name; `true` entries map to DSH inherited-tool allow filters and `false` entries map to denies; category allowlists intersect role allowlists (an empty intersection filters all inherited tools), while category and role denies are unioned and removed from allowlists so denies win. Unlike upstream tool-set overrides, these monotonic DSH filters cannot grant tools that were not already inherited. As with role filters, DSH restricts inherited global/ancestor-scope tools only; child-scoped registrations and reserved PTC `run_code` may remain. Current Host `startActivation` has no per-call `toolFilter`, so selected role/category filters fail closed before activation; compatible legacy `start` providers may enforce their advertised `toolFilter` capability; continuable tasks use DSH's scoped `tools.restrict`; this is not full upstream permission-policy parity. Category `promptAppend` remains task-message guidance, not a child system-prompt append. Category `maxTokens` maps to DSH `agentOptions.maxTokens`; the selected DSH subagent provider must advertise `SubagentCapabilities.agentOptions`. This is an output-token ceiling, not upstream `max_prompt_tokens` prompt-budget control, which is not implemented. No category/model fallback chain is implemented, and missing routes still inherit the parent/session model. Shared slash-task steering commands reject raw input longer than `maxTaskChars` before queueing it to the current agent.

`enableRoleCategoryRouteAliases` defaults to `false`. When enabled, `roleCategoryRouteAliases` accepts at most 32 exact `{from:{provider,model},to:{provider,model}}` mappings and rewrites only configured `roleRoutes`/`categoryRoutes` primary and fallback pairs, once at setup. A mapping may include an optional `reasoningEffort` default: applicable explicit role, category, and fallback settings win, and the alias default is used only when those are absent. Normalized fallback deduplication, capability preflight, `/omo status route`, and route-concurrency reservation use the effective target pair; the status command discloses source-to-target and the default reasoning setting for an aliased primary. Other controls such as `maxTokens`, prompt, skill, and tool fields are preserved. Aliases do not rewrite the parent/session route, image-query route, or profile-wide `runtimeFallback` chains; configure those chains with effective target pairs when they should cover aliased children. This DSH-specific pair remapping is not OMO's global named-model/profile alias or capability/variant normalization. Duplicate source mappings, chains/cycles, and routes that collapse to duplicate primary/fallback pairs are rejected.

`categoryRoutes[].skills` optionally binds up to four distinct exact kebab-case skill names to a category. The selected explicit category replaces the role's default category; its defaults load before per-call `dsh_omo_task.load_skills` extras, deduplicate in first-seen order, and share the four-name unique limit. This applies to one-shot `dsh_omo_task` and `dsh_omo_call_agent`; `dsh_omo_task_continuable` rejects a selected route with skill defaults rather than silently dropping them. Each name is loaded through Host `skills.get` using the exact parent Session CWD and a signal linked to caller cancellation and plugin unload, must be model-invocable, and is subject to the existing 8 KiB per-skill/24 KiB aggregate UTF-8 body caps; bodies are appended to the child task as untrusted guidance. A valid single-line Host `resourceBase` is also included as a JSON-encoded untrusted hint (up to 1 KiB UTF-8 per skill); invalid, control-character or oversized hints are omitted. This does not read resources, rewrite references, grant permissions, or guarantee a display path is usable in the child's filesystem. Unknown or unavailable names, non-model-invocable entries, over-limit bodies/counts, cancellation, and provider errors abort before activation. The loader is default/global+CWD only and does not pass an AgentPreset `ScopeKey`; if the selected user-agent or role route configures `agentPreset`, any explicit or category-default skill request is rejected before lookup rather than loading a potentially shadowed body. A route without `skills` behaves as before; when no category default is selected, this feature adds neither prompt text nor changes to the existing Tool schema.

`roleRoutes.promptAppend` and `categoryRoutes.promptAppend` are literal UTF-8 strings capped at 4,096 bytes each before trimming; whitespace-only values within the cap are ignored. dsh-omo rejects disallowed C0/C1 controls (tab and line breaks are allowed). File references remain literal by default. With `enablePromptFileExpansion: true`, only an entire selected, config-authored `roleRoutes.promptAppend` or `categoryRoutes.promptAppend` value of the form `file://relative/path.md` expands at task invocation; the path is relative to the exact live session CWD. It never resolves model-authored task text, surrounding text, unselected routes, user-agent prompts, absolute or `~` paths, globs, percent-encoded paths, or query/fragment syntax; pre/post checks reject symlinks and targets outside CWD when observed. Because DSH `readBytes` has no atomic no-follow/expected-version read, a concurrent path swap can still expose bytes before the post-read checks, so this is not adversarial isolation. Reads use DSH `fs` at the plugin level (not an approval-gated model Tool), strict UTF-8, 4,096 bytes per file/append and 8,192 bytes combined; one five-second deadline and the invocation/lifecycle cancellation signals cover both reads. Before/after identity/version checks reduce, but cannot eliminate, TOCTOU; a backend that ignores cancellation may continue I/O. Imported file text receives an untrusted-content notice and becomes task-message guidance, not a system prompt. For a selected category (explicit category before role default), its text appears in an “Additional category guidance” section, followed by any “Additional role guidance”; the two append payloads together are at most 8,192 bytes. This task-message composition is dsh-omo’s partial adapter for upstream category `prompt_append`, which appends to the system prompt; DSH exposes no per-child system-prompt append field here, so this does not change/replace the provider’s system prompt or grant an enforcement boundary. The chosen category-before-role section order is an adapter rule, not an upstream category-vs-agent system-prompt ordering guarantee.

`provider` and `model` must be set together when overriding the route; role `reasoningEffort` and positive-safe-integer `maxTokens` may be configured alone and ordinarily merge over the parent route. Category and role `maxTokens` pass through current `startActivation.request.agentOptions`; the selected provider's `agentOptions` capability is checked before activation. If provider/model changes without an explicit `reasoningEffort`, inherited effort is cleared so the new model can use its default; do not generalize this to other omitted options. By default, dsh-omo does not preflight ordinary category/role routes; optional `enablePinnedRoutePreflight: true` validates one explicitly pinned primary route when no applicable non-empty fallback chain exists (five-second deadline with caller cancellation; an adapter may continue work if it ignores abort; missing or rejected preflight fails before child creation); when a selected category has non-empty `fallbackModels` and no explicit paired role provider/model pin applies, or when an explicit paired role route defines its own non-empty chain, it probes the primary then up to 3 candidates serially with DSH `llm.resolveCallConfig` before child start, each with a five-second derived-signal deadline (a missing resolver or all rejected candidates fails the launch; timeout skips that candidate, while caller cancellation stops probing and an adapter ignoring abort may continue work). A pinned role chain supersedes the selected category chain; a role pin without its own chain still bypasses category fallback preflight. The 0.1.12 fallback-only role form instead has no primary/default category, rejects explicit category selection, and probes only its explicit candidates within one shared five-second deadline; it never silently inherits the parent after all candidates fail. This checks exact call configuration, does not reserve or bind a later dispatch, and cannot guarantee the provider/model will work at request time; routes without configured chains retain no-preflight behavior unless `enablePinnedRoutePreflight` is enabled. Separately, the human-only `/omo status route role:<name>` or `/omo status route category:<name>` explicitly checks exactly one selected configured primary, even when automatic `enablePinnedRoutePreflight` is off. It uses the normalized route, checks no fallbacks, and calls only `llm.resolveCallConfig` under a five-second caller-cancellable deadline; unknown, disabled, inherited, and unpinned routes are not checked. The command does not stream a model call or create children, and its compatibility result does not verify credentials, endpoint/model health, or later dispatch; adapter-owned lookup may continue if it ignores cancellation. `/omo-models` reports advisory metadata and does not reserve or validate a future route.

Role-route `allowTools`/`denyTools` maps remain configurable for legacy `start` providers, but current Host `startActivation` has no `toolFilter`; selecting a filtered route fails the one-shot launch closed before child creation instead of restricting tools. Even on legacy providers, these filters affect inherited global/ancestor scopes only; child-scoped registrations and reserved PTC `run_code` may remain, so this is not a hard permission boundary. An explicit `allowTools: []` likewise rejects the selected route on current Host and is only an empty inherited-tool allowlist on compatible legacy providers. Empty `denyTools` is a no-op and is omitted. DSH exposes provider-owned retry policy metadata and an `agent/request-error` retry-action waterfall; the default-off profile-wide `runtimeFallback` table adds a bounded partial cross-model route switch as described below. `maxConcurrent` limits this plugin's active one-shot runs; DSH owns the separate continuable-session capacity. A parent's `maxTokens` can be inherited at child creation, but RC2 continuable descriptors/cold resume do not persist it; dsh-omo rejects continuable launch if a role/category route or parent has `maxTokens`. DSH workers inherit the parent workspace; this plugin does not promise a separate child `cwd`.

`runtimeFallback` is an explicit profile-wide route table, not a dsh-omo-child-only policy. Example:

```yaml
runtimeFallback:
  enabled: true
  retryOnStatuses: [429, 500, 502, 503, 504]
  cooldownSeconds: 60
  chains:
    - provider: primary-provider
      model: primary-model
      fallbacks:
        - provider: approved-backup-provider
          model: backup-model
```

The config accepts at most 32 primary chains, each with 1–3 fallback routes. The controller matches the exact `provider`/`model` returned by DSH `agent/request`. In `agent/request-error`, it calls the waterfall's `next()` and preserves any delegated `{kind:'retry'}` action. It also consults the supplied `retryPolicy`: for `mode: 'normal'`, when the current `failure.code` is in `retryableCodes`, a remaining `maxRetries` budget blocks cross-route switching until the route-wide delegated retry count reaches `maxRetries` (counts are cumulative across failure codes for the same Agent/turn/step and reset on route change); `mode: 'always'` and unknown/malformed policies fail closed. If no policy is present, or no same-route retry remains (or the code is not retryable under the policy), it switches only when the numeric `failure.status` field is listed in `retryOnStatuses` (default `[429, 500, 502, 503, 504]`). If a normal policy advertises retries remaining but no delegated handler returns `{kind:'retry'}`, the adapter leaves the failure terminal rather than switching. Host Inspect contracts were checked, but no live AgentLoop/provider integration test was run. The active retry cursor is bounded and scoped to one Agent/turn/step; the separate exact-route cooldown cache is per Agent, capped, and cleared on disposal. After a successful fallback response, DSH's logged provider/model may remain in later requests, and this adapter does not restore the primary. It has no proactive availability lookup, message-text error classifier, session timeout escalation, automatic primary restoration, or user-facing toast; its optional `cooldownSeconds` only skips recently failed configured fallback candidates. Missing/unlisted statuses fail closed. A route switch can send the same prompt to another provider; configure only endpoints approved for that data. Route changes are logged without Agent/session ID, prompt, or error contents; DSH retains control of cancellation.

`disabledOmoRoles` defaults to `[]` and accepts exact dsh-omo built-in specialist names or names declared in `userAgents`; for example, `disabledOmoRoles: [architect, reviewer]`. It removes those roles from dsh-omo's one-shot/continuable tool choices and descriptions, orchestration guidance, and `/omo` help. Calls and `roleRoutes` entries targeting a disabled role fail closed, and at least one role must remain enabled. This local selector does not deregister Host/native/third-party agents and does not disable a same-named slash command (for example, `/architect`); it is not upstream per-agent `disable` behavior or OpenCode's global `disabled_agents` setting.

## DSH Host job monitoring

`enableJobTools` defaults to `false`. Set it to `true` only when the optional Host `jobController.list` and `jobController.follow` methods are available:

```yaml
enableJobTools: true
```

`dsh_omo_job_list` reads only the initial rows snapshot from the infinite stream, then closes it; output is capped at 50 jobs (25 by default) and 48,000 bytes after serialization/rendering. `dsh_omo_job_follow` derives its owner session from the current `exec.agent.id` (never a model-supplied `sessionId`), accepts an optional absolute byte offset `from`, and bounds each call to 8 seconds, 32 frames, 16 KiB of UTF-8 output, and 48,000 serialized/rendered bytes. It preserves absolute cursors and `lossy`/`gapBefore` indicators while projecting an explicit allowlist; `JobView.detail` and `output.spillPaths` are omitted. These model-facing tools do not expose or call `jobController.kill`: the Host's exact Remote kill contract only checks whether the invoking session can see a job (owned or unowned) and explicitly performs cancellation on a human's behalf. With no stable OMO-task ownership token, generic job cancellation is not safe to expose to the model; when `enableJobTools` is on and the Host method exists, only the separate human command `/omo-job-kill` calls it. Native DSH job-control tools are separate and remain governed by Host policy. Job kinds, labels, and log output are untrusted data. The optional Job Tools provide only DSH job monitoring; they do not implement OMO Monitor process output/cancellation or BackgroundManager task identity/TTL. Host has no direct result-by-child-ID Service: `startActivation` exposes a result Promise on the returned activation, `listChildren` is a catalog, and `subagent/end` is emit-only; `sessionQuery.readSession` reads the complete child log rather than a final-result projection. The opt-in `enableTaskResultTool` bridges only dsh-omo one-shot tasks by caching the activation's bounded text excerpt for the exact parent Agent and returned child ID: 64 parent Agents, 32 children per parent, 256 total entries, an 8,192-character excerpt cap, and a 30-minute expiry after settlement that reads do not extend. It also registers `dsh_omo_task_list`, which returns at most 32 exact-Agent childId/status pairs from this same cache without result bodies or Host descendant queries; expired, evicted, or untracked children are omitted. It is process-local, clears on Agent disposal/plugin unload, and exposes no arbitrary child sessions; it is a DSH-specific result lookup, not durable OMO BackgroundManager polling or monitor-process output. Enable with `enableTaskResultTool: true`. Durable read-after-restart retrieval still requires a Host API that authorizes the exact parent-child relation and returns bounded final assistant output plus terminal status. Enable the result lookup with:

```yaml
enableTaskResultTool: true
```

`enableTaskResultPersistence` defaults to `false` and requires `enableTaskResultTool: true` plus Host `storageDomain.open`. Opt in explicitly:

```yaml
enableTaskResultTool: true
enableTaskResultPersistence: true
```

This stores only completed, incomplete, or failed one-shot result snapshots, keyed by the exact parent session ID and child ID, with an 8,192-character excerpt cap and a maximum 30-minute settlement TTL. It is a derived cache, not session-log state; committed DSH session events remain authoritative. Active/running children are never written, reattached, or resumed; results are not injected into prompts and no arbitrary Session lookup is added. Stored child excerpts may contain sensitive or untrusted text. The feature is off by default; Host backend availability is profile-dependent and does not guarantee restart durability. The adapter targets a 256-row cap and bounds table scans at 512 rows: an oversized existing table makes persistent listing/new writes fail closed (exact-key reads still work for valid rows). `storageDomain.open()` validates every existing row before adapter cleanup; a malformed row can fail the whole domain open, and this spec does not request backup-and-skip, so the live in-memory cache remains usable but persistence is unavailable. The Host KV API has no multi-record transaction: the new row is written before best-effort eviction, preserving old rows if that put fails; failed cleanup may leave up to 512 rows until a later successful pass. Operations are serialized with at most 64 queued/in-flight persistence operations per store, including those waiting for domain open. Excess reads/lists/writes/deletes are skipped immediately with a coalesced saturation diagnostic; live in-memory results remain usable, but skipped mutations are not retried or guaranteed durable. Capacity returns only when an accepted operation settles. Unload drains for up to one second before best-effort close; an in-flight backend operation may settle after close, so write durability is not guaranteed. Storage failures fall back to current in-memory behavior. Clearing an Agent invalidates any in-flight `readAsync`/`listAsync` restore so late storage results cannot repopulate its cleared cache. That generation fence does not delete the stored snapshot: when persistence is explicitly enabled, a new Agent with the same session ID may still restore a previously persisted terminal result. That is intentional session-keyed recovery, distinct from stale settlement publishing to a disposed Agent; it is not proof that the old Agent is live or that its result was migrated. This is a terminal-result cache, not durable task execution or OMO resumable-long-work parity.

`enableTaskWaitTool` defaults to `false` and requires `enableTaskResultTool: true`. It exposes `dsh_omo_task_wait` for a tracked one-shot child, waiting while active or returning its cached result if settled; `waitMs` defaults to 8,000 ms and accepts 1–30,000 ms. Waits are capped at 32 concurrent calls globally and four per exact Agent. A timeout, caller cancellation, Agent disposal, or plugin unload ends the waiter but does not use the wait Tool to interrupt the child. When a timed-out/cancelled child later settles while the Agent/result cache remains available, read its bounded result with `dsh_omo_task_result` or wait again. This is a local DSH one-shot convenience, not OMO session/job polling or durable task execution.

```yaml
enableTaskResultTool: true
enableTaskWaitTool: true
```

Pinned OMO's [background-command guidance](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/features.md#L818-L841) directs one-shot commands that must continue in the background to managed Monitor `monitor_start`, not shell `&`. DSH `jobController` exposes `list`/`follow`/`kill` only, and dsh-omo Job Tools expose `list`/`follow`; these are not process-start monitors, continuable subagent tasks, or PTY terminals. A future adapter requires a Host-owned, session-scoped process-monitor API that enforces DSH sandbox/approval policy, exact Agent/session ownership, bounded resumable output, and cancellation. The lower-level `subprocess.spawn` contract accepts a fully specified `argv`/`cwd`/stdio/grace but exposes no Agent, sandbox, or approval parameter; it is not a safe model-facing Monitor replacement.

`enableToolResultPruning` defaults to `false` and requires at least one high-output adapter: `enableJobTools: true` or `enableAgentTerminalTools: true`. If the optional Host `toolResultPruner.pruneContent` method is present, it attaches DSH's final-content pruner only to successful `dsh_omo_job_follow`, `dsh_omo_terminal_read`, and `dsh_omo_terminal_send` results. Over-budget rendered text may be pruned while each structured `value` remains unchanged; errors and pruner failures keep original content. The Host pruner preserves rich-block order. If the service is absent or incomplete, no finalizer is registered. This is narrow DSH output pruning, not OMO Dynamic Context Pruning (duplicate-call recovery, protected tools, turn protection, and compaction-triggered behavior); it never invokes durable `pruneSession` rewrites. Enable it alongside job tools with:

```yaml
enableJobTools: true
enableToolResultPruning: true
```

`enableManualContextPruning` is a separate default-off human command and requires DSH `agents.get`, `sessions.get`, and `toolResultPruner.pruneSession`. Run `/omo prune-context` to prune over-budget Tool results from only the invoking Agent's exact live Session; no session ID can be supplied, and this command is never invoked automatically. The Host pruner rewrites the current model surface while preserving source events for replay; on normal return the command reports completion and directs the user to review the current conversation, without interpreting the Host's summary fields. `pruneSession` is synchronous and has no cancellation parameter; if the Host rejects a later replacement, earlier replacements may already have landed, so inspect the session before retrying. This is a manual DSH action, not OMO Dynamic Context Pruning, deduplication/recovery, protected-tool, turn-protection, or notification parity. Enable it with:

```yaml
enableManualContextPruning: true
```

`contextOverflowRecovery` is a separate default-off, one-shot retry adapter. It requires DSH `agents.get`, `sessions.get`, `toolResultPruner.pruneSession`, Cordis `ctx.on`, and `ctx.effect`; configure only exact provider/error-code pairs you have verified for your provider. It does not infer context overflow from message text, and no provider codes are enabled by default. The listener delegates first, preserves any retry selected by runtime fallback or another downstream handler, and only considers a matching code when there is no delegated retry. It verifies the exact live Agent and current Session before pruning and checks identity plus cancellation again before returning `{ kind: 'retry' }`; retry is returned only when the Host reports at least one landed replacement. If pruning has no output and the optional Host `compaction` service exists, the adapter makes one bounded `compactIfNeeded({session, options:{}}, 'context-overflow', signal)` attempt and retries only after a non-null result; null, error, cancellation, or stale identities leave the failure unretried. No-op results, lookup errors, stale identities, cancellation, malformed results, or a `pruneSession` throw leave the failure unretried. A throw may follow partial durable replacements, so the turn attempt is consumed and no second automatic retry is issued. The cap is one existing/delegated retry **or** one pruning retry per exact Agent turn. The Host pruner may remove multiple over-budget tool outputs using character budgets, can discard useful evidence, and may not resolve the provider's limit; this is a narrow DSH adaptation, not OMO DCP. Example shape only—replace the placeholder with a provider-specific code that you verified:

```yaml
contextOverflowRecovery:
  enabled: true
  codesByProvider:
    your-provider-id:
      - EXACT_CONTEXT_OVERFLOW_CODE
```

`enablePressureCompaction` defaults to `false` and requires DSH `agents.get`, `sessions.get`, `compaction.compactIfNeeded`, and Cordis `ctx.on`/`ctx.effect`. It runs at awaited `agent/turn-stopping`, after live tool calls have settled and before the turn boundary commits; the adapter checks exact live Agent/Session identity and forwards the turn signal combined with plugin disposal. DSH owns the pressure threshold, selected history range, and summary implementation; a null result is a no-op, and compaction failures emit only a fixed warning without vetoing turn closure. This may delay turn closure while a needed compaction runs. It is a DSH-specific turn-boundary subset, not OMO's same-turn after-each-tool 78% token threshold, per-Agent compaction-model selection, cooldown, or post-compaction recovery. Enable explicitly with:

```yaml
enablePressureCompaction: true
```

`enableSearchToolResultPruning` is a separate default-off option and does not require job or terminal Tools. It listens after direct case-sensitive `grep`/`glob`/`web_fetch` dispatches plus up to 32 explicitly configured `additionalSearchToolResultPruningTools` names (each an exact safe Tool name ≤128 UTF-8 bytes), and prunes only when the result is explicitly successful, the downstream decision is accepted with a `content` array and no `value` property, the caller signal is live, and `tools.get(name, agent)` captures a same-named caller-visible Tool with no `projectContent` or `finalizeContent` callback before dispatch. It snapshots the caller-visible Tool during `tools/pre-execute`, keyed by the execution token, invalidates pending snapshots on Host `tools/change`, and rechecks identity before and after the downstream waterfall. ## Optional models.dev capability snapshot

Live `/omo-models` provider listing and exact `provider/model` lookup honor both caller and plugin-lifecycle cancellation. A single 15-second wait deadline starts before the catalog stage and is reused for exact metadata resolution; an already-canceled request does not read the catalog. Host `llm.listProviders()` is a synchronous, no-signal API: these checks cannot interrupt synchronous execution. Awaited custom/async responses are locally bounded but cannot be forcibly stopped, and late responses are discarded. `resolveModelInfo` receives the same aggregate signal. This is metadata inspection, not a model request or provider-health guarantee.

`enableModelCapabilitiesRefresh` defaults to `false` and requires DSH `web.fetch` plus a provider configured to return the complete catalog. Plugin setup never fetches: a user must explicitly run `/omo-models refresh`. The adapter requests only `https://models.dev/api.json`, requires a non-truncated 2xx text response with valid JSON, and forwards cancellation with a five-second deadline; a provider that ignores abort may continue I/O, but its late reply is discarded. New refreshes are rejected while that underlying fetch remains unsettled, even after the local wait is canceled or times out; success or rejection of the backend releases the per-command slot. This bounds overlap within the registered command, not across plugin reloads or other Web callers. The exact `WebFetchResult.url` comparison is only a post-fetch consistency check: the DSH contract does not say whether it is the requested or final URL, and the built-in HTTP provider allows up to five redirects by default, so this is not redirect/SSRF protection. Generic `WebFetchRequest` has no per-call size, MIME, or redirect controls. The inspected `include:web-fetch-http` schema defaults to `maxBodyChars: 100000`, `maxResponseBytes: 5000000`, and `maxRedirects: 5`; a current models.dev response exceeded the 100,000-character cap during this audit, so the default HTTP provider may return `truncated: true` and the plugin will reject it. Raise the selected HTTP provider's `maxBodyChars` above the complete catalog (256,000 is an audit-time starting point, not a future guarantee) and keep its pre-read `maxResponseBytes` cap at or below 8 MiB; configure custom providers with comparable pre-fetch bounds. The plugin cannot inspect or change provider config, and its own 8 MiB check happens only after the body is returned, so it does not limit network/memory use from an unbounded provider.

A successful refresh stores only an allowlisted capability projection for up to 512 providers and 100,000 scanned models in memory; it does not write a file or survive plugin restart. Use `/omo-models snapshot` for the count/time summary or `/omo-models snapshot <model-id>` for a single exact model entry. The snapshot is advisory metadata only: it does not establish provider availability, route compatibility, future call success, or a valid launch; it never makes an LLM request or affects routing. This is a bounded manual-refresh slice of OMO's [pinned refresh command](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/cli/refresh-model-capabilities.ts) and [snapshot parser](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/model-core/src/model-capabilities-snapshot.ts), not full cache/startup/compatibility parity.

```yaml
enableModelCapabilitiesRefresh: true
```

## Optional DSH web search

`enableWebSearchCommand` defaults to `false`; when enabled it requires the optional DSH `web.search` service and adds `/omo web-search <query>`. Each explicit command invocation issues at most one search with `maxResults: 5` and a 2,000-character single-line query cap. A 20-second handler wait deadline forwards an abort request through a combined Command/lifecycle signal, but the provider may continue work if it ignores cancellation. To prevent repeated calls from accumulating such work, dsh-omo rejects new searches while a prior provider Promise remains unsettled; at most one request can remain in flight per registered command. It is a narrow DSH Service adapter, **not** OMO's [remote Exa/Tavily `websearch` MCP implementation](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/mcp/websearch.ts), full MCP loading, or an Agent-callable search tool.

Each call accepts one bounded single-line query, requests at most five results, and uses the same 20-second wait deadline and cancellation signal. Result text is bounded, rendered inertly, and labeled untrusted; the Tool never fetches or follows result URLs. Tool visibility and network use remain subject to DSH policy/provider configuration. ## Read-only OMO plan checklist

## Agent-owned DSH PTY tools

`enableAgentTerminalTools` defaults to `false`. When explicitly enabled, dsh-omo calls the optional Host `terminals.listBackends()` during setup and registers five core tools only if a backend and the required Host methods are available: owner-scoped list, spawn, read, send, and close. If `terminals.signal` is available, it also registers `dsh_omo_terminal_interrupt`, which sends only `SIGINT` through the Host backend to an owned session; the backend chooses its target process group. This is a Ctrl+C-style interrupt, not a guarantee of tmux `send-keys` semantics or session close; no arbitrary signal is model-selectable. Registration is at plugin/profile scope, so every Agent that receives this plugin's tools can see them; each call still passes its exact `exec.agent` object to the Host, which fences access to that caller's sessions. The tool schemas expose no caller-supplied owner id or cwd; session-specific operations accept only a PTY session id and derive ownership from exact `exec.agent`. Spawn forwards only backend type and optional display name; extra input fields are not forwarded. List is never global. Spawn uses the backend's default cwd and accepts only a registered backend type plus optional display name. Reads are capped at 200 lines and 16 KiB of text; sends are capped at 4 KiB and wait at most 12 seconds, with output capped at 16 KiB. Cancellation requests Host operation cancellation and drains for up to one second; if the Host operation still has not settled, the tool reports that the PTY may remain busy. After a cancelled or timed-out interrupt, delivery may already have occurred or may still occur; the Host signal cannot be retracted. Terminal text and backend MOTDs are untrusted.

This grants an enabled Agent the ability to send interactive input that may execute commands. dsh-omo adds no sandbox or approval layer; execution/approval semantics belong to the configured Host backend, which must be trusted and reviewed before opting in. This is an Agent-owned PTY adapter, not tmux panes/layouts, worktree isolation, or a claim of full OMO terminal parity. No live terminal backend was verified in this session.

```yaml
enableAgentTerminalTools: true
```

To opt into the Host output pruner for PTY reads and sends as well, enable both flags (the optional pruner Service must also be present):

```yaml
enableAgentTerminalTools: true
enableToolResultPruning: true
```

## Project skills

**Skill format compatibility, added in 0.1.14:** `enableProjectSkillFormatCompatibility` defaults to `false`. Opting in accepts plain Markdown and empty/comment-only YAML, deriving missing names from valid DSH filenames/directories and supplying `Project skill <name>` when description is absent or falsy. Falsy `name` values likewise use the derived name; whitespace-only strings and truthy invalid metadata still reject. Compatibility-mode catalog descriptions receive an upstream-style source scope prefix; missing descriptions retain the local generated text after the prefix rather than upstream's empty suffix. The formatted description must remain within 2,000 characters. A directory may use `<directory>.md` only when `SKILL.md` is absent; existing canonical files retain priority even when invalid or symlinked. Compatibility mode skips direct hidden files and directories within each configured skill root, including stale hidden locators; this is not a secret-protection boundary. Within each root's already bounded entry prefix, compatibility mode classifies contained entries by target type and scans directories before flat Markdown files, preserving within-type order and root precedence. Classification performs additional metadata reads; type changes or read failures yield incomplete results. Entries outside the bounded prefix cannot receive priority, and truncated scans remain incomplete. Strict mode retains its original scan order. Stale fallback lookups invalidate and recover through a fresh catalog; Nested discovery and lookups also recheck that ancestor folders have no canonical or directory-named skill before and after reading; a scan detecting a change is incomplete and will not be cached. These checks are not an atomic filesystem snapshot. Truncated listings do not authorize uncertain fallback. Existing flat-file discovery, limits, containment/link policy and version checks remain intact. In opt-in compatibility mode only, traversal now follows at most three directory levels for canonical `SKILL.md` and directory-named fallback files when folders are containers; absent-name defaults use the leaf directory and remain flat kebab-case, not upstream slash namespaces. Container folders also expose ordinary Markdown files at up to two directory levels, with flat filename-derived names and their containing directory as the resource base. To preserve bounded directory-first precedence, root flat files precede nested flat files rather than matching upstream's namespace traversal order; flat names may collide. New higher-priority competing skills elsewhere rely on watcher delivery to invalidate an existing cached locator; ancestor checks do not detect all such competitors. A delivered provider watcher event, explicit refresh, or provider-detected stale locator also fences previously selected locators before and during loading, conservatively across workspaces; loading returns undefined rather than retrying. Explicit refresh additionally retires existing watchers and pending acquisitions for rebinding, while retaining their capacity reservations until disposal; immediate scans may be incomplete, and failed disposal can prevent recovery. Missed or delayed notifications, changes in other providers, and changes after the final check remain outside this guarantee. Deeper traversal, upstream slash namespaces, model/agent/MCP execution, and permission bypass remain unsupported. Opting in can expose additional Host catalog entries; default Tool schema text is unchanged (zero default first-turn Tool-token delta).

The DSH skill registry now discovers project-local skills relative to each skill lookup's `cwd`. Defaults are `.opencode/skills`, `.claude/skills`, and `.agents/skills`, in that priority order; each root accepts `<name>/SKILL.md` bundles and top-level `<name>.md` files. Skills need YAML `name` and `description`; optional `whenToUse` becomes top-level routing guidance, while `disable-model-invocation` and `user-invocable` map to DSH invocation flags. The current Host Agent also exposes its native `skill` Tool for loading an exact name from its skill catalog, so dsh-omo does not add a duplicate loader; the installed runtime's generic loader successfully loaded the bundled `debugging` guide, and real installed one-shot `load_skills` smokes completed. Project-file discovery remains verified through native registry/real-filesystem tests, not a live fixture added to the user's Profile. Other JSON-compatible frontmatter (including upstream `agent`, `model`, `tools`, or `mcp` fields) is preserved as metadata up to 12 levels deep; YAML aliases are rejected. These fields are not enforced: dsh-omo does not execute embedded MCP or bind the skill to an agent, toolset, or model.

```yaml
- id: dsh-omo
  config:
    projectSkillDirs: [.opencode/skills, .claude/skills, .agents/skills]
    enabledProjectSkills: [incident-response]
    disabledProjectSkills: [retired-project-skill]
    disabledOmoBundledSkills: [omo-code-review]
    disabledSkills: [legacy-skill]
```

`enabledProjectSkills` is an optional exact-name allowlist of up to 256 distinct valid names for dsh-omo's project-skill provider: when omitted or set to `null`, all discovered project skills are visible; `[]` exposes none. It is a narrow local adapter for upstream [`skills.enable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills), which filters config-sourced skills; the local field filters only project-provider candidates; bundled, native, and other-provider registrations are not filtered by it, so a same-name entry may remain visible. `disabledProjectSkills` is an optional denylist of up to 256 distinct valid names for that same provider, adapting upstream [`skills.disable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills); if both project lists contain a name, the denylist wins. Excluded project entries can reveal lower-priority same-name skills from another provider. `disabledOmoBundledSkills` hides exact dsh-omo bundled-skill names only, adapting upstream [`disabled_skills`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills) narrowly; names outside this package's bundled set are rejected, and DSH-native/other-provider registrations are not filtered; a same-name entry may remain visible. If a name appears in both this field and `disabledSkills`, hiding wins. Unlike these visibility filters, `disabledSkills` keeps matching bundled/project entries visible while disabling model and user invocation. The provider still scans and parses project skill files to read their frontmatter names, so these filters are not a scan-cost reduction or filesystem security boundary. When a project skill is both enabled and listed in `disabledSkills`, it remains visible but non-invocable.

`userOpenCodeSkillRoots`, `userClaudeSkillRoots`, and `userAgentsSkillRoots` default to empty arrays and provide explicit, default-off user-level sources. Each accepts at most two normalized absolute DSH-FS directories named `skills`, with no `~`/HOME inference, URI paths, relative paths, duplicates, or ancestor scanning. Validation currently uses the plugin host's `node:path` syntax, so cross-platform execution-world paths such as Windows drive/UNC paths on a POSIX host are not supported by this adapter. Within one Host registry layer, project roots retain ranks 230–245, configured user roots receive finite ranks above 245 and below 250, and runtime has rank 250. Across layers, the Host's nearest scope wins regardless of rank. Within this provider, OpenCode user roots precede Claude user roots, which precede Agents user roots, following the pinned upstream skill discovery order; upstream command merging uses a different order. Existing OpenCode and Claude ranks remain unchanged when Agents roots are configured, but other providers with ranks in the inserted interval can compete, and extra roots share the scan budget. User roots resolve independently of cwd (including no cwd) and use their own canonical root as containment boundary rather than the lookup cwd. Reads, entry/version checks, stale-locator rejection, bounded scans, and watcher lifecycle follow the same provider limits; project-only enable/disable filters do not implicitly disable user roots. Host `customSkillDirs` remains a different native source/rank/scan contract, not an equivalent of this adapter. `disabledSkills` accepts up to 256 ASCII skill names, normalizes case to lowercase and sets model and user invocation to false only on dsh-omo's bundled/project entries; it does not alter another provider's flags. Names must be valid DSH kebab-case after normalization; no alias relationship is inferred. Disabled entries remain registered, so a lower-priority same-name external skill may still be shadowed by the DSH registry's single-winner resolution. `projectSkillDirs` must be relative to the lookup cwd and cannot contain `..`; only canonical targets under that cwd are accepted, and symlinks resolving outside the configured root are skipped. Reads go through DSH `ctx.fs.readBytes` with a 256 KiB per-file cap; each catalog scan also caps processing at 512 directory entries, 256 accepted skills, and 8 MiB of skill text. `ctx.fs.listDir` returns a complete entry array before the plugin applies its scan cap, so extremely large directories may still cost backend enumeration memory. Reads do not pass through tool-level permission/approval prompts or the mutation sandbox. Reads compare DSH file versions and revalidate the final path after reading, but RC2 exposes no atomic no-follow open; a hostile swap-and-restore race is still possible, so this is not an OS read sandbox or race-free directory-handle boundary. Treat repository-provided skill text as untrusted instructions. Within dsh-omo roots, earlier configured paths rank first; all up to 16 configured roots rank ahead of dsh-omo runtime/bundled skills but remain below higher-priority DSH project sources. The default `.agents/skills` root may overlap the Host's native `project-agents` source; native project candidates outrank dsh-omo, so duplicate discovery is possible and has not been live-verified. Filesystem watchers monitor each configured-root component's lexical parent before examining it, plus canonical skill paths when available. A watched parent or skill-directory notification conservatively invalidates all provider catalogs and retires all its watchers before rebuilding them on later lookups; a file notification retires that file's watcher. This consumes more watcher capacity and directory events may cause cross-workspace churn. In-flight observations cannot then be cached or install old-generation watchers, and asynchronous or failed closes retain their capacity. Without a notification, an ancestor or old target may remain allocated, or a replaced directory or file may retain an old backend watcher. Filesystem path checks and watch setup are not atomic, and the Host contract does not promise lossless watcher events. If watch setup fails the catalog remains uncached, and `/omo-skills-refresh` can request another scan but does not itself reclaim watchers. User-global and remote skill sources, full OMO priority/config rules, intent activation, and skill-embedded MCP lifecycle remain unsupported.

## Project command files

`enableProjectCommandEmptyDescription` defaults to `false` and requires `enableProjectCommands`. When enabled, an exact empty-string `description` uses the same filename-derived `Project command /<name>` display fallback as an absent description, adapting the pinned upstream loader's acceptance of this field. Whitespace-only, non-string, unsafe, and oversized descriptions still reject; this option does not enable execution metadata or frontmatter routing. Because a previously invalid higher-priority command may now become valid, it can change which same-name command body is selected.

`enableProjectCommandBlankDisplayMetadata` defaults to `false` and requires `enableProjectCommands`. It separately adapts upstream's acceptance of blank string display metadata: a nonempty whitespace-only description uses the filename-derived safe fallback, and an empty or whitespace-only `argument-hint` is omitted so the Host's `[arguments]` fallback applies. Exact empty descriptions remain governed only by `enableProjectCommandEmptyDescription`; null, non-string, unsafe, and oversized values still reject. Enabling this option can change same-name fallback.

`enableProjectCommandUnterminatedFrontmatter` defaults to `false` and requires `enableProjectCommands`. When enabled, an opening `---` without the pinned parser's complete closing-delimiter-plus-newline shape is preserved as plain Markdown with absent metadata, including a closing `---` at EOF. Closed-block YAML errors and unsupported execution metadata still reject; the plain-text fallback treats such lines as body text, not executable metadata. Byte/control/body checks and normal command framing remain unchanged, and selection of same-name commands can change.

`enableProjectCommandMalformedFrontmatter` defaults to `false` and requires `enableProjectCommands`. When enabled, a fully closed frontmatter block with YAML parse errors discards all metadata and loads only the post-delimiter body with the filename-derived description, following the pinned loader's fail-open parse-error path. Valid YAML with unsupported execution fields, duplicate keys, multiple documents, warnings, unterminated delimiters, and strict default behavior remain rejected. This can change same-name command selection and does not grant execution metadata any authority.

`enableProjectCommandEmptyBody` defaults to `false` and requires `enableProjectCommands`. When enabled, empty and whitespace-only command bodies are accepted like the pinned loader, rendering an empty `<command-instruction>` while preserving the invocation in `<user-request>`. Byte/control checks and argument/render caps remain enforced; strict default behavior and same-name selection can change only when this option is enabled.

`enableProjectCommandPreserveBodyLineEndings` defaults to `false` and requires `enableProjectCommands`. When enabled, the parser retains the BOM-stripped original body line endings (including CRLF and lone CR) while using normalized text only for frontmatter/YAML processing; rendering still trims only the outer body and preserves raw invocation framing. Strict default normalization remains unchanged, and byte/control/argument/render caps stay enforced.

`enableAutomaticSlashCommands` defaults to `false` and requires `enableProjectCommands`. For a real-user plain-text leading slash message, the pre-step adapter resolves the effective command and rewrites only commands marked by this manager's registered project definitions. It does not execute the command handler, launch a child, or queue a second prompt. Unknown, built-in, shadowed, synthetic, attachment-bearing, and fenced-only inputs remain unchanged. Expansion preserves the original message ID/source and downstream request-series flags, deduplicates by exact Agent plus stable message ID for 30 seconds with a 10,000-entry bound, and honors caller/plugin cancellation. Optional `@file` expansion uses the existing bounded reader and remains independently disabled. This is a prompt-rewrite subset, not skill-as-command resolution, recursive templates, shell interpolation, or upstream's separate command-execution hook.

`enableProjectCommands` defaults to `false`; optional `enableProjectCommandWatch` also defaults to `false` and requires project commands. When enabled, dsh-omo scans flat `.opencode/commands/*.md`, `.opencode/command/*.md`, and `.claude/commands/*.md` files under the exact CWD of each newly created Agent and registers them in that Agent's scoped DSH command registry. The plural `.opencode/commands` root wins over `.opencode/command`, and either OpenCode project root wins over `.claude/commands` for duplicate names. Optional `userOpenCodeCommandRoots` can add up to two explicitly configured user-level OpenCode roots; each must be a normalized absolute DSH-FS path whose final directory is named `command` or `commands`. Optional `userClaudeCommandRoots` accepts at most one normalized absolute DSH-FS path whose final directory is named `commands`. Optional `userAgentsCommandRoots` adds at most two explicit normalized absolute DSH-FS directories named `skills`, adapted as flat Markdown command sources. User roots are scanned only when `enableProjectCommands` is true, after project roots; within this adapter their precedence is OpenCode, then Agents, then Claude, preserving existing OpenCode-before-Claude behavior and following the pinned command consumer's relative user-source order. This differs from the skill-provider precedence. There is no `~`/HOME inference or Node filesystem fallback, and user roots are never inferred or loaded unless configured. A configured root reported missing is skipped by the scan; with watching enabled, safely resolvable absent top-level project parents and exact configured user roots can be watched for later creation. Errors resolving/listing a root, a configured root path whose final component is a symlink, or a non-directory fail the Agent's scan closed and are reported through the existing warning. Individual files that fail validation are skipped. Command scanning and watch-target discovery share an instance-local cap of 64 unsettled Host filesystem Promises; cancellation ends local waiting but each lease remains until its Promise settles. At capacity, discovery fails busy without hiding the condition as a missing command. This does not include the actual `fs.watch` calls, which use the separate watcher cap. The scope is disposed with the Agent or plugin. Both sources accept a nonempty plain Markdown body, with optional YAML frontmatter. If `description` is absent, the DSH composer uses `Project command /<name>`; an explicitly supplied description must still be a nonempty safe string. Empty metadata blocks are accepted, while malformed, duplicate-key, or unterminated YAML headers fail closed instead of becoming command text. Both sources may also declare one optional display-only `argument-hint` (up to 160 safe single-line characters), which is passed to the DSH command composer. Execution-affecting metadata such as `agent`, `model`, `subtask`, `handoffs`, and tool policies remains rejected. For example, in `.claude/commands/review.md`:

```markdown
---
description: Review the requested area
argument-hint: "file paths or globs"
---
Review the request: $ARGUMENTS
```

Each command is rendered as `<command-instruction>…</command-instruction>` containing the trimmed body, followed by an unconditional `<user-request>` section containing the raw invocation text. Only the literal `$ARGUMENTS` placeholder in the body is expanded, so arguments appear both in the instruction and request section when the placeholder is present; this matches the pinned upstream command template. The prompt and its wrapper count against the 128 KiB rendered limit. Invocation text remains untrusted prompt data and is never scanned for file references. Separately, `enablePromptFileExpansion` defaults to `false`; when enabled alongside project commands, a bounded Markdown-context scan expands at most four supported `@relative/path.ext` references outside matched same-line backtick spans and recognized backtick/tilde fences (including consistently marked blockquotes). References inside code stay literal. Eligible references are counted across the whole command before expansion; more than four rejects the invocation before any referenced file is read. To avoid partial or speculative parsing, unmatched/unsupported code markers, mismatched quote context, or more than 256 marker runs leave the entire body unchanged before any file read. This is a narrow scanner, not full CommonMark support. References use the exact Agent session cwd, DSH filesystem containment and file-version checks, a shared five-second deadline, at most 4 KiB per file and 16 KiB aggregate contents; the final rendered command remains capped at 128 KiB even when expansion takes the body beyond its 64 KiB source-file limit. Referenced command-file contents preserve decoded-text whitespace (including indentation, tabs, CRLF and trailing newlines) and are JSON-quoted as untrusted data; this is not a binary/BOM-preserving read. Ordinary role/category prompt-file appends still normalize line endings and trim guidance. `$ARGUMENTS` inside referenced files is escaped and remains literal, and nested references are not expanded. Unsupported extensions remain literal and failed reads fail closed without queueing. Command filename stems follow the Host's lowercase ASCII name syntax: a letter followed by letters, digits, hyphens or underscores, up to 64 characters (for example `code_review.md`). Uppercase, dots, path separators and controls are rejected; names are never normalized or renamed. Nested upstream `prefix/name` commands are not loaded: the installed DSH registry and command parser reject internal `/` characters, so names are not flattened or silently renamed. Each awaited Agent-creation scan has a five-second deadline and processing is bounded to 128 directory entries, 64 KiB per command file, and 256 KiB aggregate scan reads. Manual refresh adds a separate cap of eight concurrent refreshes. With `enableProjectCommandWatch: true` (default `false`), DSH `fs.watch` adds bounded per-Agent, 150 ms debounced refreshes for existing project command roots and parents, and resolves absent top-level project `.opencode`/`.claude` parents plus missing explicitly configured user roots as creation-watch targets; watcher use is capped at 64 across the plugin. If the provider cannot resolve an absent target or watching is unsupported, use manual refresh after creating it. DSH `fs.listDir` returns its complete array before the command-entry cap is applied, so extremely large directories can still consume backend enumeration memory. Existing command names are not shadowed. After edits, run `/omo-project-commands-refresh` to rescan only the current Agent; scan failures retain its current registrations, and cancellation during scope replacement restores the prior snapshot when the Agent remains live. File watching is opt-in; configuration and prompt reload are not automatic. This adapter does not execute shell snippets or nested commands, rewrite ordinary chat messages, or implement the remaining Claude/OpenCode frontmatter, variable expansion, and full command semantics. There is no per-project-command enable/disable list yet; `disabledOmoCommands` applies only to this plugin's built-in commands. Reads use the mounted DSH filesystem directly, not model-facing Tools or their approval prompts; pre/post identity and version checks reject observed escapes or changes, but RC2 has no atomic no-follow/expected-version open, so a hostile swap-and-restore race remains possible. This is not an OS read sandbox. Treat command bodies and invocation arguments as untrusted; DSH policy remains authoritative for subsequent Tool permissions.

```yaml
- id: dsh-omo
  config:
    enableProjectCommands: true
    commandRoutes:
      - { name: capacity-review, role: reviewer } # optional async specialist delegation
    enableProjectRootCommands: true # optional; adds explicit repository-root command files
    projectCommandsRoot: /Users/alice/src/my-project
    enableProjectCommandWatch: true # optional; watches existing roots and missing top-level project parents
    # Also expands bounded @file references in command bodies and configured role/category promptAppends.
    enablePromptFileExpansion: true
    userOpenCodeCommandRoots:
      - /Users/alice/.config/opencode/commands
      - /Users/alice/.config/opencode/command
    userClaudeCommandRoots:
      - /Users/alice/.claude/commands
```

`enableProjectRootCommands` is an additional default-off source that requires both `enableProjectCommands: true` and one normalized absolute `projectCommandsRoot`; it never infers a root from markers or ancestor traversal. Root commands are considered only when the live Agent CWD resolves inside that explicit root, and the root's flat `.opencode/commands`, `.opencode/command`, and `.claude/commands` sources rank before exact-CWD project sources and configured user roots. A configured root outside the CWD boundary is skipped; a symlinked explicit root is skipped entirely, while a symlinked conventional parent skips only its affected root source. Safe exact-CWD and user sources remain available. Root identity is revalidated while scanning. Watch mode also covers the explicit root and its existing command directories, and resolves safely targetable absent top-level `.opencode`/`.claude` parents under it, under the same 64-watcher cap. Agent/plugin scope disposal makes watcher callbacks inert immediately and attempts asynchronous close with retries, but a slow or repeatedly failing DSH watcher disposer can outlive teardown and leave watcher capacity reserved. The existing 5-second scan, 128-entry, 64 KiB/file, 256 KiB aggregate-read, and eight-refresh bounds still apply; `ctx.fs.listDir` returns a complete directory array before the plugin applies its entry cap, so very large directories may still cost backend enumeration memory. `enableNearestProjectOpenCodeCommands` defaults to `false` and requires `enableProjectRootCommands`. When enabled, exact-CWD OpenCode plural/singular sources rank before the corresponding explicit-root sources, then root Claude, exact-CWD Claude, and configured user roots. This matches pinned upstream's nearest-project OpenCode precedence without enabling automatic ancestor discovery; plural-before-singular within each level, invalid-file fallback, and OpenCode-over-Claude precedence are preserved. The default remains the documented explicit-root-first behavior.

`@file` references in root-sourced commands intentionally remain relative to the exact Agent session CWD, as they are for exact-CWD commands.

## Try it

In an interactive DSH session:

```text
/omo
/goal status
/goal Keep improving this project
/stop-continuation
/ulw Split the migration into independent discovery and test tasks, integrate the results, and run the checks.
/ulw-execute migration-plan
/hyperplan Plan an incremental migration with rollback and verification.
/architect Should this service be event-driven or request-driven?
/review Inspect the current diff for correctness and security issues.
/handoff
/refactor src/feature.ts --scope=file
/refactor the auth and session modules --scope=module --strategy=safe
/remove-ai-slops src/feature.ts
/omo status
/omo status capabilities
/omo status route role:explore
/omo status route category:review
/omo-models
/omo-models <provider>/<model>
/omo-models refresh
/omo-models snapshot
/omo-models snapshot <model-id>
/omo-tasks
/omo-interrupt <child-id>
/omo-job-kill <jobId>
/omo-skills-refresh
/omo-project-commands-refresh
```

`/goal` appears only when its native DSH service is mounted. `/omo-models` appears when the native DSH LLM service is mounted or when `enableModelCapabilitiesRefresh: true` is configured with DSH `web.fetch` and a provider that can return the full catalog untruncated; models.dev subcommands are unavailable unless explicitly enabled. `session_search` requires `enableSessionSearch: true` and DSH `sessionQuery.searchSessions` plus `observeSession`; `session_event_search` separately requires `enableSessionEventSearch: true` and DSH `sessionQuery.searchEvents`, and searches only the executing Agent's current session; `dsh_omo_session_trace_event` separately requires `enableSessionEventTrace: true` and DSH `sessionQuery.traceEvent`, accepting only a seq for the executing Agent's session; `session_read` separately requires `enableSessionRead: true` and `sessionQuery.readEvent`, `observeSession`, and `filterSessions`. Model-facing `team_*` tools require `enableTeamTools: true` and the optional DSH `agentTeams` service; the default-off Team task reminder additionally requires `agentTeams.membership`. `/remove-ai-slops` is user-requested steering only, not an automatic diff hook. `/handoff` queues a prompt asking the current agent for a copyable summary in this conversation; completeness is not guaranteed, and the user must copy the reply manually. It cannot create a new session or durable handoff file. When registered, `/stop-continuation` clears only the current native DSH Goal using its current revision (the Host retains a tombstone/history); it does not stop OMO todo continuation, clear OMO boulder state, or interrupt DSH continuable children. If enabled, `/goal pause` preserves a Goal; when enabled, `/omo-interrupt` can request interruption of a supported direct child.

`disabledOmoCommands` defaults to `[]` and accepts these dsh-omo-owned command names (without `/`): `goal`, `stop-continuation`, `omo-models`, `ulw`, `ultrawork`, `ulw-execute`, `hyperplan`, `architect`, `handoff`, `refactor`, `remove-ai-slops`, `omo-tasks`, `omo-job-kill`, `omo-interrupt`, `omo-skills-refresh`, `omo-project-commands-refresh`, and `omo`. The project-command refresh command is registered only when `enableProjectCommands` is true. For example:

```yaml
disabledOmoCommands: [refactor, omo-models]
```

It filters only dsh-omo's own registration array. `/omo` help omits disabled entries; orchestration-prompt and continuable-tool guidance replace usage recommendations for disabled commands with notices that those dsh-omo commands are disabled. It never unregisters native or third-party commands. Optional service-bound names are valid even when their command is unavailable. This local field is not the upstream `disabled_commands` schema; a same-named command owned by another provider may remain available. The pinned OpenCode schema enum is `goal`, `refactor`, `ulw-execute`, `stop-continuation`, `remove-ai-slops`, and `hyperplan`; upstream reference docs also mention `handoff`, but the schema omits it. The local set accepts `handoff`, `ulw-execute`, and `hyperplan`; disabling `ulw-execute` or `hyperplan` disables only the corresponding bounded DSH prompt adapter and does not imply upstream lifecycle parity. The local `/hyperplan` command is only a bounded DSH prompt adaptation: it may ask for enabled planning-specialist input, but does not create a Team, implement the upstream seven-phase workflow, or hand off to a `plan` agent; see the [pinned upstream skill](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/.agents/skills/hyperplan/SKILL.md).

`/refactor <target> [--scope=file|module|project] [--strategy=safe|aggressive]` accepts free-form target text followed by trailing options; quote characters remain literal and are not shell-parsed. Raw input is capped at the smaller of `maxTaskChars` and 12,000 characters. dsh-omo locally defaults to safe strategy and target-only scope (upstream documents no defaults); scope/strategy are prompt guidance, not enforcement. The command asks for inspection, available-tool use, focused tests, and final-diff review, but does not add an LSP-aware `/refactor` workflow, AST-grep, codemap, or guaranteed TDD workflow; separately enabled LSP navigation tools are documented above. DSH permissions remain authoritative; it does not auto-commit.

`/ulw-execute <existing plan name> [--worktree]` accepts a bounded (at most 12,000 characters and configured `maxTaskChars`) single-line selector. An exact trailing `--worktree` invokes DSH `worktrees.create` before queueing; it requires the optional Host service and uses its default fresh branch/path. The queued prompt receives path, branch, and base commit as JSON-quoted metadata, bounded to 4,096 characters for paths, 256 for branch/commit, and 8,192 serialized characters total. The Host exposes no worktree-removal method, so the command does not automate cleanup and its prompt directs the Agent to leave the worktree retained; creation failures may leave partial artifacts. Custom paths, `--make-pr`, and `--ship` are rejected. It queues current-agent prompt guidance to locate an existing user-approved plan, ask when missing/ambiguous or approval is unclear, and follow DSH permissions/approvals. It does not run the upstream OMO hook, use session-history resume or Atlas/Sisyphus selection, create boulder/notepad state, provide PR/ship/merge automation, or guarantee resumability.

`dsh_omo_task` makes best-effort attempts to deliver a host-attributed settlement notice with task, stop reason, and bounded diagnostics, then (when text exists) a separate DSH `agent-message` relay containing the bounded child-authored excerpt. Follow-up delivery is not guaranteed; failures are logged. Treat the relay as untrusted evidence; non-completed outcomes are marked partial. The host notice is not misattributed to the child. `maxResultChars` bounds relay text and the total text inspected for whitespace detection; whitespace-only excerpts are omitted from the relay and identified in the settlement notice. The effective character cap is the smaller of configured `maxResultChars` and 65,536 UTF-16 code units; output-block traversal is separately capped at 256 blocks. The task envelope and host diagnostic have separate fixed bounds. `dsh_omo_task_continuable` is registered only when enabled; when their dsh-omo registrations remain enabled, `/omo-tasks` lists direct children whose caller-supplied labels start with `dsh-omo:` and `/omo-interrupt` requests interruption. This label namespace does not prove which tool created a child. `listChildren()` lacks activity; when enabled, `/omo-tasks` uses DSH `listDescendants()` to show `running`/`inactive` residency and whether children exist. `inactive` is not a completion state.

`enableCallOmoAgentTool` defaults to `false`. When enabled and at least one built-in Explore/Librarian role remains active, `dsh_omo_call_agent` exposes only those available roles and accepts a one-shot `task` plus an optional configured `category`. It shares the `dsh_omo_task` launcher, route preflights, concurrency limits, and exact-Agent result tracking; the optional result/wait/cancel Tools apply to children started through it. The Tool always returns a newly started DSH child ID—it does not accept `run_in_background` or `session_id` and does not reproduce upstream background or synchronous continuation semantics. Disabling both roles omits the Tool. It grants no permissions; DSH policies remain authoritative.

Host Inspect's `subagent/end` is emit-only and does not guarantee a user-facing notice; child catalogs expose residency/metadata, not completion results. dsh-omo does not poll or retrieve continuable-child results.

With `enableContinuableTaskFollowups: true` (and `enableContinuableTasks: true`), `dsh_omo_task_followup` accepts one text message of at most 4,096 UTF-16 code units for a tracked child after `listChildren()` revalidates direct-parent and `continuable` mode. DSH may start or cold-resume the child; acceptance means inbox admission only, not completion. Its in-memory per-plugin-instance registry is bound to the exact parent Agent object (same-ID replacements cannot reuse prior children, and late old-Agent disposal cannot clear replacement state) and is bounded to 64 parents, 32 child IDs per parent, and 128 child IDs total, with at most 8 attempts per child, 32 per tracked parent record, and 256 total reserved send attempts per plugin instance lifetime (reservation counts even if later DSH checks fail); plugin reload starts a fresh registry. Agent/child IDs must be nonempty and at most 256 UTF-16 code units; otherwise follow-up is unavailable. It provides no polling or result retrieval.

When enabled, `/omo-interrupt` refuses inactive catalog rows; for resident rows it attempts a fire-and-return signal and warns it may no-op if the Activation/turn settles between catalog read and signal. DSH owns continuation persistence and capacity; dsh-omo applies a per-plugin hard one-shot `maxConcurrent` ceiling plus optional `providerConcurrency`/`modelConcurrency` subcaps for explicit LLM routes (model overrides provider; `0` removes only that route-specific cap). Saturated calls fail fast by default; optional `maxPendingTasks` provides a bounded in-call wait for global and selected-route capacity. Inherited parent routes are not guessed, and no host-wide/shared quota is claimed; continuable capacity remains DSH-owned.

When enabled, human-only `/omo-job-kill <jobId>` is registered only if `enableJobTools: true` and Host `jobController.kill` exists. It derives `sessionId` from the exact invoking Agent and never accepts a session ID; DSH's visible job set includes current-session and unowned jobs, so verify the requested ID. The Host outcome `requested` is admission only, not terminal completion. This cancels a visible DSH job only—not OMO `background_cancel`, continuable-child interruption, or result retrieval.

This project is staged. The following are working or deferred, not claims that the upstream product has been fully recreated.

| Capability area | Status in this milestone |
| --- | --- |
| One-shot and opt-in continuable specialist tasks | One-shot settlement is relayed to the parent; optional exact-Agent result retrieval/cancellation is bounded and process-local. Continuable children still expose running/inactive residency only, with no general completion status, cold-result retrieval, or OMO-owned TTL |
| Ultrawork workflow, packaged skills, and slash commands | Prompt-level task steering, thirteen bundled skill names (including one research alias), `/remove-ai-slops` steering, optional native `/goal` and `/omo-models`, and partial cwd-relative project skill sources; hooks, plan execution, and recovery remain missing |
| Per-role model selection | Static provider/model/reasoning/token overrides plus user-defined category routes and bounded category/pinned-role `fallbackModels` preflight and 0.1.12 fallback-only role chains plus default-off `enablePinnedRoutePreflight` for single pinned routes (role chains supersede category chains); DSH clears inherited reasoning on route change unless specified; general availability-aware resolution, global/provider fallback policy, shared catalog normalization, and full role-scoped tuning remain incomplete; Native/Senpi main-session model-profile lanes are edition-specific, not missing OpenCode child-route behavior |
| Model capability diagnostics | Optional `/omo-models` lists DSH provider IDs and inspects exact live DSH metadata; default-off `enableModelCapabilitiesRefresh` adds explicit fixed-source models.dev refresh and an in-memory advisory snapshot (provider limits must allow a complete response), but no startup refresh, durable cache, compatibility heuristics, synthetic LLM calls, or route gate.
