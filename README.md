# dsh-omo — Oh My DSH-style orchestration

An independent DeepSeek Harness plugin that brings an Oh My OpenCode-inspired specialist workflow to DSH. It is being implemented against the installed DSH `0.2.0-rc.2` APIs; it does **not** install or depend on the incompatible `dsh-autopilot` alpha. No Oh My OpenCode source code is copied. This is an early-stage compatibility layer, not a claim of complete 1:1 feature parity or affiliation with either project.

## First milestone

- Adds `dsh_omo_task`, a bounded one-shot launcher with automatic parent follow-up, and an opt-in `dsh_omo_task_continuable` tool backed by DSH durable child sessions. Specialist roles include `explore`, `librarian`, `architect`, `plan-consultant`, `plan-reviewer`, `ultrabrain`, `quick`, `visual`, `reviewer`, `test`, and `security`.
- Adds role personas, opt-in per-role model routes, reasoning effort and token ceilings, inherited tool-scope allow/deny filters, and bounded literal `promptAppend` guidance in delegated task messages.
- Adds twelve packaged workflow skills: four `/omo-*` skills plus `debugging`, `frontend`, `git-master`, `init-deep`, `remove-ai-slops`, `review-work`, `security-research`, and `visual-qa`; these guides do not reproduce upstream lifecycle integrations.
- Adds a cwd-aware provider for project `.opencode/skills` and `.claude/skills` files through DSH skill/filesystem services.
- Adds `/omo-skills-refresh` to invalidate the project-skill catalog after local edits; filesystem watchers normally refresh it automatically.
- Adds persistent system-prompt guidance for task decomposition, parallel delegation, integration, and verification.
- Adds `/ulw`, `/ultrawork`, `/ulw-execute`, `/architect`, `/review`, `/handoff`, `/refactor`, `/remove-ai-slops`, `/omo` (including `/omo status`), `/omo-tasks`, `/omo-interrupt`, and `/omo-skills-refresh`; `/goal` and read-only `/omo-models` are registered when their optional native DSH services are available. `/stop-continuation` is registered only when the native DSH Goal service exposes `get` and `clear`. Task commands still report DSH residency/interrupt attempts, not plugin origin or guaranteed completion.
- `/ulw-execute <existing plan name>` asks the current agent to locate and follow an existing approved project plan, asking if missing or ambiguous. It is prompt-only: no OMO hook/session-history resume, Atlas/Sisyphus selection, boulder/notepad state, worktree, PR, shipping, or merge lifecycle; `--worktree`, `--make-pr`, and `--ship` are rejected.
- Adds opt-in native Agent Teams tools (`enableTeamTools: true`) when the DSH `agentTeams` service exists; DSH remains authoritative for Team membership, permissions, persistence, messages, and task revisions.
- Adds user-configured category-to-single-route delegation via `categoryRoutes` and optional `category` arguments; categories select provider/model/reasoning plus an optional `maxTokens` ceiling; disabled routes are excluded from task choices; optional descriptions appear in task-tool metadata; category `tools: false` entries add partial inherited-tool denies; `promptAppend` adds bounded task-message guidance (not a system prompt). Categories are not personas, fallback chains, or a built-in upstream registry.
- Adds on-demand `/omo-models` diagnostics over registered DSH providers and exact model metadata. It does not query models unless the user names a `provider/model`, and it is not the upstream `models.dev` cache/refresh system.
- `/omo status` reports dsh-omo feature flags and optional-service presence observed during plugin setup only; it does not call business Service methods, query models, read session content, or claim runtime health/readiness.
- Adds opt-in, read-only `lsp_goto_definition` and `lsp_find_references` adapters when DSH `lsp.query`, `sessions.get`, and filesystem canonicalization methods are available; input paths are canonicalized and checked against the invoking Agent cwd (not a race-free OS sandbox), while provider-returned URIs are untrusted metadata and may identify files outside that cwd.
- Adds optional `enableRootAgentsContext` to snapshot bounded cwd-level `AGENTS.md` into each new Agent's DSH `systemPrompt.context()` scope at awaited `agent/created`, before its first step; it is root-only, untrusted repository text, and has no file watcher.
- Adds separate opt-in `enableRootReadmeContext` to snapshot only the cwd-root `README.md` into the Agent prompt before its first step; unlike upstream OMO's post-`read` output mutation and root-to-nested README walk, this is a bounded DSH creation-time snapshot with no backfill or watcher.
- Adds independent opt-in `enableReadmeOnRead` to enrich successful DSH `read` calls with bounded root-to-nested README contexts. It uses DSH `tools/post-execute` `additionalContexts` so the native read value/content stays intact; this is a separate user message, and only safe relative or in-cwd POSIX absolute `file_path` values are supported.
- Adds default-off `enableClaudeRulesOnRead` to scan only cwd-root `.claude/rules` Markdown (`.md`/`.mdc`) files after successful `read`, `write`, and `edit` calls and append matching rule contexts through `additionalContexts`; the legacy flag name is retained, no verified `multiedit` schema is available to this adapter, and this remains a root-only partial adapter with no ancestor/project-root or home/global rule discovery or native Tool-result mutation.
- Adds opt-in read-only `session_search` (`enableSessionSearch: true`) when DSH `sessionQuery` is available. Search defaults to the current Agent session cwd; cross-project search requires `includeOtherProjects: true`. Results are bounded snippets, not log bodies; a cold workspace observation or search indexing may still do full-session work internally, and index completeness is backend-dependent.
- Adds separately opt-in `session_read` (`enableSessionRead: true`) for one DSH `readEvent` window. It defaults to the current workspace and target-only reads, caps explicitly requested context to four events on either side (subject to any stricter Host limit), and returns only bounded direct-user/model-assistant text, omitting synthetic user-role context, system/developer content, reasoning, tool calls/results, and attachments; it does not expose a full session or resume it, though RC2 `readEvent` loads/snapshots the complete target log before slicing the bounded response window (live sources snapshot all events; persisted sources read/reconstruct the full log); a cold current-Agent workspace observation may also prepare that Agent's full log.
- Adds separately opt-in `session_list` (`enableSessionList: true`) for bounded metadata-only listing. It defaults to the current workspace, supports inclusive date bounds, caps output at 25 records, and has no stable page cursor; the Host materializes the complete logical corpus before filtering. Though results are metadata-only, a cold current-Agent workspace observation may prepare that Agent's full event log.
- Adds separately opt-in `session_info` (`enableSessionInfo: true`) for one session's allowlisted header and optional bounded title. Title lookup snapshots/scans the entire live target log or reads/reconstructs the complete persisted target log on every call; it returns no event text or message statistics. Default scope is the current workspace; global scope is only a model-supplied selector, not authorization.
- Adds optional DSH Host job monitoring (`enableJobTools: true`) through `dsh_omo_job_list` and `dsh_omo_job_follow`. It defaults off, derives the service owner from the current Agent, caps streams/output, drops `JobView.detail` and `output.spillPaths`, and exposes no model-facing kill Tool. With the same opt-in and a Host `jobController.kill` method, the separate human-only `/omo-job-kill` command can request cancellation. This does not implement OMO `background_output`, `background_cancel`, or subagent-result retrieval.
- Adds `/remove-ai-slops` steering that reuses the bundled workflow skill; it is not an automatic diff hook or enforcement boundary.
- Adds project skills as a source in the DSH skill registry. Provider reads use `ctx.fs`, cwd containment, file-version checks, and a post-read path revalidation—not model-facing filesystem tools or their approval prompts; DSH remains authoritative for normal tool mutations, shell/network access, and approvals.

A role prompt and `allowTools`/`denyTools` filters are not a hard security boundary. In DSH RC2, the subagent tool filter affects inherited global and ancestor-scope tools; the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport may still be visible. For must-be-read-only work, verify that DSH-native permissions, sandbox policy, or tool guards cover every visible tool, including scoped registrations and the reserved transport; dsh-omo does not install a per-worker hard guard. Project-skill provider reads do not pass through model-facing tool approval or mutation-sandbox checks; they use the mounted DSH filesystem backend, cwd containment, version checks, and post-read path revalidation. The RC2 filesystem contract has no atomic no-follow open, so an adversarial concurrent swap-and-restore could still evade path checks; this is not a race-free OS read sandbox. Treat repository skill content as untrusted and do not use it to expose secrets.

## Install in an isolated profile

Build a local package tarball, then add it to a dedicated profile:

```sh
cd oh-my-dsh
pnpm install
pnpm run check
pnpm pack --pack-destination .artifacts

# Create/seed the isolated audit profile from the shipped web template, then add the tarball.
dsh --profile ohmy-test --from-default-profile web --dump-config
dsh plugin --profile ohmy-test add "$(pwd)/.artifacts/dsh-omo-0.1.9.tgz"
dsh --profile ohmy-test --dump-config
```

The user-facing app should be restarted after adding the package. Test the isolated profile first; only add it to `desktop` after reviewing the effective configuration.

## Configure roles

The package installs a bundle row in `cordis.patch.yml`. Add entries to `roleRoutes` for provider/model, reasoning, token ceilings, inherited tool-scope filters (`allowTools`/`denyTools`, at most 64 names of up to 128 UTF-8 bytes each), and bounded literal `promptAppend` guidance. For one-shot launches that emit a filter, the DSH subagent provider must advertise `toolFilter`; DSH rejects unsupported filters before publishing a child. Continuable tasks apply the filter through DSH's scoped `tools.restrict` path and do not require that provider capability flag. `enableContinuableTasks` defaults to `false`; turn it on only after verifying the selected DSH subagent provider implements the optional `prepareContinuable` method and the DSH persistence path is available. Optional DSH-native `userAgents` definitions require `name` and `prompt`, accept optional `description` and `mode` (omitted `mode` defaults to `subagent`), and add up to 32 config-only named subagents. Names are ASCII slugs of at most 64 characters, descriptions are limited to 512 UTF-8 bytes, and raw persona prompts are limited to 16 KiB each (64 KiB total). Only `mode: subagent` is supported. The prompt is passed as DSH `SubagentStartRequest.persona`, so a custom role fails closed unless the selected DSH subagent provider advertises `persona`; use `roleRoutes`/`categoryRoutes` for model and inherited-tool routing, and `disabledOmoRoles` may disable built-in or custom names. dsh-omo has no `.md`, `.json`, or `.jsonc` agent-file loader or project/global source merge; these definitions cannot switch the current/primary agent or appear in a Host-native agent picker. The existing role/filter warning above applies to them as well.

```yaml
- id: dsh-omo
  name: dsh-omo
  config:
    provider: spawn
    # The DSH subagent provider in `config.provider` (`spawn` here) must advertise `persona` for docs-auditor,
    # `toolFilter` for one-shot filters, and `agentOptions` for routed child options below.
    maxConcurrent: 4
    maxDepth: 1
    maxTaskChars: 12000
    maxResultChars: 8000
    enableContinuableTasks: false
    enableTeamTools: false
    enableSessionSearch: false
    enableSessionRead: false
    enableSessionList: false
    enableSessionInfo: false
    enableJobTools: false
    enableLspTools: false
    enableRootAgentsContext: false
    enableRootReadmeContext: false
    enableReadmeOnRead: false
    enableClaudeRulesOnRead: false
    userAgents:
      - name: docs-auditor
        description: Review repository documentation.
        prompt: |-
          Audit documentation for stale claims and missing setup details.
          Report concrete, actionable findings.
        mode: subagent
    # Route `provider` fields below select LLM model providers, not `config.provider` (the DSH subagent provider).
    categoryRoutes:
      - name: research
        provider: deepseek-official
        model: deepseek-flash
        reasoningEffort: medium
        maxTokens: 2048
        description: Research with cited sources
    roleRoutes:
      - role: explore
        category: research
        allowTools: [read, glob, grep, web_search, web_fetch]
      - role: docs-auditor
        category: research
        allowTools: [read, grep, web_search, web_fetch]
      - role: reviewer
        provider: deepseek-official
        model: deepseek-flash
        reasoningEffort: medium
        maxTokens: 4096
        promptAppend: |-
          Cite one supporting file or source for each finding.
        denyTools: [bash]
```

`enableTeamTools` defaults to `false`; opt in only when the optional DSH `agentTeams` service is present. It exposes eleven Host-backed `team_*` tools, including read-only `team_status` for the caller’s current Team only; that snapshot combines membership, up to 100 visible members, and up to 100 tasks, with explicit truncation flags and a 48,000-character aggregate cap. This is not exact upstream 12-tool parity: global Team listing, whole-Team create/delete/shutdown operations, including shutdown approval flows, worktrees, and tmux lifecycle remain unavailable. An `inactive` member is not reported as completed; task `writeScopes` remain advisory and DSH owns authorization and shared state. `enableSessionSearch` also defaults to `false` and requires DSH `sessionQuery.searchSessions` plus `observeSession`; the read-only tool derives the current Agent cwd from a projection-free observation and uses the DSH `sessionFilters: [{ kind: 'cwd', values: [...] }]` contract by default. `includeOtherProjects: true` deliberately removes that filter; the flag is model-supplied, not proof of user consent/authorization or an enforcement boundary; configure DSH tool permissions separately. It bounds results to 20 hits with 600-character snippets, forwards cancellation, returns a cursor for pagination, and does not request full log output or mutate sessions; a cold workspace observation or search indexing may still do full-session work internally. DSH owns search indexing/reconciliation, so completeness and backend availability are not guaranteed. `enableSessionRead` separately defaults to `false` and requires `sessionQuery.readEvent`, `observeSession`, and `filterSessions`. It validates the selected session against the current cwd before reading, defaults to zero neighboring events and allows at most four on either side (the Host may be stricter), and projects only bounded `text` blocks from direct user (`source.kind: 'user'`) and model assistant messages; synthetic user-role context, system/developer messages, reasoning, tool calls/results, and non-text blocks are omitted. It never calls `readSession` or resumes a session; output is bounded, but RC2 `readEvent` loads/snapshots the complete target log before slicing the requested window; a cold current-Agent workspace observation may also prepare that Agent's full log. Historical text is marked untrusted. `includeOtherProjects: true` is model-supplied, not proof of user consent or authorization; use it only after an explicit user request; it does not enforce consent, so configure DSH tool permissions separately. `enableSessionList` separately defaults to `false` and requires `sessionQuery.listSessions`, `filterSessions`, and `observeSession`. It uses the current Agent cwd by default, fails closed if cwd is unavailable, and accepts optional inclusive `fromDate`/`toDate` bounds; output is metadata-only and capped at 25 records. The Host materializes the complete logical corpus before filtering and provides no stable cursor, so a truncated result must be narrowed by workspace or date. Global scope uses the same model-supplied `includeOtherProjects: true` selector; set it only after an explicit user request, since the flag does not enforce consent/authorization. `/goal` is registered only when the native DSH Goals service is available; Goal persistence and continuation remain Host-owned. `/omo-models` is registered only when DSH LLM metadata is available; it lists up to 100 provider rows and resolves a named `provider/model` on demand (lookup scans at most 1,024 provider entries, then reports indeterminate). The command returns on caller cancellation or a 15-second timeout and passes that signal to the adapter; an adapter that ignores cancellation may continue its own work. This is diagnostic metadata, not model validation for child launch or a model request.

`enableLspTools` defaults to `false` and requires DSH `lsp.query`, `sessions.get`, and `fs.resolve`/`contains`/`processPath`. It exposes only the read-only definition and references aliases; the input is a relative path resolved against the invoking Agent session cwd and checked with canonical DSH filesystem containment before the query; this is not a race-free OS sandbox. Provider queries may inspect dependencies, and returned file URIs are untrusted metadata that may be outside the cwd; results are never followed or read by this adapter and do not grant access. Only `file:` result URIs are accepted; non-file schemes are rejected. The response caps locations at 50 and serialized data at 24,000 bytes and forwards cancellation. Upstream defaults `includeDeclaration` to true, but DSH exposes no such control: provider behavior is unverified, `false` cannot be honored and is rejected, and `true` is not guaranteed. The adapter uses the session cwd as `workspaceRoot`; whether providers expect that or the project root is unverified. The adapter assumes standard zero-based LSP positions when converting the upstream 1-based line; Inspect does not specify DSH indexing, and this conversion has not been tested with a live provider. Seven other upstream LSP tools remain missing: status, diagnostics, symbols, prepare_rename, rename, format, and install decisions. No live LSP provider was verified in the current target profile; service presence alone is not provider health. Configure DSH permissions separately for any later file access.\n\n`enableRootAgentsContext` defaults to `false`. When enabled, for each awaited DSH `agent/created` event (`startup`, `resume`, `clear`, or `compact`) while the hook is registered, it checks only that Agent session cwd's `AGENTS.md`; an eligible file is registered through that Agent's `systemPrompt.context()` scope before creation resolves and queued input proceeds. Missing, invalid, or otherwise rejected files produce no context. This is a DSH creation-time snapshot, not upstream OMO's post-`read` result injection; no read Tool result is modified. The file must be regular, canonically contained beneath the session cwd, at most 16 KiB with a five-second total filesystem-read deadline (a backend that ignores cancellation may continue underlying I/O after the event returns), and valid UTF-8; control/bidi characters are replaced, repeated brace runs are rendered as full-width braces to disable DSH prompt-variable interpolation, and the content is marked untrusted. Agent-scope teardown and plugin unload remove the registration. The hook does not backfill already-live Agents; each qualifying creation receives a snapshot, with no file watcher or same-Agent refresh. After reading, the adapter rechecks `lstat`, containment, stable `targetKey` and `stat` plus available size/version metadata, which detects many changes; DSH has no atomic no-follow open, so a concurrent swap/restore remains a TOCTOU risk, not an authorization boundary. The feature is root-only: ancestor/nested `AGENTS.md`, README, `.claude/rules` globs/frontmatter, dedicated compaction-context injection, and mode/skill injection parity remain missing. Transient filesystem errors/cancellation skip the current Agent; a later Agent creation may retry; a filesystem backend that ignores cancellation can continue underlying I/O after the Agent event returns. Repository instructions are untrusted and do not grant tool or filesystem permissions. Enabling this option explicitly authorizes plugin-side `ctx.fs.readBytes` access during Agent setup; it is not a model-facing Tool call, so do not assume Tool approval prompts gate it. Host filesystem-service policy remains authoritative.

`enableRootReadmeContext` defaults to `false` and is independent of `enableRootAgentsContext`. When enabled, each awaited DSH `agent/created` event (`startup`, `resume`, `clear`, or `compact`) snapshots only that session cwd's root `README.md` through the live Agent's `systemPrompt.context()` before creation resolves. The eligible file must be a regular non-symlink file contained in cwd, valid UTF-8, and at most 32 KiB of source bytes; repeated-brace escaping can expand rendered text to roughly 96 KiB plus its fixed wrapper. Oversized or invalid files are skipped rather than truncated. The bounded filesystem pipeline has a five-second per-file deadline; when both root-context flags are enabled, their serial listeners can together delay Agent creation by up to roughly ten seconds for stalled reads. It rechecks `lstat`/containment/stable `targetKey`/`stat` and available size/version metadata, replaces disallowed control/Bidi characters with `?`, and full-width-escapes repeated braces. Enabling this option authorizes plugin-side DSH filesystem reads, not a model-facing Tool call or separate Tool-approval gate; content remains untrusted and grants no permissions. This is a DSH creation-time snapshot, not upstream OMO's post-read result mutation: it includes no ancestor/nested READMEs, does not backfill existing Agents, and has no watcher or same-Agent refresh, so edits remain stale for that Agent (a later Agent creation can see changes). A filesystem backend that ignores its abort signal may continue underlying I/O after the event returns.

`enableReadmeOnRead` defaults to `false` and is independent of the creation-time root snapshot. After a successful DSH `read` Tool call, its awaited `tools/post-execute` listener reads `README.md` from the cwd root through the requested file's ancestors (the rootward first eight directories, root-to-nested) and adds bounded context through DSH `additionalContexts`; the original Tool result `value` and `content` remain unchanged, and the README arrives as a separate user message for the next model step. It accepts only safe relative POSIX or in-cwd POSIX absolute `file_path` values; out-of-cwd absolute paths, `.`/`..` segments, backslashes, Windows/URI schemes, and unsupported provider path forms are skipped. Each file is capped at 16 KiB and total source bytes at 32 KiB, with a five-second filesystem deadline, strict UTF-8, disallowed control/Bidi replacement while preserving LF/CR/tab, brace escaping (up to roughly 96 KiB rendered text plus wrappers), and post-read identity/containment checks. Directory dedupe is bounded to 256 cached directories per live Agent and resets on clear/compact Agent creation; this is in-memory only, not persisted across Agent recreation or plugin restart. Clear/compact generation changes fence stale context/dedupe commits but do not abort in-flight filesystem operations; a backend that ignores its abort signal may continue underlying I/O after the five-second waiter returns. If `enableRootReadmeContext` is also enabled, the post-read adapter unconditionally skips the cwd-root README to avoid duplicating its snapshot—even if that snapshot was absent/failed or the Agent was not backfilled—so there is no post-read root fallback. As with the snapshot, these are plugin-side filesystem reads, not model Tool calls or a Tool-approval gate; README text is untrusted, no dynamic truncation is provided, and DSH's opaque path semantics mean this remains a partial adapter rather than exact upstream parity.

`enableClaudeRulesOnRead` defaults to `false` and is independent of both README options. After successful DSH `read`, `write`, and `edit` Tool calls, it scans only `<session cwd>/.claude/rules/**` (root-first) for regular `.md`/`.mdc` files; it uses the validated scalar `exec.arguments.file_path` from those known schemas (cross-checking `exec.schema` when present) rather than rendered Tool output, and prunes `node_modules`, `.git`, `dist`, `build`, `.turbo`, `.next`, and `coverage` subtrees; it does not search ancestor project roots, home/global or other OMO rule directories. No verified `multiedit` schema is available to this adapter, so multi-edit calls are not adapted or guessed; the existing flag name is retained for compatibility. Its bounded frontmatter parser supports `alwaysApply`, `globs`, `paths`, and `applyTo`, merges repeated glob aliases, ignores unknown metadata (including `mode`), and normalizes backslash separators; Picomatch 4.0.7 with dot/Bash options matches both the cwd-relative POSIX target path and basename; `alwaysApply: true` matches unconditionally, otherwise a matching negated pattern excludes the rule and no positive patterns means no match. Matching rules are separate `additionalContexts` user messages, preserving native Tool `value/content`. It caps traversal at depth 8/32 directories/256 processed entries, 8 injected rules, 16 KiB per file/32 KiB aggregate raw bytes, and a five-second filesystem deadline; `listDir` may still materialize a full direct listing before the adapter enforces its processing cap. Scan/byte/deadline caps are per file-operation invocation, not per Agent; simultaneous operations may each run an independent bounded scan. Files are strict UTF-8, disallowed controls/Bidi are replaced while LF/CR/tab are preserved, repeated braces are escaped, wrapper metadata brackets are full-width encoded and Unicode line separators are escaped, and targets are revalidated after reads. DSH has no atomic no-follow read, so these checks cannot prevent a concurrent swap-and-restore race and are not a hard security boundary. A scan-limit or filesystem failure skips this injection pass; malformed individual rules are skipped, and no dynamic truncation is provided. Dedupe is bounded to 256 target/content entries per live Agent and resets on clear/compact; it is in-memory only, without transcript hydration, persistence, or a watcher. The cache commits when this listener returns an enriched decision: an earlier outer `tools/post-execute` listener can still block/replace it or drop `additionalContexts`, so a rule may be marked injected even though the final Tool decision did not deliver that context.

Changed rule content may be injected on a later read, but prior context remains in session history. Clear/compact fences stale commits but does not abort in-flight FS work; a backend ignoring its abort signal may continue I/O after the five-second waiter returns. These are plugin-side FS reads, not Tool-approval gated; rule text remains untrusted. This is a cwd-root-scoped, non-mutating partial adapter, not upstream rule discovery or lifecycle parity.

`categoryRoutes` is an explicit dsh-omo user-configured (custom-only) single-route table (up to 32 names, each at most 64 characters), not an upstream built-in category registry: a task may choose a configured `category`, or `roleRoutes.category` may set that role's default. Optional `description` is a single line capped at 512 UTF-8 bytes before trimming and appears as `name: description` entries in the one-shot/continuable task-tool description for enabled categories only; it is chooser metadata, not a child prompt or policy. Optional `disable` defaults to `false`; `disable: true` hides a configured route from tool choices and rejects explicit selection; role defaults to disabled routes fail configuration because they implicitly select that category; disabled entries still require provider/model. A category selects provider/model plus optional `reasoningEffort` and dsh-omo's camelCase `maxTokens` field (not upstream's canonical `max_tokens`); dsh-omo validates it as a positive safe integer. Explicit role provider/model/reasoning/token settings take precedence, while the specialist role controls the prompt. Category `tools` accepts at most 64 boolean tool-name rules (each name at most 128 UTF-8 bytes); only `false` maps to a DSH deny filter and `true` is a no-op (upstream `tools` maps true to allow and false to deny). Category denies are unioned with role denies and removed from role allow-lists, so category denies win over role allows here; upstream role restrictions may override category entries, making this adapter intentionally monotonic/stricter. As with role filters, DSH restricts inherited global/ancestor-scope tools only; child-scoped registrations and reserved PTC `run_code` may remain. One-shot filters require the selected DSH subagent provider's `toolFilter` capability; continuable tasks use DSH's scoped `tools.restrict`; this is not full upstream permission-policy parity. Category `promptAppend` remains task-message guidance, not a child system-prompt append. Category `maxTokens` maps to DSH `agentOptions.maxTokens`; the selected DSH subagent provider must advertise `SubagentCapabilities.agentOptions`. This is an output-token ceiling, not upstream `max_prompt_tokens` prompt-budget control, which is not implemented. No category/model fallback chain is implemented, and missing routes still inherit the parent/session model. Shared slash-task steering commands reject raw input longer than `maxTaskChars` before queueing it to the current agent.

`roleRoutes.promptAppend` and `categoryRoutes.promptAppend` are literal UTF-8 strings capped at 4,096 bytes each before trimming; whitespace-only values within the cap are ignored. dsh-omo rejects disallowed C0/C1 controls (tab and line breaks are allowed); `file://`, relative-path, home-path, and network references remain literal text; the adapter never resolves or reads them. For a selected category (explicit category before role default), its text appears in an “Additional category guidance” section, followed by any “Additional role guidance”; the two append payloads together are at most 8,192 bytes. This task-message composition is dsh-omo’s partial adapter for upstream category `prompt_append`, which appends to the system prompt; DSH exposes no per-child system-prompt append field here, so this does not change/replace the provider’s system prompt or grant an enforcement boundary. The chosen category-before-role section order is an adapter rule, not an upstream category-vs-agent system-prompt ordering guarantee.

`provider` and `model` must be set together when overriding the route; role `reasoningEffort` and positive-safe-integer `maxTokens` may be configured alone and ordinarily merge over the parent route. Category and role `maxTokens` pass through DSH `agentOptions`; `subagents.start` rejects options unsupported by the selected DSH subagent provider before delegation. If provider/model changes without an explicit `reasoningEffort`, inherited effort is cleared so the new model can use its default; do not generalize this to other omitted options. dsh-omo does not preflight category/role routes; DSH may accept the child session and reject an unavailable provider/model/reasoning choice on its first model request. `/omo-models` reports advisory metadata and does not reserve or validate a future route. `allowTools` and `denyTools` are DSH filters over tools inherited from the global and ancestor scopes; restrictions intersect, the child's own scoped registrations remain visible, and these are not hard permission boundaries. An explicit `allowTools: []` is preserved and hides all tools inherited from the global and ancestor scopes, but the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport may remain; it is not a hard deny-all. Empty `denyTools` is a no-op and is omitted. DSH's retry policy covers same-route request retries; OMO-style cross-model fallback chains are not implemented. `maxConcurrent` limits this plugin's active one-shot runs; DSH owns the separate continuable-session capacity. A parent's `maxTokens` can be inherited at child creation, but RC2 continuable descriptors/cold resume do not persist it; dsh-omo rejects continuable launch if a role/category route or parent has `maxTokens`. DSH workers inherit the parent workspace; this plugin does not promise a separate child `cwd`.

`disabledOmoRoles` defaults to `[]` and accepts exact dsh-omo built-in specialist names or names declared in `userAgents`; for example, `disabledOmoRoles: [architect, reviewer]`. It removes those roles from dsh-omo's one-shot/continuable tool choices and descriptions, orchestration guidance, and `/omo` help. Calls and `roleRoutes` entries targeting a disabled role fail closed, and at least one role must remain enabled. This local selector does not deregister Host/native/third-party agents and does not disable a same-named slash command (for example, `/architect`); it is not upstream per-agent `disable` behavior or OpenCode's global `disabled_agents` setting.

## DSH Host job monitoring

`enableJobTools` defaults to `false`. Set it to `true` only when the optional Host `jobController.list` and `jobController.follow` methods are available:

```yaml
enableJobTools: true
```

`dsh_omo_job_list` reads only the initial rows snapshot from the infinite stream, then closes it; output is capped at 50 jobs (25 by default) and 48,000 bytes after serialization/rendering. `dsh_omo_job_follow` derives its owner session from the current `exec.agent.id` (never a model-supplied `sessionId`), accepts an optional absolute byte offset `from`, and bounds each call to 8 seconds, 32 frames, 16 KiB of UTF-8 output, and 48,000 serialized/rendered bytes. It preserves absolute cursors and `lossy`/`gapBefore` indicators while projecting an explicit allowlist; `JobView.detail` and `output.spillPaths` are omitted. These model-facing tools do not expose or call `jobController.kill`; when `enableJobTools` is on and the Host method exists, only the separate human command `/omo-job-kill` calls it. Native DSH job-control tools are separate and remain governed by Host policy. Job kinds, labels, and log output are untrusted data. The model-facing tools provide DSH job monitoring only; they do not implement OMO `background_output`, `background_cancel`, or background subagent-result retrieval.

## Project skills

The DSH skill registry now discovers project-local skills relative to each skill lookup's `cwd`. Defaults are `.opencode/skills` and `.claude/skills`; each root accepts `<name>/SKILL.md` bundles and top-level `<name>.md` files. Skills need YAML `name` and `description`; optional `whenToUse` becomes top-level routing guidance, while `disable-model-invocation` and `user-invocable` map to DSH invocation flags. Other JSON-compatible frontmatter (including upstream `agent`, `model`, `tools`, or `mcp` fields) is preserved as metadata up to 12 levels deep; YAML aliases are rejected. These fields are not enforced: dsh-omo does not execute embedded MCP or bind the skill to an agent, toolset, or model.

```yaml
- id: dsh-omo
  config:
    projectSkillDirs: [.opencode/skills, .claude/skills]
    enabledProjectSkills: [incident-response]
    disabledProjectSkills: [retired-project-skill]
    disabledOmoBundledSkills: [omo-code-review]
    disabledSkills: [legacy-skill]
```

`enabledProjectSkills` is an optional exact-name allowlist of up to 256 distinct valid names for dsh-omo's project-skill provider: when omitted or set to `null`, all discovered project skills are visible; `[]` exposes none. It is a narrow local adapter for upstream [`skills.enable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills), which filters config-sourced skills; the local field filters only project-provider candidates; bundled, native, and other-provider registrations are not filtered by it, so a same-name entry may remain visible. `disabledProjectSkills` is an optional denylist of up to 256 distinct valid names for that same provider, adapting upstream [`skills.disable`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills); if both project lists contain a name, the denylist wins. Excluded project entries can reveal lower-priority same-name skills from another provider. `disabledOmoBundledSkills` hides exact dsh-omo bundled-skill names only, adapting upstream [`disabled_skills`](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#skills) narrowly; names outside this package's bundled set are rejected, and DSH-native/other-provider registrations are not filtered; a same-name entry may remain visible. If a name appears in both this field and `disabledSkills`, hiding wins. Unlike these visibility filters, `disabledSkills` keeps matching bundled/project entries visible while disabling model and user invocation. The provider still scans and parses project skill files to read their frontmatter names, so these filters are not a scan-cost reduction or filesystem security boundary. When a project skill is both enabled and listed in `disabledSkills`, it remains visible but non-invocable.

`disabledSkills` sets model and user invocation to false only on dsh-omo's bundled/project entries; it does not alter another provider's flags. Disabled entries remain registered, so a lower-priority same-name external skill may still be shadowed by the DSH registry's single-winner resolution. `projectSkillDirs` must be relative to the lookup cwd and cannot contain `..`; only canonical targets under that cwd are accepted, and symlinks resolving outside the configured root are skipped. Reads go through DSH `ctx.fs.readBytes` with a 256 KiB per-file cap; each catalog scan also caps processing at 512 directory entries, 256 accepted skills, and 8 MiB of skill text. `ctx.fs.listDir` returns a complete entry array before the plugin applies its scan cap, so extremely large directories may still cost backend enumeration memory. Reads do not pass through tool-level permission/approval prompts or the mutation sandbox. Reads compare DSH file versions and revalidate the final path after reading, but RC2 exposes no atomic no-follow open; a hostile swap-and-restore race is still possible, so this is not an OS read sandbox or race-free directory-handle boundary. Treat repository-provided skill text as untrusted instructions. Within dsh-omo roots, earlier configured paths rank first; all up to 16 configured roots rank ahead of dsh-omo runtime/bundled skills but remain below higher-priority DSH project sources. Filesystem watchers monitor symlink parents and canonical skill paths when available; if watch setup fails the catalog remains uncached, and `/omo-skills-refresh` can request another scan. User-global and remote skill sources, full OMO priority/config rules, intent activation, and skill-embedded MCP lifecycle remain unsupported.

## Try it

In an interactive DSH session:

```text
/omo
/goal status
/goal Keep improving this project
/stop-continuation
/ulw Split the migration into independent discovery and test tasks, integrate the results, and run the checks.
/ulw-execute migration-plan
/architect Should this service be event-driven or request-driven?
/review Inspect the current diff for correctness and security issues.
/handoff
/refactor src/feature.ts --scope=file
/refactor the auth and session modules --scope=module --strategy=safe
/remove-ai-slops src/feature.ts
/omo status
/omo-models
/omo-models <provider>/<model>
/omo-tasks
/omo-interrupt <child-id>
/omo-job-kill <jobId>
/omo-skills-refresh
```

`/goal` and `/omo-models` appear only when their native DSH services are mounted. `session_search` requires `enableSessionSearch: true` and DSH `sessionQuery.searchSessions` plus `observeSession`; `session_read` separately requires `enableSessionRead: true` and `sessionQuery.readEvent`, `observeSession`, and `filterSessions`. Model-facing `team_*` tools require `enableTeamTools: true` and the optional DSH `agentTeams` service. `/remove-ai-slops` is user-requested steering only, not an automatic diff hook. `/handoff` queues a prompt asking the current agent for a copyable summary in this conversation; completeness is not guaranteed, and the user must copy the reply manually. It cannot create a new session or durable handoff file. When registered, `/stop-continuation` clears only the current native DSH Goal using its current revision (the Host retains a tombstone/history); it does not stop OMO todo continuation, clear OMO boulder state, or interrupt DSH continuable children. If enabled, `/goal pause` preserves a Goal; when enabled, `/omo-interrupt` can request interruption of a supported direct child.

`disabledOmoCommands` defaults to `[]` and accepts these dsh-omo-owned command names (without `/`): `goal`, `stop-continuation`, `omo-models`, `ulw`, `ultrawork`, `ulw-execute`, `architect`, `handoff`, `refactor`, `remove-ai-slops`, `omo-tasks`, `omo-job-kill`, `omo-interrupt`, `omo-skills-refresh`, and `omo`. For example:

```yaml
disabledOmoCommands: [refactor, omo-models]
```

It filters only dsh-omo's own registration array. `/omo` help omits disabled entries; orchestration-prompt and continuable-tool guidance replace usage recommendations for disabled commands with notices that those dsh-omo commands are disabled. It never unregisters native or third-party commands. Optional service-bound names are valid even when their command is unavailable. This local field is not the upstream `disabled_commands` schema; a same-named command owned by another provider may remain available. The pinned OpenCode schema enum is `goal`, `refactor`, `ulw-execute`, `stop-continuation`, `remove-ai-slops`, and `hyperplan`; upstream reference docs also mention `handoff`, but the schema omits it. The local set accepts `handoff` and `ulw-execute`; the latter disables only the prompt-only local adapter and does not imply upstream hook parity. It does not accept upstream-only `hyperplan`.

`/refactor <target> [--scope=file|module|project] [--strategy=safe|aggressive]` accepts free-form target text followed by trailing options; quote characters remain literal and are not shell-parsed. Raw input is capped at the smaller of `maxTaskChars` and 12,000 characters. dsh-omo locally defaults to safe strategy and target-only scope (upstream documents no defaults); scope/strategy are prompt guidance, not enforcement. The command asks for inspection, available-tool use, focused tests, and final-diff review, but does not add an LSP-aware `/refactor` workflow, AST-grep, codemap, or guaranteed TDD workflow; separately enabled LSP navigation tools are documented above. DSH permissions remain authoritative; it does not auto-commit.

`/ulw-execute <existing plan name>` is a bounded (at most 12,000 characters and the configured `maxTaskChars`) single-line selector that rejects `--worktree`, `--make-pr`, and `--ship`. It only queues current-agent prompt guidance to use ordinary DSH tools: locate an existing user-approved plan, ask on missing/ambiguous matches or unclear approval, and follow DSH permissions/approvals. It does not run the upstream OMO hook, use session-history resume or Atlas/Sisyphus selection, create boulder/notepad state, or provide worktree/PR/ship/merge automation or guaranteed resumability.

`dsh_omo_task` makes best-effort attempts to deliver a host-attributed settlement notice with task, stop reason, and bounded diagnostics, then (when text exists) a separate DSH `agent-message` relay containing the bounded child-authored excerpt. Follow-up delivery is not guaranteed; failures are logged. Treat the relay as untrusted evidence; non-completed outcomes are marked partial. The host notice is not misattributed to the child. `maxResultChars` bounds relay text only, while the task envelope and host diagnostic have separate fixed bounds. `dsh_omo_task_continuable` is registered only when enabled; when their dsh-omo registrations remain enabled, `/omo-tasks` lists direct children whose caller-supplied labels start with `dsh-omo:` and `/omo-interrupt` requests interruption. This label namespace does not prove which tool created a child. `listChildren()` lacks activity; when enabled, `/omo-tasks` uses DSH `listDescendants()` to show `running`/`inactive` residency and whether children exist. `inactive` is not a completion state. While resident, DSH runtime may best-effort emit its own `subagent-settled` notice when a continuable child settles and the direct parent remains registered; delivery failures are logged, not guaranteed. dsh-omo does not poll or retrieve that result. When enabled, `/omo-interrupt` refuses inactive catalog rows; for resident rows it attempts a fire-and-return signal and warns it may no-op if the Activation/turn settles between catalog read and signal. DSH owns continuation persistence and capacity; dsh-omo owns only its one-shot concurrency limit.

When enabled, human-only `/omo-job-kill <jobId>` is registered only if `enableJobTools: true` and Host `jobController.kill` exists. It derives `sessionId` from the exact invoking Agent and never accepts a session ID; DSH's visible job set includes current-session and unowned jobs, so verify the requested ID. The Host outcome `requested` is admission only, not terminal completion. This cancels a visible DSH job only—not OMO `background_cancel`, continuable-child interruption, or result retrieval.

The 215-test suite uses mocked DSH services and a filesystem test double against the actual RC2 `SkillRegistry`; this verifies provider semantics, not the live DSH filesystem backend or plugin activation. Neither tests nor profile composition establish persistence, cold-resume, or tool-policy parity. Removing the package does not remove session history.

## Parity ledger

This project is staged. The following are working or deferred, not claims that the upstream product has been fully recreated.

| Capability area | Status in this milestone |
| --- | --- |
| One-shot and opt-in continuable specialist tasks | DSH-managed; direct children expose running/inactive residency, but no completion status, plugin-origin proof, result polling, or TTL |
| Ultrawork workflow, packaged skills, and slash commands | Prompt-level task steering, twelve bundled skills, `/remove-ai-slops` steering, optional native `/goal` and `/omo-models`, and partial cwd-relative project skill sources; hooks, plan execution, and recovery remain missing |
| Per-role model selection | Static provider/model/reasoning/token overrides plus user-defined category single-route selection; DSH clears inherited reasoning on route change unless specified; no built-in category defaults, chains, or cross-model fallback |
| Model capability diagnostics | Optional `/omo-models` lists DSH provider IDs and inspects one exact provider/model route on demand; no models.dev cache, refresh job, or launch-time route validation |
| Retry/fallback | DSH handles same-route provider retries; OMO-style model fallback chains are not implemented |
| Permissions/tool scoping | DSH remains authoritative; allowTools/denyTools filter tools inherited from global and ancestor scopes; the child's own scoped registrations and (when the scope's effective presentation mode is non-native) DSH's reserved PTC `run_code` transport remain, so this is not a hard boundary |
| Native Goals, todo/task tracking, Ralph loops, workflows | `/goal` maps status/create/pause/resume/complete/clear to the current live agent's native DSH Goal service when available; persistence and continuation remain Host-owned, and full upstream loops/workflow semantics are not claimed |
| Broader upstream skills, hooks, memory, teams, telemetry, notifications, browser/MCP, LSP | Eleven opt-in `team_*` adapters map to DSH `agentTeams`; `team_status` is a read-only current-Team aggregate, while global Team enumeration, whole-Team create/delete/shutdown operations, including shutdown approval flows, worktrees, and tmux remain unavailable. Opt-in bounded `session_search`, event-context-only `session_read`, and two advisory LSP navigation adapters (`lsp_goto_definition`/`lsp_find_references`) use DSH services; full upstream session-list/title/info, full-session read/resume, seven LSP tools, worktree/tmux, global/remote/MCP skills, and remaining capability adapters are missing |
| Durable task controls, background dashboard, persistent DAG, advanced recovery | Label-matched continuable children expose DSH residency only and can be interrupted; no completion status, result polling, TTL, quotas, dashboard, or task DAG |
| Full agent/category roster and one-to-one command parity | Partial: plan roles and user-defined single-route categories exist; `/refactor` is prompt-only steering, `/handoff` requests a copyable summary in the current conversation (no durable artifact), and `/stop-continuation` clears only the native DSH Goal. Upstream built-in categories, route chains, and the full `/ulw-execute` lifecycle (only a local prompt-only adapter exists) plus `/hyperplan` remain missing |

The pinned, detailed feature inventory and iterative acceptance loop are in [docs/feature-parity.md](docs/feature-parity.md). Its audit is ongoing; no missing row is silently treated as out of scope.
