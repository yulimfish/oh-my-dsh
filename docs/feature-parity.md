## Shared catalog follow-up included in 0.1.13

Same-entry explicit `reasoningEffort` wins. An explicit provider/model pair stays literal; alias targets retain their exact model tail and expand before existing route aliases/deduplication.
- Normalized catalogs are immutable and limited to 64 safe aliases and exact bounded target/control strings; reserved prototype keys, unknown fields, unqualified/recursive/cyclic targets and malformed references reject. The pure normalizer additionally rejects accessors/symbols without invoking getters; this is not a claim that native Loader evaluation is a hostile-JavaScript sandbox. Default catalogs are empty. This adds no canonical provider/model tables, network/filesystem/provider discovery, fuzzy selection, implicit parent mutation or suffix parsing. Catalog references now also expand in role/category fallback entries before existing exact-pair route aliases and duplicate checks; explicit pairs stay literal and role/candidate reasoning/token precedence remains unchanged. Invalid configuration fails closed rather than reproducing upstream per-subtree diagnostic recovery.

## 0.1.14 foreground joining and rc.3 compatibility

- Added default-off `enableForegroundTaskTool`/`dsh_omo_task_join`, sharing the existing launcher and sole cache/quota/disposal owner. It waits up to eight seconds after startup and returns bounded untrusted terminal text or the real running child ID; caching is independently optional.

No content is released merely because a wait times out or its caller aborts: native success acknowledges a terminal result or authorizes background handoff, canonical `ABORTED` permits later relay, and other final failures/policy vetoes suppress original and future relays. ## Verified DSH reuse candidates

The fresh `ohmy-test` config composition is described in the audit baseline; it is composition evidence only. The separate `desktop` team bundle is not included in that profile, and active desktop was not changed.

The live Host Inspect `subagents` Service contract exposes `startActivation`, `sendMessage`, `interrupt`, `listChildren`, and `listDescendants`, but no Service-level `start` or `startContinuable`. `SubagentProvider.prepareContinuable` is only a provider hook, not a child-creation API. `listChildren()` catalog rows expose only `id`, `createdAt`, `mode`, and `label`; they are not activity/completion status. `listDescendants()` child rows expose activity `running|inactive`, `hasChildren`, `parentId`, and `depth`; diagnostic rows carry `kind: 'diagnostic'`, `id`, `parentId`, `depth`, and `reason`, without activity, `hasChildren`, mode, or label. `inactive` does not mean completed. `enableContinuableTasks: true` therefore fails dsh-omo setup on this Host, even though a previous isolated-profile dump recorded that option. One-shot `startActivation` returns an Activation with a result Promise; optional default-off `enableTaskResultTool` exposes bounded `dsh_omo_task_result` reads (in-memory by default; optional terminal-only `enableTaskResultPersistence` restores snapshots only when the configured backend retains them) plus `dsh_omo_task_list`, which returns at most 32 retained exact-Agent one-shot child ID/status pairs without result bodies; active entries stay until settlement, terminal results expire 30 minutes after settlement, and reads do not extend TTL. Separate default-off `enableTaskWaitTool` requires result tracking and accepts only a tracked one-shot child owned by the exact parent Agent; it returns an already-cached terminal result or waits 8 seconds by default (maximum 30 seconds, 32 concurrent waiters globally and four per Agent), returns the same cached bounded result on settlement, and reports `running` on timeout/cancellation. Ending the wait never invokes child interruption; this does not add generic session/job polling or durable result retrieval. The `subagent/end` event is emit-only and does not guarantee a user-facing notice; durable continuable-child result retrieval remains unavailable. Direct-child queries and exact-ancestor authority remain parent-scoped. Labels are caller-supplied and do not prove plugin origin. `interrupt()` is fire-and-return; `/omo-interrupt` refuses catalog rows marked inactive and reports an attempt (not confirmed cancellation) for resident rows, which may settle between read and signal.

The optional provider hook `prepareContinuable` and DSH persistence are insufficient by themselves: this Host exposes no `startContinuable` Service API, so dsh-omo rejects `enableContinuableTasks: true` during setup. On any future/legacy Host that adds this method, the selected provider must also implement `prepareContinuable`. A parent creation `maxTokens` value is initially inherited, but is absent from the continuable descriptor and cold-resume state; dsh-omo therefore rejects launch if either the role route or parent has `maxTokens`. If provider/model is explicitly changed without reasoning effort, inherited effort is cleared so the new model can choose its default; this is distinct from other omitted options, which follow their normal merge/inheritance behavior. None of the API surface, config composition, or mocked unit tests alone proves a live provider/session lifecycle.

The inspected Host `agentTeams` contract has membership, roster, teammate spawn, peer message, task CRUD/CAS, wait, and interrupt; `SpawnTeammateRequest` contains name/description/prompt/context/provider/signal, with no per-member worktree or tmux option, and the service has no Team create/delete or mailbox-drain API. Host `worktrees.create(agent, request, signal)` creates a checkout for the exact caller Agent and enters it as that Agent's current cwd; it cannot provision a separate checkout for a teammate as part of spawn. No Host tmux service or Team worktree-assignment contract was found. Consequently, the upstream Team worktree/tmux lifecycle cannot safely be simulated by creating a worktree on the Lead and calling that per-member parity; the missing Host contract would need to atomically bind a dedicated checkout/backend to each spawned teammate and clean it up with Team lifecycle.
