# Oh My OpenCode / OpenAgent parity ledger

> **Status: gap audit in progress.** This is an acceptance ledger, not a completion claim. Every upstream feature remains open until implemented in `dsh-omo`, proven equivalent by a native DSH capability, or shown unavailable in the DSH host with the closest safe adapter documented.

## Audit baseline

- Upstream is pinned to [`oh-my-openagent` SHA `e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6`](https://github.com/code-yeongyu/oh-my-openagent/tree/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6); feature and configuration references below are from this snapshot.
- Initial plugin code baseline: `3398f8a`; continuable-task implementation commit: `0b1121f`. The current follow-up tranche is dsh-omo `0.1.9` with a hardened project-skill provider; this remains a partial parity milestone, not a full recreation.
- The installed DSH runtime descriptor reports DSH `0.2.0-rc.2` and Node `24.21.0`. Separately, the app-bundled CLI at `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh` reports DSH `0.2.0-rc.2`; `dsh-omo doctor` invoked by that CLI printed Node `24.18.1`. These are distinct runtime/doctor observations, not a single reconciled Node version.
- A fresh `--dump-config` from that absolute app CLI shows `ohmy-test` composing base + web + `dsh-omo` 0.1.9, with the user profile patch `enableContinuableTasks: true`. This confirms composition/config intent only—not plugin activation, filesystem service injection, provider capability, or a live task lifecycle. The separate `desktop` profile bundles the experimental agent-team profile; the active desktop profile was not modified.
- “Native reuse” means a comparable user-visible DSH capability; it does **not** mean dsh-omo installs, configures, or verifies it. Mocked tests and profile composition are not live parity evidence.

## Verified DSH reuse candidates

The fresh `ohmy-test` config composition is described in the audit baseline; it is composition evidence only. The separate `desktop` team bundle is not included in that profile, and active desktop was not changed.

The installed RC2 `@deepseek-ai/dsh-subagent` API includes one-shot `start`, durable `startContinuable`, `sendMessage`, `interrupt`, `listChildren`, and `listDescendants`. `listChildren()` catalog rows expose only `id`, `createdAt`, `mode`, and `label`; they are not activity/completion status. `listDescendants()` child rows expose activity `running|inactive`, `hasChildren`, `parentId`, and `depth`; diagnostic rows carry `kind: 'diagnostic'`, `id`, `parentId`, `depth`, and `reason`, without activity, `hasChildren`, mode, or label. `inactive` does not mean completed. DSH runtime may best-effort emit a `subagent-settled` notice when a continuable child settles while resident and its direct parent remains registered; delivery failures are logged. The dsh-omo tool does not poll or retrieve that result. Direct-child queries and exact-ancestor authority remain parent-scoped. Labels are caller-supplied and do not prove plugin origin. `interrupt()` is fire-and-return; `/omo-interrupt` refuses catalog rows marked inactive and reports an attempt (not confirmed cancellation) for resident rows, which may settle between read and signal.

Continuable creation depends on the selected DSH subagent provider implementing the optional `prepareContinuable` method and on DSH persistence. A parent creation `maxTokens` value is initially inherited, but is absent from the continuable descriptor and cold-resume state; dsh-omo therefore rejects launch if either the role route or parent has `maxTokens`. If provider/model is explicitly changed without reasoning effort, inherited effort is cleared so the new model can choose its default; this is distinct from other omitted options, which follow their normal merge/inheritance behavior. None of the API surface, config composition, or mocked unit tests alone proves a live provider/session lifecycle.

## Audit loop

1. Keep this matrix pinned to the source snapshot above; update the pin and re-audit when upstream changes.
2. For each row, obtain independent DSH API evidence, define observable acceptance tests, implement one coherent tranche, and commit it.
3. Commission a fresh adversarial review after each tranche; resolve valid findings and rerun tests/profile checks.
4. Do not mark a feature complete based only on prompts, README claims, bundle composition, or mocked unit tests. Require an API-backed behavior test or precisely documented host-native equivalence.
5. Completion requires every row implemented or independently evidenced as host-native/platform-incompatible; no unverified row may be silently treated as out of scope.
