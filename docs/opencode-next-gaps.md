# Confirmed OpenCode plugin gaps and next work

This is a source/API audit, not a claim that the features below are implemented. The target is the user-confirmed **OpenCode plugin edition**, pinned to `e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6`. Native/Senpi main-session profiles and daemon/DAG behavior are not automatically plugin requirements. Current deployment events remain in the [deployment record](<deployment-record.md>).

## 1. Skill format compatibility — included in the 0.1.14 candidate

The upstream [skill loader](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/loaded-skill-from-path.ts) supplies filename/directory defaults when metadata is absent. Its [directory scanner](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/skill-directory-loader.ts) prioritizes `SKILL.md`, then a directory-named Markdown file.

Local [project skills](<../src/project-skills.js>) **already discover flat root Markdown files**; an initial audit incorrectly called that absent and was corrected after direct source review. The original audit gaps were metadata-light/plain Markdown and directory-named fallback files; an opt-in source subset is now implemented below. A default-off `enableProjectSkillFormatCompatibility` source subset is implemented with valid DSH kebab-case name derivation, absent/falsy name and description defaults, unchanged byte/entry/containment/version checks and no namespace flattening or extra roots. Invalid explicit metadata must still reject. Canonical-file priority must survive stale lookup and truncated directory listings. The native-registry/real-filesystem suite passes 38/38, including seven new compatibility cases and recovery after canonical-file replacement. Complete source and output-contract suites pass 1,246/1,246 each; default Tool schema bytes remain identical to deployed 0.1.13 (2,098 bytes, token delta zero). This bounded subset is included in the 0.1.14 candidate; its installation outcome is tracked separately, not inferred from source checks. Later workspace-only follow-ups skip hidden direct entries in compatibility mode and reject stale hidden locators. The latest source-only scan first truncates each root listing to the existing remaining entry budget, classifies contained targets, and processes directories ahead of flat files within that prefix; it rechecks types, marks failures incomplete, and keeps root and same-type order. Strict discovery is unchanged. Extra metadata operations may increase cost, and entries excluded by root truncation remain undiscovered; this is not full upstream ordering parity. A source-only follow-up in the default-off compatibility mode now traverses at most three directory levels for canonical `SKILL.md` or directory-named Markdown entries when a directory is only a container. Ordinary Markdown inside container directories is now also discovered at up to two directory levels in this default-off mode; it uses flat DSH names and its containing directory as resource base. Directories are read before root flat files, then nested flat files, not upstream's exact depth-first collision order. Nested discovery and cached lookups recheck ancestor canonical/named-file absence before and after reading. Discovery marks the scan incomplete, while lookup invalidates stale locators when a container becomes a skill directory; these checks are not atomic filesystem snapshots. A new higher-priority competitor elsewhere in the root is not rechecked on cached get and relies on watcher invalidation. A source-only provider-wide observation-revision fence now rejects a previously selected locator when its own watcher event is delivered after discovery, including during loading; explicit refresh and provider-detected stale locators also advance the fence before invalidating. Callers must retry. This can conservatively reject loads on unrelated workspace changes, and cannot cover missed/delayed events, other providers, or changes after the final check. Explicit refresh now also retires path-keyed watchers and pending acquisitions so that subsequent scans can rebind after a missed replacement event. Temporary-file regressions cover root, directory and file replacement using an inode-bound watcher substitute; real watcher delivery is not established. Closing or failed handles remain charged to the watcher budget, so immediate rescans can be incomplete and failed disposal can prevent recovery; missed or delayed events without an explicit refresh remain a limitation. Missing-name defaults use the leaf directory without upstream slash namespaces; arbitrary nested Markdown and deeper trees remain unsupported. Strict discovery remains non-recursive. Hidden-name filtering is not a secret-protection boundary. This remains incomplete upstream recursive/namespace/MCP/agent/model execution parity.

### Delegated skill resource context

The Host skill contract provides an optional directory, URL, or opaque resource base, but delegation previously discarded it. A source-only adaptation now includes valid single-line bases as bounded JSON-encoded untrusted guidance (at most 1 KiB UTF-8 per skill); invalid or oversized bases are omitted. It does not resolve references, read resources, grant access, or ensure the child's filesystem accepts a display path. Source tests now pass a real temporary nested project skill through the project provider, native SkillRegistry and ToolRuntime into captured one-shot and foreground activation requests, with admission configured both off and on; category/explicit deduplication and disabled invocation are checked. Activation is mocked, watchers are inert and the admission case is not contended, so these tests do not establish live child access or queue behavior. This is not a claim of exact upstream delegation parity: the pinned upstream [loader](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/loaded-skill-from-path.ts) builds a base-aware template, but its [template extractor](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/loaded-skill-template-extractor.ts) rereads the raw body for filesystem-backed delegation.

## 2. Same-call foreground delegation — bounded 0.1.14 adaptation

The pinned [OpenCode dispatcher](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/tools/delegate-task/tools.ts) separates synchronous and background execution. The default local [delegation](<../src/index.js>) still returns a started child and later delivers settlement/relay. Version 0.1.14 adds default-off `dsh_omo_task_join`, sharing that launcher and waiting up to eight seconds after startup. This is a separate adapted API, not the original upstream task schema or unlimited blocking.

The implemented gate waits for exact-token native `tools/result`, honors successful replacements and policy blocks, and only releases background publication after successful running-result acceptance or canonical native cancellation. Timer/caller cancellation alone cannot bypass output policy. Native and unit suites pass 32/32, including post-body cancellation, policy block concurrent with cancellation, delayed acknowledgements, late startup cleanup and exact-parent disposal. All source and output-contract suites pass 1,278/1,278 against actual rc.3 dependencies. Cache/quota/disposal still have one owner; timeout is not proof the child stopped and no durable resume is claimed.

## 3. Pending background admission — feasible, larger state machine

Upstream [BackgroundManager](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/features/background-agent/manager.ts) and [concurrency](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/features/background-agent/concurrency.ts) keep pending tasks and cancel queued waiters. The local adapter rejects saturation by default; the optional bounded in-call global-and-route admission wait described below does not create upstream-style pending tasks. The pinned upstream [configuration reference](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/docs/reference/configuration.md#L475-L490) describes `defaultConcurrency` as an all-provider maximum, while its [concurrency manager](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/features/background-agent/concurrency.ts) defaults to 5 per model key when no explicit provider/model entry applies. The local `maxConcurrent` instead remains an instance-wide hard ceiling.

A first source-only, process-local `pending-task-registry.js` now implements bounded `bg_*` task IDs, per-parent/global capacity, pending and terminal TTLs, exact-Agent ownership, queued cancellation, one-time child binding/settlement, and detach-on-dispose semantics. A default-off `enablePendingBackgroundTasks` now connects this registry only to direct `dsh_omo_task`: it performs no-wait admission for global and selected-route caps and returns a distinct `bg_*` ID when saturated. The scheduler retries only on admission/capacity notifications, not by acquiring an in-call waiter or spinning; the shared launcher remains unwrapped for foreground join, `dsh_omo_call_agent`, and `commandRoutes`. Launch arguments and normalized skills are copied and bounded, the original Tool signal is detached after queueing, and exact-parent disposal/plugin unload aborts starting work and disposes captured activations. Startup failures, pending expiry for the exact current parent, and child settlement report the pending ID; successful startup has no separate notice. Dedicated exact-Agent `dsh_omo_task_pending_status` and `dsh_omo_task_pending_cancel` Tools accept these IDs; the latter cancels queued/starting work (startup may already have been accepted) or requests fire-and-return interruption of a bound child through its pending ID when DSH supports it. This request does not prove the child stopped and does not expose its child ID. Child-ID result/wait/cancel Tools remain mutually exclusive with this opt-in. Queue state remains process-local with a pending TTL; cross-reload persistence/cancellation and full upstream lifecycle parity remain incomplete. A source-only follow-up now checks caller cancellation when a one-shot activation arrives late, attempts disposal without relaying its result, and retains instance capacity if disposal rejects. Tests cover ordinary current and legacy startup plus native ToolRuntime with a simulated abort-ignoring Host. An accepted child may already have executed; this is not proof of quiescence, and a successful `dispose` is not documented as an OS-level safety boundary. Native ToolRuntime currently surfaces the cleanup warning as a Tool error rather than a canonical `ABORTED` code for this thrown-error path. Further source-only follow-ups observe accessible result rejections for a malformed current-Host activation or legacy-provider run, and retain instance global/route capacity unless the captured disposer succeeds. Cleanup warnings on these and late-cancellation paths use fixed messages rather than Host-controlled error names. Host-provided accessors may still hide values or execute arbitrary same-process code; cleanup failures in other paths remain separate concerns. Instance reload does not prove an unknown worker stopped. A source-only, default-off first stage now offers a bounded FIFO wait inside the original Tool call for global capacity only, configured with `maxPendingTasks` (1–16) and an eight-second monotonic deadline, subject to event-loop scheduling. Waiting launch fields are capped at 32,768 UTF-16 code units; this bounds logical input size, not Host or JavaScript heap allocation. It returns a real child ID only after startup, not an immediate pending ID; route-specific saturation is handled by the combined coordinator described below when enabled. Unit, plugin-fixture and native ToolRuntime tests cover selected ownership, capacity, cancellation and foreground cases; this is not a live deployment test. Opt-in cleanup failures and ambiguous duplicate IDs retain instance capacity without retry; the Host's cross-instance behavior is not guaranteed. A source-only follow-up races the local skill-lookup wait against caller cancellation or unload, forwarding a linked signal to the Host and freeing the launch slot when that wait ends. It retains a separate per-instance lease until each returned `skills.get` Promise settles, capped at 64 unsettled Host calls. Inspect says the current Host itself races provider work against cancellation; a real `SkillRegistry` test confirms its returned Promise can reject while a deliberately uncooperative provider Promise remains pending. This adapter therefore does not bound that underlying work or guarantee termination across reload. This is an adaptation, not an upstream background queue. Either design must not represent an unstarted item as a Host child ID, guess fallback admission lanes, silently retry ambiguous starts, or claim restart persistence. A route-aware queue additionally needs atomic global/selected-route admission and must not hold a global slot while waiting on a saturated route.

The source-only launch route preflights and `/omo status route` now share an instance-local cap of 64 unsettled Host `llm.resolveCallConfig` Promises. Cancellation and timeouts end the wait but retain each lease until its Host Promise settles; saturation fails busy instead of probing more fallback candidates. Host resolver errors are isolated from the gate's own busy decision, so rethrowing an earlier busy error cannot suppress an available fallback. This does not cover think-mode probes, bound adapter work after the Host Promise settles, or span plugin instances. Separately, the source-only preset preflight now shares its own 64-call unsettled-Host-Promise cap between one-shot and continuable launches; it is independent of the route cap. `agentPresets.resolve` has no cancellation parameter, and neither cap proves Host-internal work has stopped or spans plugin instances.

A source-only combined admission coordinator now performs route resolution first, followed by one atomic global-and-route grant. It keeps same-route FIFO while unrelated buckets may bypass a saturated route, shares the existing 8-second/16-waiter limits, and defers skill/prompt loading until a grant. This remains caller-visible waiting, separate from the opt-in pending-ID scheduler described above. That scheduler now has exact-Agent pending status/cancel Tools; its cancel Tool can request fire-and-return interruption of a bound child through the pending ID when DSH supports it, but does not prove stop. The scheduler remains process-local; persistence/reload, distributed cancellation, and other upstream lifecycle behavior are still absent. Resolution may include asynchronous fallback or project preflight, so arrival-order FIFO across routes is not guaranteed; an abort-ignoring resolver retains its separate Host-preflight lease until settlement. The coordinator does not provide upstream pending IDs, persistence, or cross-reload cancellation.

The optional LSP adapters now share a source-only cap of 64 unsettled Host `fs.resolve` Promises per tool factory. Cancellation still prevents later containment checks and LSP dispatch, while the original Host Promise retains its lease until settlement; saturation fails before LSP query. This is backpressure for the existing four operations, not additional upstream LSP parity or a bound on provider-internal work. Hostile or cross-realm Promise accessors can make an original rejection unobservable before any handler attaches; same-process Host objects are not an adversarial-code isolation boundary. A source-only project-command adapter follow-up now shares a separate 64-slot cap for unsettled Host filesystem Promises across command scans and watch-target discovery. Cancellation ends the local wait, while each Host Promise retains its lease until settlement; busy discovery returns an explicit error rather than being treated as an absent command. Actual `fs.watch` calls use the existing watcher cap and are outside this preflight cap. `listDir` has no bounded Host pagination API.

## 4. Bundled specialist presets — new public seam, not a sandbox claim

Fresh Host contracts expose preset registration and a serial `agent/created` event. A preset can install an exact-Agent monotonic `tools.guard` before input. This is a potential named-tool dispatch allowlist beyond merely hiding global tools with `tools.restrict`.

Before shipping it, native tests must deny global and preset-scoped writers, shell/delegation and reserved transport attempts without side effects; verify approved reads, sibling isolation, permissive later middleware, failed initialization, disposal and resume. Public preset definitions expose no arbitrary OS permission/sandbox policy field. A tool-dispatch allowlist is **not** proof of read-only filesystem/network behavior or protection from trusted plugin/direct-service code. A source-only non-default `omo-read-search` declaration now registers a scoped policy plugin that presents native Tools and permits only `read`, `glob`, and `grep` dispatches. It does not change the profile default; select it explicitly through a trusted `roleRoutes[].agentPreset` reference. This is a named Tool-dispatch allowlist, not proof of read-only implementations, direct Service/filesystem/network restrictions, or an OS sandbox. Native ToolRuntime and isolated same-version AgentPresetRegistry/Loader tests now cover mounting, PTC nesting, sibling isolation, denied writer/delegation/reserved transport calls, and disposer cleanup. This remains a named Tool-dispatch allowlist, not proof of read-only implementations, direct Service/filesystem/network restrictions, or an OS sandbox. It has not been installed or live-smoked in the real Profile, and other specialist permission semantics remain open.

## 5. Explicit skill roots and routed commands — narrower adapters need design

Upstream [skill roots](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/loader.ts) and the actual [OpenCode command consumer](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/plugin-handlers/command-config-handler.ts) use additional explicit user/config sources. DSH may already supply user skills, but its inspected API does not expose provider-root inventory, so do not claim all user skills are unavailable. A source-only default-off adapter now accepts normalized absolute `userOpenCodeSkillRoots` and `userClaudeSkillRoots` directories named `skills` (at most two each), with project rank 230–245 and configured OpenCode-before-Claude user precedence below runtime rank 250. A further source-only `userAgentsSkillRoots` option adds at most two explicitly configured absolute roots, without HOME inference. In the same registry layer it follows OpenCode then Claude user roots, consistent with the pinned [skill discovery loader](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/skills-loader-core/src/features/opencode-skill-loader/loader.ts), not the distinct command merge order; existing root ranks remain unchanged. Fractional ranks are accepted by the inspected rc.3 registry, but other providers may compete in those intervals, and extra roots consume the shared scan budget. User roots use their own canonical root as boundary, work without cwd, and share the provider's bounded reads, entry/version checks, stale-locator rejection, and watcher lifecycle; project-only filters do not implicitly disable them. This is not native `customSkillDirs` equivalence, recursive namespace/MCP/agent/model execution, or a claim that every native user source is covered. Any adapter must use explicitly configured roots and native layer precedence, not infer HOME or scan ancestors.

Command agent/model/subtask/handoff metadata is currently rejected by [project commands](<../src/project-commands.js>) rather than silently ignored. The pinned upstream [Claude command loader](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/claude-code-compat-core/src/features/claude-code-command-loader/loader.ts) copies `agent`, `subtask`, and `handoffs` and sanitizes `model`; its [command consumer](https://github.com/code-yeongyu/oh-my-openagent/blob/e50fc64a26f35ea07ceab26a8f23e8853fd2c4d6/packages/omo-opencode/src/plugin-handlers/command-config-handler.ts) remaps agent names; this alone does not establish upstream child-launch or authorization semantics. Locally, rejection skips the whole file: a valid lower-priority same-name command can then be selected, so rejection does not reserve the name or guarantee no command runs. A default-off `enableProjectCommandEmptyDescription` adapter accepts an exact empty-string description and uses the existing filename-derived display fallback; this does not copy upstream's scope-prefixed empty display text and can change same-name selection. A default-off `userAgentsCommandRoots` source now accepts at most two explicit normalized absolute directories named `skills` and scans their direct Markdown files with the same containment, stale-file and shared-budget checks as other user command roots. Within this adapter user precedence is OpenCode → Agents → Claude, following the actual upstream command consumer rather than the distinct skill-discovery order; project roots still precede user roots. This is not recursive Agents command discovery, automatic HOME inference, or native command-source equivalence. A separate default-off `enableProjectCommandBlankDisplayMetadata` adapter accepts nonempty whitespace-only descriptions and empty/blank hints, replacing them with safe DSH display fallbacks rather than forwarding values the Host rejects. Exact empty descriptions remain controlled by the earlier separate option; null, non-string primitives, unsafe values and execution metadata remain rejected. These options can change same-name fallback. A default-off `enableProjectCommandUnterminatedFrontmatter` adapter now treats an opening `---` without the pinned complete closing-delimiter-plus-newline shape as plain Markdown, including an EOF closing marker, matching the pinned frontmatter no-match path. It retains strict closed-YAML errors, body safety limits and normal framing; literal metadata in the fallback is not executed. A separate source-only compatibility follow-up trims skill bodies only in `enableProjectSkillFormatCompatibility`, matching the pinned loader's `body.trim()` while preserving strict-mode whitespace. It also retains the BOM-stripped original body line endings (including CRLF/CR) for that compatibility output, using normalized text only for delimiter/YAML parsing; strict-mode line-ending behavior remains unchanged. A further compatibility-only pure-text step now rewrites at most 64 nonescaping, file-like `@relative/path` references against the already validated canonical skill-directory display path, with a final 256-KiB output cap and literal fallback on overflow/unsupported bases. The same compatibility parser now treats falsy `name`/`description` values as absent and uses the derived leaf name or generated nonempty DSH description, following the pinned loader's `String(data.name || defaultName)` and `data.description || ""` defaults without copying truthy wrong-type coercion; strict mode and truthy invalid metadata remain rejected. It performs no referenced-file reads or permission changes; strict mode remains unchanged. Local hardening also leaves tokens with unconsumed `#`, backslash, or Windows `:` suffixes literal so partial regex matches cannot retarget downstream paths (including NTFS alternate streams); these are safety deviations from the pinned resolver's incomplete-token behavior, not claims of upstream parity. This follows the pinned eager loader's display rewrite, not the separate raw-body template extractor or universal consumer behavior. Neither is full template/path-reference parity. A separate default-off `enableProjectCommandMalformedFrontmatter` adapter now follows the pinned closed-block YAML parse-error path: discard all metadata and preserve only the body, with the existing display fallback and safety limits. Valid YAML unsupported fields, duplicate keys, multiple documents, warnings and incomplete delimiters remain strict; this is an opt-in selection change, not execution-metadata acceptance. A separate default-off `enableProjectCommandEmptyBody` adapter accepts empty/whitespace-only command bodies, rendering the pinned empty instruction plus unconditional request section while retaining byte/control/argument caps. It changes same-name fallback only when enabled and does not add shell or execution metadata support. A default-off `enableProjectCommandPreserveBodyLineEndings` adapter now preserves original command body CR/CRLF/LF line endings while keeping normalized text for parsing; outer trim, argument substitution and all caps remain unchanged. This is a source-fidelity subset, not a change to execution or frontmatter authority. Native command definitions do not expose equivalent route fields. A source-only, administrator-configured `commandRoutes` adaptation can now route selected discovered command names to enabled existing specialist roles. It returns an asynchronous child ID and uses the existing settlement relay rather than queueing the original prompt. Setup rejects unknown/disabled roles, duplicate routes and built-in/disabled command conflicts; a mapping does not create a command or override shadowing. Text-only, one-shot execution, result ownership and cancellation stay within the existing launcher; this is not upstream `agent`/`model`/`subtask`/`handoffs` parity or frontmatter-driven route selection. A separate default-off `enableAutomaticSlashCommands` adapter now rewrites eligible real-user project-command invocations in pre-step while excluding routed commands; it is not upstream's complete command/skill/shell expansion lifecycle. It has not been installed or live-smoked. Project metadata must not silently choose an egress model or acquire permissions.

## 6. Pressure-triggered compaction — safe turn-boundary subset

The pinned OMO hook evaluates pressure after each tool and can summarize within the current turn at a 78% context threshold. A default-off DSH adapter now runs only at the serial awaited `agent/turn-stopping` boundary, after live tools settle; it verifies exact live Agent/Session identity and calls `compaction.compactIfNeeded({ session, options: {} }, 'pressure', signal)`. DSH owns the threshold and summary range, and the adapter may delay turn closure while compaction runs. This is a safer turn-boundary subset, not same-turn OMO timing, cached usage/model selection, cooldown, post-compaction monitoring, or degradation recovery.

## Still Host-limited

Malformed raw tool-argument repair is not supported by the freshly inspected public hooks: pre-execute receives parsed immutable arguments; tools/execute can replace only its signal. Pre-step user-message editing and postcommit session events are not decoders for generated tool-call JSON. Keep after-failure guidance separate from parser repair.

## Project-skill watcher capacity recovery

Workspace-only follow-ups watch the lexical parent of every configured-root component before examining it, then conservatively reset provider watchers and invalidate all catalogs when a watched parent changes. This covers the observed directory-to-symlink race when notifications are delivered, but uses more watcher capacity. Since DSH's callback supplies no changed entry name, even an unrelated parent-directory event currently resets watchers and caches across workspaces; frequent events can keep scans incomplete and cause repeated rebuilds. Old-generation scans cannot be cached or start new watchers; pending watches that ignore cancellation, and asynchronous or failed closes, continue to consume capacity until actually settled. A later source-only follow-up also resets all provider watches on a skill-directory event and retires the individual file watch on a file event, so the next lookup can rebind after an observed same-path replacement. Directory events can therefore also cause cross-workspace churn; a file event alone still invalidates the shared catalog but does not retire unrelated watches. Without a delivered notification, old watchers can remain allocated or bound to old objects. The public filesystem contract does not guarantee atomic path/watch binding, lossless events, or race-free reads. Incomplete observations return current candidates but are not cached. Tests use temporary directories with manually delivered watcher callbacks, not the actual DSH filesystem watcher backend.

A possible future reduction in watcher churn is a bounded dependency graph between logical lookup-root groups and watcher identities. Directory notifications would retire the connected component of groups and shared watchers, not merely zero-reference watches: another group may still reference a watcher attached to a replaced object. This is a design hypothesis, not implemented or verified. Registration must precede awaits; overflow must fail discovery incomplete rather than drop dependencies; generation fencing, in-flight ownership, slow/failed close accounting and synchronous callback reentrancy need explicit tests. `control.invalidate()` still invalidates the registry globally, so even a correct graph would not isolate registry-cache invalidations.

A source-only compatibility follow-up adds `(scope - Skill)` to catalog descriptions: project OpenCode maps to `opencode-project`, user OpenCode to `opencode`, project Claude/Agents and custom project roots to `project`, and user Claude/Agents to `user`. The post-prefix 2,000-character limit remains enforced; a falsy original description retains the local generated fallback rather than upstream's empty suffix. Strict-mode descriptions remain unchanged.

No upstream source or canonical table was copied for this audit. Licensing review remains necessary before any such redistribution.
